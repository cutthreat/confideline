# Функциональное ТЗ G3.INT «Интеграция новой верстки Oracle / Nebula с backend Confideline»

## 1. Цель

Подключить новую верстку Oracle / Nebula к существующему backend Confideline так, чтобы клиент получил новый интерфейс сайта, а все данные, действия, права, деньги и состояния продолжали работать через единую серверную логику проекта.

Итогом должна быть не отдельная статическая копия сайта и не набор демонстрационных HTML-страниц, а рабочие страницы на реальных маршрутах Confideline.

## 2. Место G3.INT в общем продукте

```text
принятая верстка Oracle / Nebula
+ реальные маршруты и данные Confideline
+ правила G1, G2 и G3.1–G3.7
-> рабочие клиентские страницы
-> G3.5 сквозная приемка клиентского пути
```

G3.INT отвечает за интеграцию представления с backend. Это сквозной implementation package, а не новая продуктовая задача: он не меняет канонический реестр 30 задач, не придумывает бизнес-правила и не заменяет G3.5, которая независимо проверяет уже собранный продуктовый путь.

Класс G3.INT: `MIXED`. Основная layout/backend-интеграция относится к разработке. Работа с контентом и настройками остаётся у существующих admin-владельцев.

Подпоток `G3.INT.I18N` имеет класс `OPS_FIRST`:

1. moderator/super-admin инвентаризирует видимые строки;
2. ищет и переиспользует существующие keys;
3. заполняет RU/EN и необходимые rollout-locales через существующий раздел `Языки`;
4. выполняет cache refresh, admin readback и public readback;
5. классифицирует остатки как `existing_ok`, `translation_missing`, `key_missing`, `broken_binding` или `runtime_gap`;
6. Игорь получает только `key_missing`, `broken_binding`, hardcoded production copy, placeholder/pluralization defect, unsafe import-runtime или иной доказанный technical gap.

## 3. Продуктовый результат

После выполнения задачи:

1. новая верстка открывается на целевых маршрутах сайта;
2. страницы получают реальные данные, а не демонстрационные значения;
3. все видимые действия выполняют реальные серверные операции;
4. гость и авторизованный клиент видят корректные для своей роли состояния;
5. существующие URL, языки, SEO, авторизация и история пользователя не ломаются;
6. старую версию можно безопасно вернуть без потери данных;
7. G3.5 может проверить единый путь от витрины до консультации.

## 4. Границы задачи

### Входит

- общий клиентский shell новой версии: header, navigation, footer, mobile navigation и общие состояния;
- витрина G3.1;
- expert-only dashboard, каталог, country/city/category surfaces G3.2;
- профиль Эксперта G3.3;
- подбор и matching result G3.4;
- login, signup и возврат пользователя в начатый сценарий;
- подключение реальных карточек Экспертов, специализаций, методов, цены, availability, rating и reviews;
- подключение фильтров, сортировки, pagination и empty states;
- переходы в бесплатный диалог, consultation request и другие разрешенные действия;
- отображение персональных состояний клиента: баланс, активная/ожидающая консультация и последние консультации там, где это предусмотрено владельцем функции;
- инвентаризация всех видимых строк новой верстки, создание недостающих translation keys и заполнение переводов через существующую систему языков Confideline;
- существующая система переводов, SEO и локализованных маршрутов;
- безопасный поэтапный rollout и rollback;
- runtime evidence для каждой интегрированной поверхности.

### Не входит

- изменение продуктовых правил G1/G2;
- новая state machine консультации;
- изменение финансовых формул, packages, refunds или Agent accruals;
- разработка отдельной второй админ-панели;
- перенос внутренних staff-экранов в публичную верстку;
- автоматическое признание всех Oracle / Nebula HTML production-ready;
- полный редизайн экранов, для которых нет принятого source-backed варианта;
- сквозной release verdict — его выдает G3.5;
- удаление legacy-кода до успешного rollout и rollback proof.

## 5. Роли и видимость

### Гость

Видит публичную витрину, каталог, региональные страницы и профиль Эксперта. При попытке написать или начать персональный сценарий проходит авторизацию, после которой возвращается к выбранному Эксперту и сохраненному intent.

### Клиент

Видит те же публичные поверхности и свои персональные данные: разрешенные действия, баланс, связанные диалоги и консультационные состояния. Не видит внутренние ID, Agent, staff-комментарии и служебные причины.

### Эксперт

На публичном сайте представлен своей экспертной анкетой. G3.INT не дает ему новых прав редактирования и не раскрывает внутренние данные других анкет.

### Агент и модератор

Не получают отдельного публичного режима новой верстки. Их рабочие функции остаются в staff/admin-контуре соответствующих задач.

### Super-admin

Видит фактическую версию интерфейса, карту подключенных поверхностей, режим rollout, источник данных, ошибки binding и audit переключений. В MVP управление доступно super-admin; дальнейшие права назначаются через существующий permissions.

## 6. Реестр интегрируемых поверхностей

G3.INT использует тот же стабильный реестр, что G3.6/G3.7:

1. `home`;
2. `dashboard_catalog`;
3. `country`;
4. `city`;
5. `category`;
6. `matching_result`;
7. `thematic_block`;
8. `expert_profile`.

Дополнительно подключаются общие auth-состояния и shared shell. Они не становятся новыми eligibility surfaces и не создают параллельную taxonomy.

Для каждой поверхности должна существовать явная карта:

- целевой route;
- source layout и его статус;
- владелец данных;
- видимые действия;
- loading/empty/error states;
- режим rollout;
- runtime acceptance status.

Скрытые aliases и неявное наследование маршрутов запрещены.

## 7. Правила использования верстки Oracle / Nebula

1. Figma и source-backed Oracle / Nebula страницы задают визуальный результат.
2. Статический HTML является источником структуры и поведения интерфейса, но не источником бизнес-данных.
3. Демонстрационные имена, цены, рейтинги, online-статусы, reviews и counters не переносятся в рабочий сайт.
4. Исторические или заблокированные layout-кандидаты не включаются публично без отдельного source/visual gate.
5. Общие принятые components и responsive rules переиспользуются, а не копируются в независимые версии для каждой страницы.
6. Если layout расходится с принятым PM-ТЗ, продуктовое поведение определяется PM-ТЗ; визуальное расхождение возвращается на согласование, а не исправляется новой бизнес-логикой.

## 8. Основной сценарий интеграции поверхности

Для каждой поверхности Игорь:

1. фиксирует действующий route и фактическое текущее поведение;
2. связывает route с принятой новой версткой;
3. заменяет demo data реальными источниками владельцев G1–G3;
4. связывает каждую CTA, форму, filter и pagination с реальным действием;
5. реализует loading, empty, error и unauthorized состояния;
6. проверяет языки, SEO, mobile/desktop и role visibility;
7. включает поверхность сначала в preview;
8. проводит runtime-проверку;
9. включает ограниченный rollout;
10. сохраняет возможность отката к предыдущему представлению без отката пользовательских данных.

## 9. Данные и единые владельцы

G3.INT только отображает или передает данные владельцев:

- профиль, специализации, methods и reviews — G3.3/G3.6;
- display/action eligibility и порядок — G3.7;
- matching result — G3.4;
- effective price в credits/minute и баланс — G2.1;
- request, consent, session и history — G1.1/G1.3;
- постоянный диалог и сообщения — G1.2;
- availability и assignment — G6;
- support/refund indicators — G4/G2.3.

G3.INT не хранит параллельные копии этих данных и не рассчитывает собственную цену, eligibility, rating или session status.

## 10. Карточки Экспертов

Одна и та же анкета на home, dashboard, country, city, category, matching result и related blocks должна использовать единый контракт данных.

Карточка:

- показывает только фактические публичные поля;
- получает effective price в credits/minute;
- получает real availability;
- получает итоговые capabilities G3.7;
- не показывает недоказанные counters или KPI;
- ведет в канонический профиль;
- не обещает немедленный paid start;
- непосредственно перед финансовым стартом проходит свежие guards G1/G2/G6.

## 11. Действия, формы и авторизация

Каждое видимое действие обязано иметь реальный результат.

- Гостевая CTA сохраняет выбранного Эксперта, тему и введенный вопрос, затем открывает auth.
- После успешной авторизации пользователь возвращается в исходный сценарий.
- Повторная отправка формы не создает дубль действия.
- Недоступное или запрещенное действие отклоняется server-side, даже если вызвано напрямую.
- При устаревшем availability/price/eligibility интерфейс получает актуальное состояние и не продолжает ложный сценарий.
- Ошибка одного действия не должна повреждать профиль, баланс, диалог или session.

Кнопки без реального backend-result не показываются как рабочие.

## 12. URL, языки и SEO

Обязательный P0 workstream `G3.INT.I18N` выполняется внутри G3.INT и не создаёт новую продуктовую задачу или вторую translation-админку.

1. Сохраняется мультиязычная структура `/{lang}/...`.
2. Каждая видимая системная строка новой верстки заменяется стабильным translation key; hardcoded клиентские тексты в production запрещены.
3. До подключения страницы moderator/super-admin формирует реестр: key, назначение, поверхность, контекст, утверждённый русский и английский текст, placeholders/pluralization, допустимость HTML, functional owner, статус каждого языка и technical disposition.
4. Сначала выполняется поиск существующего key. Если key существует, moderator заполняет или исправляет перевод и делает readback. Только доказанное отсутствие key или broken binding передаётся Игорю; новый key остаётся редактируемым в разделе `Языки`. Отдельная система переводов Oracle / Nebula не создаётся.
5. Русский и английский являются обязательной исходной парой. До включения конкретной публичной локали все обязательные ключи этой поверхности должны иметь проверенный перевод на соответствующий включённый язык.
6. Набор «необходимых языков» определяется явной матрицей `surface × rollout locale` в управлении rollout G3.INT. Она ссылается на существующие Language IDs и не копирует переводы; глобальный статус языка сам по себе не означает, что новая Nebula-поверхность уже готова для этой локали.
7. Динамические значения, имена, цены, числа и даты не копируются в ключи, а передаются как типизированные и безопасно экранированные placeholders. Для plural forms и форматирования используется действующий механизм выбранной локали.
8. Один ключ не переиспользуется для нового смысла. Изменённый смысл получает новый key либо явную versioned migration; устаревший key выводится из использования контролируемо.
9. G1–G4 и другие функциональные владельцы предоставляют утверждённый смысл сообщений; moderator размещает и переводит его. Игорь отвечает только за отсутствующие/сломанные key bindings и runtime, но не переписывает product, financial, support или legal-правила.
10. Активный язык сохраняется при переходах, auth и возврате в intent.
11. Canonical, title, description, hreflang и index/noindex читаются из существующих владельцев SEO/translation.
12. Персональные dashboard, баланс, dialogs и consultation states не индексируются.
13. Изменение route требует явного redirect/canonical решения; тихие дубли URL запрещены.
14. Старые внешние ссылки не должны вести на 404 после rollout.
15. Массовая загрузка переводов использует существующий import-контур только в безопасном translation-only режиме: preview/dry-run и diff обязательны, а создание языка, изменение его глобального статуса и изменение нецелевых ключей запрещены.
16. Перед импортом сохраняются preimage и hash целевых значений. Запись выполняется как один контролируемый batch: ошибка в одном элементе не оставляет частично применённый набор.
17. Повторная загрузка того же пакета идемпотентна и показывает `0 changes`. Конфликт с ручной правкой после preimage останавливает batch и требует нового preview.
18. Для batch фиксируются actor, time, source package, target locales/keys, diff, result и rollback reference. После записи обязательны cache refresh, admin readback и public readback.

## 13. Состояния страницы

Каждая динамическая поверхность имеет:

- `loading` — skeleton без фиктивных данных;
- `ready` — реальные данные и разрешенные действия;
- `empty` — понятное отсутствие результатов и безопасный следующий шаг;
- `unauthorized` — auth с сохранением intent;
- `stale` — обновление данных и отмена устаревшего действия;
- `error` — безопасное сообщение и retry без дубля;
- `degraded` — только те данные и действия, истинность которых подтверждена.

Ошибка не заменяется демонстрационными Экспертами, ценами или online-статусами.

## 14. Responsive, accessibility и визуальная приемка

Обязательные контрольные ширины: `320`, `576`, `768`, `992`, `1200`.

На каждой ширине:

- отсутствует горизонтальная прокрутка;
- header/footer/navigation сохраняют принятую иерархию;
- карточки, filters, forms и CTA доступны;
- текст, таблицы, изображения и controls не обрезаны;
- keyboard navigation и видимый focus работают;
- формы имеют labels и понятные errors;
- контент не меняет смысл между desktop и mobile;
- нет скачков layout, мешающих основному действию.

Визуальная проверка проводится по актуальному source/Figma для конкретной страницы, а не по памяти или screenshot-замене.

## 15. Rollout и rollback

Для каждой поверхности используются явные режимы:

- `legacy_active` — работает текущая версия;
- `nebula_preview` — новая версия доступна super-admin/tester;
- `nebula_limited` — ограниченный согласованный rollout;
- `nebula_active` — новая версия является основной;
- `rollback_active` — временно возвращено прежнее представление.

Переключение:

- не меняет доменные данные;
- имеет actor, time, reason, old/new value и build marker;
- не разрывает активную пользовательскую сессию;
- не создает второй URL без canonical решения;
- позволяет вернуть предыдущую версию представления.

Новая поверхность не получает `nebula_active`, пока ее task-specific runtime и visual proof не пройдены.

## 16. Размещение управления в админ-панели

Не создается отдельная дублирующая «админка Oracle».

Используются существующие владельцы:

- `Настройка темы` и `Темы` — active theme, preview, rollout/readback;
- `Языки` (`/{lang}/admin/language/list` и существующая страница переводов) — создание, поиск и редактирование translation keys и переводов;
- существующий SEO/translation contour — metadata;
- G3.1 — содержимое и порядок блоков витрины;
- G3.3 — review policy;
- G3.4 — matching settings;
- G3.6 — taxonomy/completeness;
- G3.7 — eligibility/ranking;
- G1/G2/G4/G6 — собственные operational settings.

На стороне theme settings требуется карта surface → layout version → rollout mode → rollout locales → build marker → last proof. Выбор rollout locales ссылается на существующие языки и управляет только допуском новой поверхности, не хранит копии ключей или переводов. Бизнес-настройки других задач там не дублируются.

В существующем разделе `Языки` должен быть доступен однозначный scope/filter для ключей Nebula и контроль покрытия по включённым локалям. Это расширение текущего translation-контура, а не новая страница с отдельной копией переводов.

## 17. Связанные задачи и зависимости

- G3.1–G3.4 определяют продуктовые страницы и действия.
- G3.6 определяет taxonomy/completeness input.
- G3.7 определяет display/action eligibility и ranking.
- G1/G2 определяют dialog, request, session, history, price, balance и paid behavior.
- G4 определяет support/refund entry points.
- G4 предоставляет утверждённые тексты support/refund/policy и legal-ready формулировки; G3.INT превращает их в translation keys и подключает переводы, не меняя их смысл.
- G5.1 определяет события воронки.
- G6 определяет availability, assignment и admission.
- G3.5 принимает сквозной путь после task-specific acceptance G3.INT.

## 18. Ошибки и особые случаи

Обязательно обработать:

1. route существует, а layout отсутствует;
2. layout существует, но source status блокирует публикацию;
3. backend вернул пустой список;
4. Эксперт стал недоступен между render и CTA;
5. цена изменилась после открытия страницы;
6. пользователь авторизовался в другой вкладке;
7. auth callback повторен;
8. filter/query содержит недопустимое значение;
9. pagination изменилась из-за обновления списка;
10. translation key отсутствует;
11. translation key существует только на русском или английском, но поверхность включают для другой локали;
12. placeholder отсутствует, имеет неверный тип либо переведён как обычный текст;
13. один key используется для двух разных смыслов;
14. asset не загрузился;
15. SEO metadata не определена;
16. старая ссылка открывает новый route;
17. partial rollout дает разные shells в одном journey;
18. rollback выполняется во время активного диалога/consultation;
19. cache показывает заблокированную анкету;
20. direct action выполнен без разрешенной capability;
21. demo data случайно попала в production build.

## 19. Что запрещено

- публиковать статический export как рабочий сайт;
- обслуживать одну бизнес-операцию двумя независимыми реализациями;
- доверять цене, eligibility, balance или role из client-side markup;
- сохранять demo profiles и фиктивные ratings;
- менять accepted business rule ради удобства layout;
- включать неподтвержденную страницу сразу для всех;
- создавать отдельные translation, SEO, reviews, pricing или ranking settings внутри theme screen;
- удалять rollback path до отдельного post-acceptance решения;
- объявлять G3.INT принятой только по визуальному сходству.

## 21. Критерии готового результата

1. Все восемь G3 surfaces имеют явную route/layout/data/action карту.
2. Shared shell и auth состояния интегрированы без отдельной второй навигации.
3. Demo data отсутствует.
4. Все CTA и forms имеют реальный server-side result.
5. G3.6/G3.7 остаются единственными владельцами taxonomy/completeness и eligibility/ranking.
6. G1/G2 остаются владельцами consultation и money behavior.
7. Locale, SEO, auth intent и внешние URL сохранены.
8. Выпущен полный реестр translation keys новой верстки, отсутствуют hardcoded production-строки.
9. Для каждой включаемой Nebula-локали доказано 100% покрытие обязательных ключей выбранных поверхностей; неполная локаль fail-closed.
10. Переводы редактируются и читаются обратно через существующий раздел `Языки`, без второй translation-админки.
11. Translation import имеет dry-run/diff, preimage/hash, atomic result, audit, идемпотентный повтор, rollback и не может менять Language/status.
12. Loading/empty/error/stale/degraded состояния доказаны.
13. Visual proof выполнен на пяти ширинах по актуальному source.
14. Unauthorized, duplicate, concurrent и stale cases не создают side effects.
15. Preview, limited rollout и rollback доказаны.
16. Admin settings не дублируют существующих владельцев.
17. Для каждой поверхности есть build marker и runtime evidence.
18. G3.5 явно потребляет принятую G3.INT build.

## 22. Development handoff и операционный handback

### До реализации

Игорь передает:

- инвентаризацию текущих routes и backend actions;
- карту Oracle / Nebula source pages и их актуальных статусов;
- surface-by-surface mapping;
- список demo/stub данных, подлежащих замене;
- список конфликтов layout с действующими PM-ТЗ;
- план поэтапного rollout/rollback;
- список зависимостей и task-specific test plan.

До этого moderator/super-admin передаёт baseline существующих admin owners и отдельный I18N registry с результатами existing-key search, translations/readback и technical disposition. Игорь не повторяет операционную инвентаризацию как автор текстов.

### На QA

Игорь передает development evidence:

- build marker и перечень измененных surfaces;
- route/layout/data/action matrix;
- proof реальных данных и server-side действий;
- role/ACL и auth-intent proof;
- locale/SEO proof;
- список исправленных `key_missing/broken_binding/hardcoded/runtime/import-safety` gaps и build proof;
- screenshots/visual comparison на пяти ширинах;
- loading/empty/error/degraded proof;
- duplicate/concurrent/stale/cache cases;
- preview/limited rollout/rollback readback и audit;
- список residuals;
- готовность передать сборку в G3.5.

Moderator/super-admin отдельно передаёт итоговый translation-key registry, матрицу покрытия rollout-locales, import/readback/rollback evidence и подтверждение, что утверждённые значения отображаются. QA независимо проверяет интегрированный пакет перед G3.5.
