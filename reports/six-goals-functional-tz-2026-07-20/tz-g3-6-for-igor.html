Операционно-функциональный пакет G3.6 «Полнота и готовность анкеты Эксперта»

Инструкция super-admin по taxonomy/completeness и правила технической эскалации.

1. Цель

Создать объяснимую и управляемую оценку полноты экспертной анкеты, а также единый версионированный справочник тем и специализаций, на котором строятся фильтры и публичные данные профиля.

Система должна различать:

  • обязательные данные, без которых анкета не может появиться на конкретной поверхности;
  • полезные данные, повышающие полноту;
  • информационные данные, не влияющие на оценку;
  • рискованные данные, требующие проверки или блокирующие публикацию.

Super-admin должен понимать итог анкеты, видеть вклад каждого правила и безопасно менять правила через версии и preview.

Класс исполнения: OPS_FIRST.

  • Super-admin сначала фиксирует фактическую semantics map существующих profile fields, specialization IDs, translations и текущий readback.
  • Он утверждает taxonomy/completeness rules, overrides, preview/publish/rollback и операционный результат.
  • Игорь получает только подтверждённый gap evaluator, snapshots, versioning, binding, bulk action, ACL либо отсутствующей admin capability.
  • Содержимое полей, taxonomy meaning и решение о публикации не передаются разработчику.

2. Место G3.6 в общем продукте

G3.6 отвечает за два связанных входа в клиентские поверхности:

  • версионированную таксономию категория -> специализации -> методы;
  • оценку полноты и blockers конкретной анкеты под опубликованной версией правил.
taxonomy registry + profile fields
-> validation / moderation
-> versioned completeness evaluation
-> eligibility input для G3.7
-> финальное решение G3.7
-> карточка / каталог / витрина / разрешённые действия

G3.6 не выдаёт display_eligible, не назначает capabilities[], не решает окончательный порядок выдачи и не заменяет admission, assignment, availability, safety moderation или quality review. Эти результаты принадлежат G3.7; возможность начать paid-режим дополнительно проверяется свежим транзакционным guard G1/G2/G6.

Минимум V3 limited paid pilot: опубликованная expert_specialization_taxonomy_v2 и вручную управляемый, объяснимый completeness/blocker input G3.6. G3.7 при этом применяет eligibility и manual order; G3.6 не допускает анкету на поверхность самостоятельно. Полная автоматизация completeness относится к V5 public scale.

Полный стабильный registry surface IDs одинаков для G3.6 и G3.7: home, dashboard_catalog, country, city, category, matching_result, thematic_block, expert_profile. Для каждого ID applicability задаётся явно; несуществующая, сокращённая или скрыто унаследованная surface-конфигурация запрещена.

3. Продуктовая идея

Формально непустая анкета не всегда полезна клиенту. Одно слово, повторяющийся текст, запрещённое обещание или нерелевантное значение не должны давать такой же результат, как содержательная и проверенная информация.

Оценка G3.6:

  • помогает администратору подготовить анкету;
  • не является публичным рейтингом Эксперта;
  • не является KPI Агента;
  • не гарантирует качество консультации;
  • не подменяет ручную модерацию рискованных формулировок;
  • хранит версию правил, по которым получен результат.

4. Термины

Field rule

Управляемое правило для одного profile field и одной или нескольких поверхностей.

Блокирующее поле

Поле или условие, отсутствие которого создаёт blocker input для указанной поверхности. Итоговый display_eligible рассчитывает G3.7.

Весовое поле

Поле, валидное заполнение которого вносит определённый вклад в completeness score.

Информационное поле

Поле, которое может показываться клиенту или staff, но не влияет на score и completeness/blocker input.

Рисковое поле

Поле, содержимое которого требует проверки claims/safety/content и может временно блокировать публикацию.

Completeness score

Объяснимая оценка заполненности под текущей опубликованной версией правил. Она не равна качеству консультации.

Evaluation snapshot

Сохранённый результат оценки анкеты: версия правил, входные значения/статусы, вклад, blockers и итог.

Taxonomy registry

Опубликованная версия связей между короткой клиентской категорией, полной категорией, значениями Specialization и методами Эксперта. Страницы используют registry и не хранят собственные списки.

Manual override

Ручное решение super-admin с причиной, scope и сроком, которое меняет только completeness/blocker input. Оно не является прямым разрешением или запретом показа: окончательное решение остаётся в G3.7.

5. Роли

Клиент

Не видит внутренний score и служебные причины. Видит только допустимую публичную анкету и реальные заполненные поля.

Эксперт / Агент

Может видеть понятный список того, что требуется дозаполнить или исправить, если такая staff-поверхность предоставлена. Не может менять веса, blockers или итоговую модерацию.

Модератор

Проверяет назначенные ему поля/контент в пределах permissions. Не может самовольно менять глобальные правила полноты.

Super-admin

Создаёт draft правил, проверяет preview, публикует версию, видит причины результата, выполняет допустимый override и rollback.

6. Классы полей

6.1. Блокирующие

Стартовый продуктовый состав должен включать как минимум:

  • публичное имя/псевдоним;
  • допустимое фото;
  • язык консультации;
  • основную тему/специализацию;
  • основной метод или понятное направление;
  • короткое описание;
  • действующую цену либо применимый источник цены;
  • подтверждённое согласие с правилами работы;
  • допустимый moderation status.

Конкретный набор и scope управляются в админ-панели. Блокирующее поле не получает произвольный числовой вес: его результат — выполнено/не выполнено/ожидает проверки/не применимо.

6.2. Весовые

Примеры:

  • дополнительные специализации;
  • структурированное описание;
  • консультационный стиль;
  • опыт;
  • языки;
  • методы и практики;
  • качественно заполненные ответы профиля;
  • опубликованные допустимые отзывы.

Весовой вклад засчитывается только при валидном значении.

6.3. Информационные

Необязательные биографические и дополнительные поля, отсутствие которых не понижает score и не блокирует анкету.

6.4. Рисковые

Примеры:

  • обещание гарантированного результата;
  • медицинские, юридические или финансовые утверждения;
  • страх, давление или зависимость;
  • неподтверждённые claims;
  • запрещённые контакты;
  • спорное изображение;
  • небезопасные формулировки.

Рисковое поле получает отдельный moderation status. Простое наличие текста не считается успешным заполнением.

8. Правила валидности

Для каждого учитываемого поля определяется наблюдаемое условие валидности:

  • значение присутствует;
  • соответствует допустимому типу/варианту;
  • прошло требуемую модерацию;
  • не является технической заглушкой;
  • не содержит запрещённых утверждений;
  • соответствует выбранному языку и поверхности;
  • если требуется источник, он указан;
  • если поле устарело, оно не засчитывается до подтверждения.

Пустое, мусорное, дублированное или запрещённое значение не даёт положительный вклад.

Отсутствие необязательного поля обозначается optional_missing, а не fraud, quality fail или нулевое качество.

9. Расчёт и результат

Для каждой опубликованной версии правил система формирует:

  • итоговый score, если он применим;
  • максимальный возможный score;
  • выполненные blockers;
  • невыполненные blockers;
  • поля, ожидающие проверки;
  • weighted contribution по каждому полю;
  • optional missing;
  • risk blockers;
  • surface-specific eligibility input;
  • применённую taxonomy_version;
  • время оценки и версию правил.

Публично score не показывается по умолчанию. Клиенту показываются реальные данные, а не внутреннее число.

При одинаковых данных и одной версии правил результат воспроизводим.

10. Поверхности и scope

Правило задаёт applicability отдельно для каждого стабильного ID:

  • home;
  • dashboard_catalog;
  • country;
  • city;
  • category;
  • matching_result;
  • thematic_block;
  • expert_profile.

Массовое «ко всем» допускается только как явное действие редактора, разворачивающее значения для всех восьми IDs в draft/preview. Скрытой inheritance и отдельной paid-start surface нет: fresh paid-start guard остаётся вне G3.6.

Разные поверхности могут иметь разные обязательные поля. Например, отсутствие region assignment не должно блокировать общий online-каталог, но может исключить анкету из конкретной city page.

G3.6 передаёт G3.7 completeness_status, blocker codes, применённые rule/taxonomy versions и объяснение. Только G3.7 формирует итоговые display_eligible, capabilities[], reason_codes[] и позицию анкеты. Канонический список capabilities закрыт: open_profile, send_free_message, notify_availability, create_consultation_request; paid-start capability не существует.

11. Версии правил

  1. Изменения создаются в draft.
  2. Draft имеет preview на выбранных анкетах.
  3. Публикация создаёт новую неизменяемую версию с effective time.
  4. Новая оценка использует текущую опубликованную версию.
  5. Исторический snapshot не переписывается.
  6. Rollback публикует новую версию, основанную на предыдущей допустимой версии.
  7. Неполная или невалидная версия не активируется.
  8. Массовая переоценка показывает прогресс и ошибки; частичный сбой не смешивает версии.

12. Manual override

Для pilot super-admin может вручную изменить completeness/blocker input анкеты для выбранной поверхности. G3.7 затем заново применяет остальные eligibility-правила; прямого «допустить/исключить из каталога» в G3.6 нет.

Override обязан содержать:

  • actor;
  • причину;
  • область применения;
  • начало;
  • срок либо явное «бессрочно»;
  • исходный автоматический результат;
  • ожидаемый входной результат для G3.7;
  • audit/history.

Override не может:

  • отменить admin/safety block;
  • разрешить paid start без admission/assignment/price;
  • напрямую установить display_eligible, capabilities[] или позицию;
  • скрыть невыполненный обязательный blocker в readback;
  • переписать исторические snapshots.

После истечения override автоматически перестаёт влиять, а анкета снова оценивается по текущим правилам.

13. Существующие поля

Переиспользуется существующий контур profile fields и profile field categories.

Важно различать продуктовый смысл:

  • поле опыта в годах сохраняет свой текущий смысл;
  • ручное значение «число консультаций» не является системным счётчиком completed sessions;
  • searchable, sort order, порядок отображения или иное текущее служебное свойство не считается автоматически весом G3.6;
  • существующее значение не получает product weight без явного опубликованного field rule.

Новые поля создаются только когда требуемого продуктового значения действительно нет. Дублировать опыт, специализации или языки нельзя.

14. Админ-панель

Управление разделяется без дублирования:

  • существующий /ru/admin/profile-field/index владеет исходными значениями profile fields, а новая страница /ru/admin/profile-field/expert-taxonomy (Поля профиля → Таксономия Экспертов) является единственным редактором category→specialization→method mapping;
  • /ru/admin/profile-field/completeness — единственный редактор «Поля анкеты → Полнота анкеты»: field rules, evaluation, preview и input override;
  • G3.7 отдельно владеет итоговым display/action eligibility и ranking.

Super-admin должен иметь:

  • редактор taxonomy draft, mapping, preview, publish, audit и rollback;
  • список правил;
  • field и class;
  • surface scope;
  • required/optional/not applicable;
  • weight для weighted rule;
  • validation/moderation requirement;
  • no-data behavior;
  • allowed range;
  • draft/current version;
  • effective time;
  • preview;
  • список затронутых анкет;
  • audit/history;
  • rollback;
  • карточку объяснения каждой анкеты;
  • manual override с reason/scope/expiry.

Различия значений:

  • unset — обязательная настройка не задана; draft нельзя опубликовать;
  • 0 — нулевой вклад weighted rule, если это допустимо;
  • disabled — правило исключено из новой версии;
  • no_data — у анкеты нет достаточных данных;
  • not_applicable — поле не требуется для этого scope.

15. Ошибки и особые случаи

  • Неизвестное поле удалено/архивировано: активная версия не должна молча изменить смысл; требуется configuration incident.
  • Значение изменилось во время оценки: сохраняется один согласованный snapshot либо выполняется повторная оценка.
  • Две публикации одновременно: активируется одна последовательная версия, без смешения.
  • Массовая переоценка прервана: уже завершённые результаты помечены версией, остальные остаются на предыдущем результате до retry.
  • Translation отсутствует: клиентская поверхность не показывает технический ключ.
  • Рисковый текст появился после допуска: анкета получает безопасное ограничение до moderation result.
  • Optional field отсутствует: не блокирует и не получает скрытый штраф.
  • Manual override истёк: состояние пересчитывается без удаления audit.
  • Текущий code-field имеет «weight»: это не доказательство, что он реализует правила G3.6.
  • Неизвестная или неопубликованная taxonomy version: consumer не угадывает mapping и получает configuration result.

16. Обязательные invariants

  1. Непустое не означает валидное.
  2. Optional missing не является quality fail.
  3. Completeness не равна rating, KPI, admission или гарантии качества.
  4. Блокирующее правило применяется до ranking.
  5. Исторический evaluation snapshot неизменяем.
  6. Одновременно действует одна опубликованная версия правил для scope.
  7. Manual override всегда объясним и не обходит safety/access/money invariants.
  8. Невалидная версия не активируется.
  9. Existing sort/search/display properties не считаются весами без явного правила.
  10. Клиент не видит внутренний score и staff-причины.
  11. G3.6 не устанавливает финальные display_eligible, capabilities[], ranking или paid start.
  12. Все потребители используют одну опубликованную taxonomy version без локального hardcode.
  13. Legacy specialization value IDs 1–20 не переиндексируются.

17. Связанные задачи

  • G3.2/G3.3 — поля каталога и профиля.
  • G3.7 — eligibility и ranking.
  • G6.3 — quality actions, но не profile completeness.
  • G6.4 — admission, но не заполненность профиля.
  • G4.3 — claims/safety rules.
  • G5.3 — KPI, который не смешивается с score анкеты.

18. Что не входит

  • ранжирование и ротация;
  • финальное display/action eligibility;
  • проверка paid_start_eligible;
  • KPI Агента;
  • public rating;
  • admission/exam;
  • full-text content moderation engine;
  • автоматические санкции;
  • гарантии качества консультации;
  • скрытая замена существующей семантики profile fields;
  • определение структуры хранения и способа расчёта.

19. Критерии готового результата

  1. Полная анкета получает воспроизводимый результат.
  2. Неполная анкета показывает точные blockers.
  3. Optional missing не блокирует.
  4. Мусорное значение не засчитывается.
  5. Рисковое значение создаёт moderation/blocking result.
  6. Разные surface scopes дают объяснимые различия.
  7. Draft не влияет на public result.
  8. Published version применяется с effective time.
  9. Historical snapshot остаётся прежним после изменения правил.
  10. Manual override имеет reason/scope/expiry и не обходит protected blockers.
  11. Preview и фактический readback совпадают для одинаковых входных данных.
  12. 3–5 pilot-анкет демонстрируют весь набор случаев.
  13. expert_specialization_taxonomy_v1_legacy сохранена как baseline, а expert_specialization_taxonomy_v2 опубликована с пятью категориями.
  14. Legacy IDs не переиндексированы; id=18:value=13 deprecated/excluded, id=17:value=16 и id=18:value=21 добавлены append-only с migration readback.
  15. Все восемь surface IDs (home, dashboard_catalog, country, city, category, matching_result, thematic_block, expert_profile) читают одну taxonomy version.
  16. Override G3.6 меняет только входной результат; итоговое решение G3.7 остаётся отдельным и проверяемым.

20. Операционный preflight и development handoff

До реализации

Super-admin/moderator подготавливает:

  • инвентаризацию существующих profile fields и их фактического смысла;
  • список переиспользуемых и действительно недостающих полей;
  • карту поверхностей;
  • карту существующих specialization value IDs, translations и taxonomy mapping;
  • baseline save/readback, applied version и список конфликтов.

Материалы до реализации должны однозначно показывать, какие текущие поля остаются источниками данных, какие правила добавляются G3.6 и где проходит граница с admission, eligibility, rating и KPI. Неописанное изменение смысла существующего поля запрещено.

Игорь получает только строки missing_capability, broken_binding или runtime_gap, предлагает способ version/readback без изменения продуктовых правил и возвращает build/fixture plan.

На QA

  • build marker;
  • 3–5 контролируемых анкет;
  • positive/negative evaluation results;
  • preview/readback каждой версии;
  • publish/rollback taxonomy version и доказательство сохранения legacy IDs;
  • доказательство draft/publish/rollback;
  • manual override/expiry;
  • concurrent/partial-failure cases;
  • audit и cleanup.

QA-handoff собирает QA/super-admin. Он включает воспроизводимые входные данные каждой анкеты, версию правил, рассчитанный snapshot, причины blocking/warning, admin preview и публичный readback. Итоговый процент без расшифровки применённых правил и без negative cases не принимается.
