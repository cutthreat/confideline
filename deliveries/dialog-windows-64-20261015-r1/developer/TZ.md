# #64: диалоговые окна MakTaro — инвентарь, единый контракт и ТЗ

**Передача 15.10.2026:** документ сохранён как исходный контракт с переносимыми ссылками. Адресный объём работ и формат результата — в [задании Игорю](../TASK-FOR-IGOR.md). Исторические статусы и ограничения не являются новым аудитом.

**Статус:** `WORKING_SOURCE_INVENTORY_WITH_LIMITS`, уточнение 05.10.2026. Клиентский контракт сохранён; добавлены известные админские исходники и настоящие локальные HTML-примеры. Полнота всех окон, согласованный стиль и подключение к backend не подтверждены.

**Граница задачи.** Актуальный сценарий карточки `EFQ9AXJM` требует перечень всех диалоговых окон: клиентские и админские области входят в объём. Прежнее исключение админки ошибочно сужало задачу. Немодальные боковые панели, меню и браузерные подтверждения нужно учитывать отдельно по типу, не выдавать их за HTML-модальные окна. Вёрстка не переделывается: сохраняются существующие стили каждой поверхности.

**Исходники.** Прежняя визуальная карта (историческое основание, не входит в эту выдачу) содержит клиентские паспорта со снимками и остаётся историческим основанием, не интерактивным примером. Новая [рабочая редакция #64](../index.html) связывает [реестр исходных экземпляров](inventory.json) и [HTML-примеры](index.html). Прочитаны 78 клиентских HTML final-r2 с проверкой capture-хэшей, девять текущих локальных страниц баланса #23 и отдельная админка отзывов #62. Это известный статический объём, не полный перечень live-окон и серверных AJAX-шаблонов.

## 1. Единый контракт окна

| Элемент | Обязательное правило |
| --- | --- |
| Открытие | Только от конкретного пользовательского действия либо подтверждённого серверного события. Одно событие не должно открыть два одинаковых окна. |
| Контекст | Передавать идентификаторы исходного объекта: `expertId`, `conversationId`, `consultationId`, `orderId` или `reviewId`, если они есть. Не строить действие на отображаемом имени, цене или тексте. |
| Фокус и доступность | При открытии фокус получает заголовок либо первое поле; `Escape`, крестик и Back возвращают фокус инициатору, если окно не относится к незавершённому необратимому действию. Фон недоступен клавиатуре, пока окно активно. |
| Закрытие | Закрытие скрывает интерфейс, но не отменяет уже отправленный платёж, `Start`, `Complete` или запрос в поддержку. После обновления страницы показывать только подтверждённое сервером состояние. |
| Основная кнопка | До ответа сервера блокируется повторное нажатие. У каждого запроса есть idempotency key/nonce; ошибка или timeout сначала сверяются с исходной операцией, затем разрешается повтор. |
| Ошибка | Понятное нейтральное сообщение рядом с действием; не раскрывать платёжные реквизиты, внутренние причины, чужие данные и текст консультации. Для платёжной ошибки — безопасный переход к другому способу или Support. |
| Мобильный вид | Ширина не превышает viewport; длинное содержимое прокручивается внутри окна; фиксированный footer не перекрывает обязательную кнопку. Проверить 360, 480, 768, 992 и 1280 px. |
| Аналитика | Писать только тип окна, инициировавшее событие, результат и технический идентификатор объекта. Текст чата, карта, e-mail, номер телефона и реквизиты платежа в событие не включать. |

## 2. Классы риска

| Класс | Окна | Правило |
| --- | --- | --- |
| `informational` | offline, no matching, notification destination, picker details | Закрытие безопасно; не меняет состояние. |
| `form` | astrological details, question before start, notify email/telegram, review, support | Проверить обязательные поля и серверную валидацию; черновик не равен отправке. |
| `paid_or_consent` | top-up/start/continue, checkout, card details, discounted offer, auto-refill, one-click top-up | Перед запросом видны цена/credits/условия; нужна явная команда пользователя. Close/Back не покупает и не запускает счёт. |
| `session_state` | connecting, end or stay, completed, reconnect grace, expert wants to continue | Источник состояния — сервер. Интерфейс не считает таймер или списание локально как окончательный факт. |
| `error_recovery` | payment/order/card error, consultation support | Сначала readback исходной операции, затем один допустимый путь восстановления. |

## 4. Что Игорь должен подтвердить до подключения

1. Реестр `window ID -> route -> trigger -> backend event -> state source -> API -> permission`. Если окна нет в текущей реализации, явно указать `new`.
2. Кто вправе вызывать `Start`, `pause`, `resume`, `Complete`, auto-refill и возврат к активной сессии. Покупка credits, согласие и вход в чат не являются ими автоматически.
3. Источник прав на trial, скидку, saved payment method, статус эксперта, баланс и право на отзыв.
4. Идемпотентность `Buy`, one-click top-up, Start, End и Send Support; поведение timeout/повторного открытия.
5. Какие окна сохраняют серверный черновик, а какие не должны сохранять никаких введённых данных.

## 5. Минимальная приёмка

| Проверка | Ожидаемый результат |
| --- | --- |
| Обычное окно | открытие, Escape/Close/Back и возврат фокуса работают; фоновая страница не активна клавиатурой. |
| Формы | пустые/невалидные данные не отправляются; успешный результат прочитан с сервера. |
| Платёж | двойной клик, refresh и timeout не дают двойного заказа/списания; неизвестный результат не ретраится автоматически. |
| Start и End | баланс/покупка/согласие не запускают платное время сами; один Start/End даёт одно подтверждённое серверное изменение. |
| Сессия | reconnect не теряет контекст и не удваивает списание; Complete не возобновляется через UI. |
| Безопасность | сторонний пользователь не открывает чужой review/order/consultation/support context подменой ID. |
| Адаптивность | все классы проверены на 360, 480, 768, 992 и 1280 px; обязательные кнопки и ошибки доступны. |

## 6. Решения и границы

- **Принято:** сохраняем утверждённую вёрстку и не делаем общий редизайн окон.
- **Принято Заказчиком 05.10:** агент и эксперт — один человек; агент является внутренней ролью этого же человека при работе с несколькими экспертными профилями, не отдельным переписчиком.
- **Нужна сверка Игоря:** фактическое наличие каждого триггера, API и серверной модели состояния. Это не вопрос к Заказчику до технической проверки.
- **Отдельные карточки:** отзывы/рейтинг — `#62`; Support V2 — `#25`; credits/баланс — `#23`; права — `#49`; чат и денежные расчёты принимаются пакетно в `#67`. Настоящий документ не заменяет их QA.

## 7. Готовность результата #64

Полный результат карточки **ещё не установлен**. Есть клиентский контракт, расширенный инвентарь известных исходников и настоящие локальные HTML-примеры. Открыты полнота live/dynamic-областей, подтверждение Игорем триггеров/API/прав, согласование правил внутри клиентского и админского стиля и нативная проверка поведения/ширин. После технической сверки Игорь отмечает существующие и новые окна в реестре из раздела 4; затем QA выполняет раздел 5 на известной сборке. Исходный DOM, fixture-намерение и локальный файл не доказывают серверный переход или приёмку платежей/сессий.
