## Размещение

Рекомендация: **Диалоги → Контакты в сообщениях**. Объект разбора — сообщение разговора клиента и эксперта. В экспертном чате есть переход к журналу конкретного conversationId. Это даёт сотруднику контекст без поиска в отдельной очереди.

Раздел «Поддержка» предназначен для Support-переписки, которая исключена из этой проверки. Верхний самостоятельный пункт сейчас не нужен: первый этап не создаёт отдельный процесс санкций или аккаунтной модерации. Если позднее появится общая модерация нескольких объектов, журнал можно перенести в её раздел, сохранив адрес и ссылки из диалогов. Это предложение по навигации, ещё не изменение меню сайта.

Блок **«Цензура» в Настройках → Настройки чата** после правки пользователя сгруппирован компактно: «Проверка сообщений», «Правила», раскрываемые «Хранение и история изменений». Проверка правил раскрывается внутри списка правил. Повторные заголовки, вкладки и служебные тексты удалены. Прежние поля lifecycle/лимитов остаются у существующего обработчика; этот HTML показывает только цензуру.

## Интеграция и расширение

1. Подключить новый CSS и JS через отдельный Yii2 AssetBundle. `contact.css` ограничен `.cr-page`; для интеграции использовать этот namespace вокруг компонента. Donor CSS не менять и не подключать повторно, если они уже в layout. Служебные панели уже удалены. Fixture-скрипты заменить серверными данными; новых frontend-библиотек нет.
2. Общая серверная политика должна стоять до записи доставленного текста и до fan-out. Проверить send/edit, ChatManager/MessageManager и существующий путь оператора. Sender/channel берутся из авторизованного server context, не из произвольных полей клиента. Support исключается по каналу.
3. Сохранять безопасный MessageDTO для чата, истории, preview, WebSocket, поисковых индексов и уведомлений. Не передавать raw original, matched_ranges или категорию обычным участникам. Удалить оптимистический сырой bubble после server ack, при ошибке сохранить только черновик отправителя. Редактирование проверяется повторно.
4. Запись сообщения, события и защищённого оригинала — согласованная транзакция с идемпотентностью отправки. При ошибке проверки/хранилища не доставлять сырой текст. Retry не должен дублировать message/event. Уведомление отправителя — без совпадения.
5. Коллекция правил: стабильный id, category, тип обработчика (сначала regex), pattern/flags, enabled, version, author/timestamps. Не связывать UI с одним выражением на категорию: в макете можно добавить несколько. Версия конфигурации — неизменяемый snapshot параметров и всех правил; аудит изменения, проверка optimistic concurrency и серверная валидация обязательны. Лимит regex CPU/длины сообщения должен быть серверным. Web Worker здесь защищает только тестовую вкладку.
6. В backend хранить отдельно `censorship_event`, `censorship_original`, `censorship_access_log` и результат разбора (названия таблиц — предложение из PM). В событии нужны sender/recipient/conversation/message, фактический actor оператора, категория/категории, rule id/version, время и status. В permission endpoint просмотра оригинала сначала проверить право и записать аудит; при сбое аудита не выдавать оригинал. Прямые URL, API, cache и экспорты не обходят право.
7. Коды PM: `chat_censorship.view_log`, `.view_original`, `.manage_rules`, `.mark_false_positive`. Последний используется и для подтверждения, если это соответствует текущей RBAC; точные grants согласовать с текущим backend. Получение права нельзя привязывать исключительно к super admin. Не создавать новую роль.
8. В интерфейсе ключи `phone/email/link/messenger` соответствуют PM `phone/email/url/messenger_contact`. Нужна явная mapper-функция, а не две несовместимые категории в БД. Порядок перекрытий: email, messenger, URL, phone; каждый физический фрагмент скрывается один раз, все независимые категории сохраняются в событии.

## Ограничения и решения перед эксплуатацией

- Журнал трактуется как архив **всех сработавших сообщений** с защищёнными полными оригиналами. Обычная история всех сообщений остаётся на существующем /admin/message/index. Массовое копирование всей переписки не реализовано. Это принятая для макета трактовка неоднозначного слова «все»; отдельный общий архив потребует уточнения.
- Детектор правил — baseline, не универсальное распознавание: номера заказов из 10 цифр могут дать false positive; телефон словами не распознаётся; bare domain с неизвестным TLD может пропускаться. Нулевой false-positive rate не заявляется.
- Allowlist собственных ссылок пока отсутствует. До её включения нужны точные домены, контекст и test corpus. Не добавлять широкое исключение для всей категории URL.
- Срок хранения оригиналов ещё не согласован. В UI по умолчанию «Не задан», доступны варианты 30/90/180/365 дней. Очистка и retention job здесь отсутствуют.
- Голосовые записи, QR, OCR и изображения данным текстовым baseline не проверяются. Отдельные категории и обработчики можно расширять в схеме, но их нельзя объявлять включёнными только потому, что UI уже готов к коллекции правил.
- Первый этап: частичное скрытие, Support исключён, аудит просмотров обязателен, **нет автоматических санкций и блокировки аккаунтов**. Изменение версии не раскрывает старые сообщения и не отменяет маску при false positive.

Backend-приёмка: назвать commit/сборку, реальные маршруты, grants, миграции и storage/retention; выполнить матрицу из knowledge с прямым доступом без permission, audit failure, send/edit/retry и отсутствием утечки во всех DTO/уведомлениях. HTML и отключённая кнопка этого не доказывают.
