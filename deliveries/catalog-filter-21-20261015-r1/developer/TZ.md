# #21. Новый фильтр каталога экспертов

Актуальная редакция для передачи Игорю: 15.10.2026. Статус: техническое ТЗ; реализация и полная приёмка не подтверждены. Основа: существующий контракт 30.09 с уточнениями 05–09.10 и согласованный следующий шаг Codex + Dots от 15.10. Нового аудита и перерисовки нет.

## 1. Цель И Объём

Подключить второй вариант фильтра к существующему каталогу, не удаляя старый поиск и не меняя его параметры/ссылки молча. Состав нового фильтра — ровно 11 опций исходного публичного макета. Существующие макеты публичного каталога и каталога в кабинете поставлены вместе с зависимостями.

Применение нового server-side query к каталогу в кабинете Игорь подтверждает по реальному месту подключения. Фильтр не распространяется автоматически на chat picker, избранное, назначения, SEO или другие списки экспертов. В кабинете имеющаяся кнопка Filter psychics сама по себе не доказывает наличие фильтрующей формы или API; недостающий контракт подключения следует явно описать, не выдавать за существующий.

## 4. Семантика И Допуск

```text
published AND allowed_for_catalog
AND (areas empty OR profile has any selected area)
AND (topics empty OR profile has any selected topic)
```

- Внутри одной группы — OR: подходит хотя бы одно выбранное значение.
- Между непустыми группами — AND: эксперт соответствует обеим группам.
- Пустая группа не ограничивает выдачу.
- Отсутствующее необязательное поле не исключает допущенный профиль из общего каталога, но не совпадает с выбранным значением этого поля.
- Непрошедший модерацию, заблокированный или иначе не допущенный профиль не входит ни в items, ни в total; действующее правило допуска сверить по коду, не изобретать по Required.
- Busy/offline не исключаются только из-за занятости: отображается правдивый статус без обещания мгновенной консультации. Выбранный эксперт не подменяется другим.
- Допуск и выбранные параметры применяются до total, сортировки и LIMIT/пагинации. У одного экспертного профиля один результат даже при нескольких совпадающих значениях. Не смешивать дедупликацию одного профиля с объединением разных анкет одного человека.
- Детерминированную сортировку взять из действующего каталога. Язык, GEO, цена, рейтинг и стаж не добавляются в новый фильтр только из-за наличия в карточке.

## 5. API, URL И Пагинация

`areas[]`, `topics[]`, `catalog_filter_variant`, `legacy` и `maktaro_v1` — предлагаемые имена контракта, не подтверждённые текущие endpoint/config. Игорь показывает фактическое место запроса и схему данных, затем закрепляет интерфейс реализации.

Нужны items, total, page/cursor, hasMore и применённые стабильные ID с локализованными подписями; точный формат согласовать с существующим API. Не фильтровать уже полученную страницу в браузере вместо серверной выдачи.

Смена набора фильтров и Reset должны давать согласованное состояние выбранных значений, запроса, URL, страницы и результатов; при изменении параметров сбрасывать или нормализовать страницу по закреплённому правилу. Полный GET/reload и штатный динамический переход должны возвращать тот же набор при одинаковых входах. Сохранить прежний смысл legacy URL и предпочтений; прежние параметры не интерпретировать как новые без явного совместимого правила.

Некорректные/недоступные ID не раскрывают закрытый справочник или приватные профили. Зафиксировать поведение в фактическом API: рекомендуется нейтральный отказ 400; иной существующий контракт должен быть явно описан. Не маскировать ошибку случайной выдачей.

## 6. Варианты, Полномочия И Откат

Новый вариант вводится отдельной стратегией на существующих моделях. Старый остаётся активным до разрешённого включения. Настройка должна иметь один подтверждённый источник, валидацию и fail-safe на прежний поиск при неизвестном значении с серверным журналом ошибки.

Управлять вариантом может только фактически уполномоченный пользователь с серверной проверкой конфигурационного permission. Название роли и скрытая кнопка не заменяют проверку. Следовать принятой модели #49, не вводить новый RBAC этим ТЗ. Изменение записывается в аудит: актёр, старое/новое значение, время, причина.

Показать, какой вариант действует, кто/когда его изменил и как вернуться к старому. Откат переключателя отдельно от обратимости изменений данных: новые связи не должны теряться, опубликованные профили и зависимые фильтры не должны ломаться при возврате legacy. План миграций и отката описать до изменений; эта передача не разрешает запуск миграций или production-переключение.

## 7. Экранные Состояния

| Ситуация | Ожидаемый результат |
|---|---|
| Опубликован и допущен, доступен | Карточка и разрешённое действие перехода |
| Допущен, busy/offline | Карточка с честным статусом, без автоматической замены эксперта |
| Пустое необязательное поле | Есть без ограничения по нему; нет при выборе отсутствующего значения; выдуманной подписи нет |
| Не допущен | Нет в API, total и карточках; внутренние причины и приватные поля не раскрываются |
| Нет совпадений | items=[], total=0; понятный сброс/корректировка, без случайных экспертов |
| Некорректный ID или ошибка запроса | Нейтральное согласованное состояние, не ложная пустота или успешная выдача |

Исходные chips публичного макета статические; выбранность, клавиатурная работа, Reset, empty/error и загрузка при интеграции должны быть настоящими состояниями, а не обещанием статической картинки. Макеты в этой поставке не меняются. В приёмке сохранить размеры 360, 480, 768, 992 и1280 px из существующего контракта.
