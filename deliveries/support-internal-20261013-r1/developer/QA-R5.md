# Проверка R5: что подтверждено

Редакция 15.10.2026. Это приемка интерактивных макетов, не backend.

## Пройденные сценарии

| Сценарий | Результат в макете |
| --- | --- |
| Клиентский тикет → подключение агента → вопрос → связанный ответ → работа Support с клиентом | Один ID, пустой новый participant-канал, отдельный клиентский поток, ход возвращен Support |
| Агент создает обращение по чату, Support подключает эксперта | Необязательный разрешенный context, участник добавляется независимо от автора |
| Общий вопрос агента без клиента/консультации | Создан без фиктивного клиента и обязательного conversation |
| Несколько вопросов → один ответ → продолжить ожидание другого | Ответ завершает только свой вопрос; ход Support; resume использует тот же вопрос |
| Отмена и переназначение | Приватная причина, нейтральное уведомление адресату, исходные ID/отправка/deadline сохраняются; старый адресат не может ответить формально |
| Напоминание / просрочка / поздний ответ | Сдвиг demo-clock 13/25 ч.; просрочка видна при paused SLA, ничего автоматически не закрывается; поздний ответ принят |
| Чтение и обычная реплика | Не отвечают на вопрос и не продлевают срок |
| Настройка срока | Невалидные значения отклонены, 6/48 применены новому вопросу; возврат к 12/24 не изменил его snapshot |
| Срочная текущая консультация | Отдельный сигнал немедленного ручного разбора, не разрешение ждать сутки |
| Агент-автор → решение → возврат → повторное решение → подтверждение | Тот же ID; отдельная demo capability, не role=client; закрытая история без неработающего «Ответить» |
| Приватность | Агент не получает client/staff/чужой participant текст или служебную причину отмены; рабочие личные чаты отдельно |
| Ошибка сохранения | Многострочный composer переживает переключения; форма повторно открывается с текстом; повторная отправка после снятия demo-сбоя очищает текст только при успехе |
| Доступность и mobile | Доступное имя/focus диалога, клавиатурные вкладки/ESC; 320×568 оставляет место ленте и прямой ответ, без расширения страницы |

Чистая модель ticket-policy проверена 23 автоматическими проверками: snapshots, переходы, независимые вопросы, поздние ответы, отмена, перенос, сохранение сроков, author capability, closed/read-only разделение. Скрипт включен в developer/tests/policy.test.cjs. Браузерные наблюдения и снимки текущей редакции хранятся локально отдельно от публичного комплекта; чужие live-переписки не публикуются.

## Что изучено на действующем сайте

Read-only просмотр авторизованной админки Support V2 и настроек Support, внутренней формы вопросов и «Проблема» Chat V2. Никаких реальных тикетов, вопросов, участников, статусов и настроек не изменяли.

Подтверждены видимые lifecycle enum и приоритеты Support low/normal/high/urgent; поля адресного вопроса; текущее Settings[resolvedReplyHours] = 24. Обнаружено несовпадение приоритетов: Chat V2 показывает low/medium/high/critical. В макете общий intake использует Support enum; реальное соответствие и обработку payload разработчику еще нужно проверить.

## Не подтверждено и требуется серверу

- Нет актуального исполняемого PHP checkout для полного аудита; wiki + read-only UI не доказывают поведение реальных POST.
- Подтвердить существующие reply/accept/rework права агента/эксперта-автора. Не переносить demo authorCapabilities как доверенный input и не вводить искусственного клиента.
- Проверить/добавить server-authorized подключение нужного участника независимо от reporter, приватные projections и права контекста, без выдачи Chat V2 transcript.
- Реализовать question revision/idempotency, формальный answer, resume/reassign с неизменным deadline, аудит и обработку гонки answer/cancel/reassign.
- Подключить серверное UTC-время, настройки, once-only reminder/overdue worker и адресные уведомления. 12/24 — гипотеза; worker, push/email и доставка этим макетом не реализованы.
- Сохранить текущий SLA и отдельное окно решения; разрешить собственный read cursor в closed, запретив остальные business writes.
- Согласовать оба intake по priority enum; использовать существующие source/permission checks для chat context и независимого общего обращения.
- Реальные HTTP retries/таймауты, транзакции, revoke membership, CSRF/RBAC, upload/scan и клиентский frontend требуют отдельной приемки. Клиента в админке нет; полный трехсторонний production E2E не выполнялся.

Изменена только общая реализация виджета и подключение его policy-скрипта в тех же пяти страницах. Исходные фоновые CSS/JS контроллеры Support/Chat V2 не дорабатывались. Полный комплект и ZIP имеют общий manifest; опубликованные bytes/ZIP сверяются отдельно при выпуске.
