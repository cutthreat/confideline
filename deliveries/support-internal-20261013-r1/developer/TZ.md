# Сообщения: тикеты и внутренний чат

Редакция для передачи: support-internal-20261013-r1, обновление communications-v2 от 13.10.2026. Это ТЗ и интерактивная верстка, не внедрение в Yii2. Позднее решение Алексея заменяет прежнюю гипотезу общего рабочего диалога с очередью Support на личные диалоги с выбранным сотрудником.

## 1. Результат

Убрать вкладку `Internal` из правой панели карточки Support. Ее функции сохранить в сквозном виджете общего layout админки. Не создавать второй Support и не менять каноническую историю обращений.

Виджет доступен на любой разрешенной пользователю странице админки. Наличие доступа в админку не дает доступ ко всем обращениям. Общая кнопка и заголовок для агента/эксперта и сотрудников — `Сообщения`: это контейнер двух способов коммуникации, не только служба поддержки.

Два раздела на одном уровне:

- `Тикеты`: адресные каналы существующих обращений.
- `Внутренний чат`: личные рабочие диалоги агента и выбранного сотрудника сайта без обязательного тикета. Название одинаково для обеих сторон.

В карточке остаются `Properties`, `Client`, `History`. Основная клиентская переписка не переносится целиком в общий рабочий чат. Кнопка в хедере открывает тот же кейс/канал с любой страницы без потери рабочего контекста.

## 3. Размещение и внешний вид

Использовать текущий YouDate/AdminLTE layout, Bootstrap 3 и Font Awesome проекта. Сохранить хедер, левое меню, футер, плотность, цвета, таблицу и исходный `custom.css`. В HTML меню показано полностью, но ссылки на другие разделы намеренно не действуют.

Кнопка виджета находится в общем хедере рядом с пользователем. Счетчик показывает число доступных обсуждений, требующих внимания, а не количество всех сообщений. Один кейс в своем разделе считается один раз, даже при нескольких событиях. `Непрочитанные` и `Нужен ответ` — разные признаки: прочтение не закрывает вопрос.

На desktop правая панель сохраняет основную страницу видимой. Компактная ширина около 28% viewport, с ограничением 360–440 px. Кнопка expand/compress переключает компактный вид и половину экрана. Левый край имеет hover-индикатор и col-resize cursor; перетаскивание задает произвольную ширину в пределах 360 px — 75% viewport. Двойной клик возвращает компактный вид; separator доступен с клавиатуры: стрелки, Home/End, видимый focus и ARIA min/max/value. При изменении размера не теряются канал, текст, выделение и позиция чтения. Предпочтение сохраняется для actor на этом устройстве; чужая роль не получает эту настройку. На mobile панель полноэкранная, resize/expand скрыты, сохраненная desktop-ширина не переписывается; закрытие, вкладки, вопрос и поле ответа доступны без расширения страницы. Смена роли производится только через ссылки демонстрации, не элементами продуктового интерфейса.

`Support info` — компактная сводка рядом с конкретной консультацией, не дополнительное модальное окно. Два примера (`CT-1043` и `CT-1045`) имеют разные ID обращения, статусы и черновики; второй содержит адресный вопрос. `Открыть` сразу выбирает соответствующий тикет и private participant-канал в виджете. Внутри уже открытой переписки повторной ссылки `Support info` нет. Это вход из Chat V2 в существующий кейс, не копия истории и не новый клиентский кабинет.

Инициализация один раз вне PJAX-контейнера через AssetBundle. PJAX-переход не создает второй виджет, таймер или обработчик. Открытый канал, черновик и позиция чтения сохраняются при смене страницы; при logout/смене актера состояние очищается в рамках безопасного пользовательского lifecycle приложения.

## 4. Аудитории и права

| Пользователь | Разрешено | Не разрешено |
| --- | --- | --- |
| Support с `support-update` | Разрешенные кейсы, вопросы проверенным адресатам, reporter update, заметки, открытие проверенного client-канала, регистрация action request | Исполнение возврата, изменение доступа или платной сессии |
| Support с правом только чтения | Просмотр разрешенного контекста/истории | Любая мутация; кнопки скрыты, прямой POST отклоняется |
| `support-super-moder` | Действия старшей поддержки по действующим правам; закрытие `senior_decision` | Автоматическое получение финансовых/сессионных полномочий |
| Super Admin / уполномоченный исполнитель | Подтвержденные результаты через авторитетную систему и разрешенный контракт | Признание операции выполненной только потому, что в UI выбран `Completed` |
| Агент/эксперт | Только собственные активные participant-memberships, адресованные ему вопросы/сообщения, статус собственного репорта и личные диалоги с разрешенными сотрудниками | Client-лента, staff-заметки, чужой participant, запросы действий, полный History и чужие личные диалоги |
| Клиент | Только открытый client-канал в существующем клиентском Support | Internal/рабочие чаты админки и participant-ленты |

Названия выше соответствуют описанным в памяти ролям; точные action-grants проверить по текущему `Permission`/`canAdminPermission`. Новые granular permission names не считаются уже существующими. Общий layout должен проверять capability, а не только `isModerator` или наличие меню. Право личной переписки не дает права читать/изменять Support-тикеты. Роль в адресной книге — подпись для человека, а не grant; Moderator без Support-update не получает служебные действия по одному лишь названию.

Личные диалоги видны только двум участникам. Даже Super Admin в обычном списке чатов видит собственные диалоги, а не переписку всех сотрудников. Если нужен привилегированный служебный аудит, это отдельный явно авторизованный процесс с аудитом доступа, не неявное раскрытие в виджете.

Сервер получает actor из сессии, сам выбирает разрешенные membership и audience. ID пользователя, роль, verified-флаги, source-связи, сумма и статус из браузера не являются полномочиями. Ответ API агента вообще не содержит закрытых полей; скрытие DOM или фильтр массива на клиенте не являются защитой. Reply-to, поиск, файлы, счетчики, deep links и ошибки подчиняются тем же границам.

## 5. Раздел «Тикеты»

Список строится по разрешенным обращениям/участию, а не по происхождению из рабочего чата. Агент видит свой репорт из Chat V2, клиентский кейс, куда его явно добавили как проверенного участника, и кейс из рабочего чата. Другие агенты не появляются автоматически из совпадения имени, профиля или текста сообщения.

Support выбирает локальную аудиторию внутри кейса: команда Support (`internal`), конкретный участник (`participant` + membership ID), клиент (`client`, только после открытия). Явная подпись аудитории находится над лентой и полем. В local demo `staff` — технический alias, не новый серверный audience.

Агент видит один свой канал; полная служебная панель ему не выдается. `Support info` напрямую открывает тот же канал и тот же вопрос, без промежуточного dialog. В макете две сводки показаны компонентами в сохраненной админской оболочке, а не новой версткой всего Chat V2. Выбор собеседника во внутреннем чате не создает participant-membership в тикете и не раскрывает его историю.

### Вопрос и следующий ход

Вопрос имеет ID, адресата, audience/membership, статус `open|answered|cancelled`, автора и время; source message необязателен. В макете разрешен один открытый вопрос на адресный канал, параллельные вопросы разным адресатам независимы.

1. Явный вопрос переводит кейс в `waiting_participant` и приостанавливает SLA Support.
2. Обычное сообщение не подменяет ответ на вопрос и не закрывает его. В UI ответ привязывается через `Ответить на вопрос`.
3. Ответ закрывает только выбранный вопрос. По описанному серверному контракту ход возвращается Support (`waiting_support`), даже если другой вопрос еще открыт. Остальные вопросы сохраняются; Support оценивает ответ и может снова явно ожидать оставшегося участника. Не вычислять workflow как «есть хотя бы один вопрос → всегда waiting_participant».
4. Отмена сохраняет исходный текст, автора и причину в History. Адресату показывается факт отмены, но не внутренняя причина. Последняя отмена возвращает `waiting_support`; при других открытых вопросах текущий следующий ход самопроизвольно не меняется.
5. Ошибка или уже закрытый вопрос не стирают текст ответа. Повторная отправка с тем же ключом не создает сообщения/события повторно.

Существующий callback Chat V2 описан для ответа на формальный вопрос. Свободное participant-сообщение вне вопроса в макете — целевое расширение: использовать разрешенный сервисный метод/отдельную команду, а не обходить проверки question ID текущего callback. Общий рабочий чат не зависит от этого расширения.

### Reporter update

Статусы: принято, в работе, нужна информация, консультация приостановлена, эскалировано, решено; пояснение необязательно. Видит только автор репорта. Это короткий рабочий итог, не lifecycle тикета, не публичный ответ и не доказательство изменения `service_session`. Для настоящего ожидания ответа создается вопрос. Сохраняется событие аудита.

### Client channel

Открывается осознанно, только по проверенной серверной связи исходного чата/сессии/платежа/аккаунта. Произвольного поиска клиента по имени/e-mail нет. Подтверждение показывает клиента, источник, ID кейса, ответственного и SLA. В production дополнительно используется безопасная клиентская тема; внутренний заголовок/репорт автоматически клиенту не публикуется.

Тот же ID, один ответственный, одна история и SLA. Новая client-лента начинается пустой: репорт, staff/participant-текст и файлы не копируются. Клиентский статус зависит только от вопросов клиенту: вопрос агенту означает для клиента дополнительную проверку, а не «нужен ваш ответ».

### Заметки, History и запросы действий

Заметки/закрепления только для Support. Быстрые заготовки вставляют редактируемый текст, не выполняют действие. Свободная staff-переписка использует существующую модель private notes/internal messages, без второго клиентского потока.

Запросы возврата/доступа требуют проверенного соответствующего source; пауза/возобновление/завершение — проверенной сессии. Упоминание CT в сообщении связи не создает. Для возврата production обязан проверять авторитетный платеж, валюту, доступную к возврату сумму и отсутствие повторного исполнения: фиксированный USD в demo не является платежным контрактом.

Support регистрирует `requested` с причиной, source reference, ключом идемпотентности. Только авторизованный source/executor подтверждает `completed|rejected|failed`, с evidence/result ID и аудитом. Повторный/устаревший callback не повторяет операцию. Результат не закрывает тикет автоматически. Форма `Результат исполнителя` доступна лишь в отдельной demo-персоне; это симуляция записи результата, не реализация платежного адаптера.

History сохраняет автора, стабильные ID объектов, время, тип и безопасные before/after-данные. Нет кнопок редактирования/удаления аудита. Реальная неизменяемость обеспечивается сервером; localStorage этого не доказывает.

## 6. Внутренний чат без обязательного тикета

Это личная рабочая переписка агент ↔ выбранный сотрудник, не общая комната всех пользователей и не Support queue. `Новый диалог` открывает адресную книгу внутри панели, не еще одно модальное окно поверх нее. Основной список показывает последние диалоги, никнейм/роль, последнее сообщение и признаки внимания; есть поиск и фильтры «Все / Непрочитанные / Нужен ответ».

Агент выбирает активного разрешенного сотрудника: `Support — Chapajev Wasil`, `Moderator — Alexey Saava`, `Super Admin — Admin Admin` (примерные demo-персоны). Есть поиск по никнейму без учета регистра и фильтр по роли. Клиенты, другие агенты, неподтвержденные и неактивные аккаунты не попадают в его адресную книгу. В production сервер возвращает разрешенный каталог с пагинацией/ограниченным поиском, не весь User table.

Support, Moderator и Super Admin могут первыми написать агенту: их адресная книга показывает разрешенных активных агентов и поиск по никнейму. Примеры: Alex Morgan, Sara Morgan, Nina North. Нельзя начинать диалог по произвольному user ID, выбирать клиента или обходить проверку текущих полномочий. Один эксперт с несколькими публичными профилями остается одним человеком/actor в адресной книге, а не несколькими собеседниками.

Никнейм и роль всегда видны в результатах выбора и заголовке переписки. Выбор определяется стабильным user ID, не строкой никнейма/роли. Для одной пары пользователей — один постоянный диалог независимо от того, кто его начал. Повторный выбор открывает прежнюю историю. Диалоги одного агента с Support, Moderator и Super Admin раздельны; другой сотрудник или агент не получает к ним доступ. Не создаются группы, рассылки и неявная общая аудитория модерации.

Выбор адресата и набор текста не создают пустой диалог. Первая отправка атомарно находит/создает пару и записывает первое сообщение; повтор с тем же operation key не дублирует эффект. Для пары нужен канонический ordered pair key и уникальный индекс. Черновик привязан к actor + паре, сохраняется при переходе между адресатами/тикетами, закрытии панели и reload; переключение не отправляет его. Счетчики и read cursor индивидуальны по user ID, не общие для всех пользователей с ролью Moderator. В открытой панели новое сообщение остается непрочитанным до явного открытия/подтверждения уже отрисованного cursor. Признак «Нужен ответ» рабочего диалога не меняет lifecycle/SLA тикета и не является формальным blocking question.

В личном диалоге нет `Принять диалог`, shared owner, claim/release или «вернуть в очередь»: адресат уже выбран. При потере права отправки/неактивности собеседника сервер запрещает новые сообщения, сохраняет доступную по действующей политике историю, UI показывает причину; не перенаправляет переписку другому сотруднику автоматически. Операционные вопросы без ответа можно оформить отдельным тикетом, но личный чат не обещает SLA Support и не заменяет формальные обращения.

Если нужен формальный процесс/SLA/платежная проверка, сотрудник с реальным правом создания Support выбирает конкретные сообщения и явно создает обращение. Непомеченные сообщения и дальнейшая переписка не копируются. Сохраняются source message IDs и ссылка; повторная конвертация выбранных сообщений исключена. При наличии существующего кейса не создавать дубликат. Выбор сотрудника во внутреннем чате сам по себе не дает ему права на платеж/консультацию или доступ к тикету.

Новая persistence-модель: conversation ID, ровно два participant user IDs, уникальный pair key, revision, сообщения, индивидуальные read cursors, аудит создания/отправки/конвертации. Имена таблиц/endpoints выбрать в текущем Yii2 namespace после сверки кода; их существование не заявлено. Предыдущая team-chat гипотеза существовала только в mockup, поэтому нельзя выдавать его demo backfill в localStorage за миграцию production-данных. Первый этап — текст, без загрузки новых файлов, AI, звонков, групп и фиктивных online/typing-индикаторов.

## 7. Непрочитанное и обновление

Использовать per-user/per-membership cursor, не общий `staff_read_at`. При открытии канала подтверждать только максимальный уже отрисованный доступный message ID. Сообщение, поступившее позже, остается непрочитанным, даже при открытой панели. Ответ/отмена вопроса и чтение — разные команды. В макете это показано безопасной моделью флагов; production должен использовать серверный cursor.

В Chat V2 переиспользовать действующий 15-секундный `v2-session-state` и private-feed revision, сохраняя draft/composer. Не добавлять второй heartbeat для той же страницы.

Для сквозного индикатора вне Chat V2 нужна новая компактная actor-scoped summary-проекция. Предлагаемый ограниченный transport: один foreground GET раз в 30 секунд, плюс открытие/возврат фокуса с дедупликацией; hidden/offline — пауза, ошибка — ограниченный backoff. Не опрашивать весь каталог тикетов и не добавлять Support WebSocket. Это новая часть сквозного виджета, а не ранее реализованный realtime Support V1. Серверная производительность/лимиты подлежат staging-проверке. Уведомления о просрочке SLA не входят в задачу.

Встроенный local demo синхронизирует изменения между вкладками через storage event только на одном origin. Отсутствие server transport намеренно; после распаковки browser file-origin policies могут ограничивать межвкладочную синхронизацию. Визуальный просмотр одной страницы не требует сервера; совместный двухролевой просмотр надежнее по опубликованному HTTPS URL.

## 8. Жизненный цикл и SLA

Канонические статусы: `new`, `waiting_support`, `waiting_participant`, `resolved`, `closed`. Назначение, эскалация и external wait — отдельные измерения, не новые lifecycle-статусы. Старые статические строки исходной очереди не задают новые серверные значения.

SLA работает 24/7: urgent 1 час, high 2, normal 8, low 16; due soon после 75% активного бюджета. В waiting participant показываем паузу, в resolved/closed активного дедлайна нет. Заметка, reporter update, чтение, переназначение и повтор команды не перезапускают часы. External wait и смена приоритета используют действующий `SupportSlaService`, не логику виджета.

После resolved клиентское окно по умолчанию 24 календарных часа, настройка superadmin 1–168; дедлайн — snapshot в тикете. Это не SLA. Ответ до дедлайна обрабатывается существующим сервисом; closed не открывается поздним ответом. Обычная поддержка закрывает spam/duplicate с причиной и проверенной связью дубликата; старшая — также senior decision. Сохраняются guards по открытым вопросам, запросам и external wait.

Closed исключен из активного списка, но доступен по явной ссылке/архивному фильтру. Во всех аудиториях — только разрешенная история, без формы ответа, заметок/закрепления, нового вопроса или action request. Клиентское повторное обращение создается существующей явной формой follow-up в его кабинете с отдельным ID/связью и заданным в настройках маршрутом. Виджет агента не выдает себя за клиентский кабинет и не создает follow-up автоматически.

Не переносить из старого HTML семидневное переоткрытие, mock-таймеры, dropdown устаревших статусов и прямые финансовые кнопки. Не менять cron/настройки жизненного цикла в рамках этой UI-задачи.

## 9. Серверная интеграция и ошибки

В общем admin layout подключить widget partial и AssetBundle; передавать только capabilities, разрешенные initial projections и безопасные локализованные строки. В `SupportV2Controller`/views убрать лишь Internal tab trigger/pane, не удалять сервисы, существующие действия и History. Актуальные пути по памяти: `application/modules/admin/controllers/SupportV2Controller.php`, `application/modules/admin/views/support-v2/view.php`, `application/services/support/*`. Конкретный layout и action names сверить с текущим checkout Игоря до патча.

Нужны операции: actor-scoped summary/list, разрешенная лента, mark-read с rendered cursor, существующие вопросы/replies/updates/notes/channel/action requests; для внутреннего чата — разрешенный recipient directory/search, list/read, find-or-create pair + send и selected-message conversion. Это карта команд, не утверждение готовности новых API. Для participant вне выбранного Chat V2 нужен отдельный узкий серверный adapter с проверкой active membership/source и текущего доступа; нельзя расширять доверие к клиентским параметрам существующего Chat callback. Смена адресата не переписывает membership существующего чата; прямые GET/POST, поиск, unread counters и source conversion проверяются на ту же пару участников.

Каждая мутация: session auth, CSRF, действующее право, объектная принадлежность, ожидаемая revision и стабильный operation/idempotency key. Изменение состояния и audit — в одной транзакции. Conflict возвращает свежую разрешенную projection; UI сохраняет текст, показывает конфликт и предлагает обновление, не отправляет повтор вслепую. После неизвестного результата сначала сверить исходную операцию по ключу. Закрытие/отзыв membership между открытием и submit проверяются сервером повторно.

UI states: загрузка; пусто; нет совпадений; недоступно по правам; нет сети; ошибка сохранения; конфликт; отправка; успех. Не показывать «отправлено» до подтверждения. Draft привязан к actor + channel/case; не передается другому пользователю. Production drafts использовать через текущий сервис/retention, не хранить полные приватные кейсы в localStorage. HTML input экранировать; локализация `Yii::t` с literal English keys охватывает JS, ARIA, title и server errors. Приемка минимум RU/EN, длинные строки, клавиатура, focus/ESC, reduced motion.

## 10. Карта приемки

| Экран / действие | Ожидаемый серверный/видимый результат |
| --- | --- |
| Любая разрешенная admin-страница → открыть виджет | Один экземпляр, те же разделы/счетчики/черновики; основной workflow не сброшен |
| Два Support info → поочередно Открыть | Два разных тикета/статуса/черновика; прямой переход без modal и новой копии кейса |
| Агент → Тикеты | Только свои verified memberships, включая Chat V2-origin; без чужих DTO/счетчиков |
| Support → выбор аудитории | Клиент, конкретный участник, internal не смешиваются; negative GET/POST и поиск/файлы изолированы |
| Support → Reporter update | Только автору; workflow/SLA/сессия не меняются |
| Два вопроса разным участникам → один ответ | Только свой question answered; другой open; ход Support, новый цикл SLA по действующему сервису |
| Обычный текст при открытом вопросе | Вопрос не закрыт; нет неявного перехода workflow |
| Отмена последнего / не последнего вопроса | Текст/причина аудируются; нет private-reason leak; правильный следующий ход |
| Открыть client-канал → reload | Тот же кейс/owner/SLA, безопасная client subject, пустая новая лента, private history не скопирована |
| Агентский вопрос на client-surface | «Дополнительная проверка», не «нужна информация от вас» |
| Новое сообщение при открытой панели | Badge остается до явного открытия/подтверждения rendered cursor; чужие cursor не изменились |
| Новый диалог → поиск / роль / выбор | Правильные доступные никнеймы и роли; zero match; нет клиентов, self и запрещенных аккаунтов |
| Support / Moderator / Super Admin → агент | Каждый может первым отправить; получатель видит отдельные личные диалоги |
| Одна пара → одновременная первая отправка / retry | Один conversation, два разных сообщения при двух разных отправках, один эффект при повторе одного ключа |
| Один агент → три разных сотрудника | Раздельные истории, drafts, read cursors; третий сотрудник и другой агент не читают чужую пару |
| Work-chat send / selected conversion | Без тикета на обычный send; один кейс на conversion retry; только выбранные source IDs |
| Action request / повтор / result | Requested не исполняет source; повтор не дублирует; результат только от authorized executor |
| Закрытый кейс / stale submit | История доступна по правам, мутация отвергнута, старый кейс не переоткрыт |
| Reload / PJAX / logout | Нет дублей handlers/timers, loss/leak drafts и старого actor context |
| Half / drag / keyboard resize / mobile | Сохранение личной ширины, каналов и текста; корректные границы; на mobile full screen без resize |
| 1440/1024/768/390/360/320; mobile 320×568 | Нет page overflow, пересечений и пропавшего поля/закрытия/действия вопроса |

Для backend-приемки Игорю: точный commit/build, миграции и три реальные роли; service acceptance + role-negative HTTP + сохранение/reload + конфликт/идемпотентность + Chat V2 readback. Локальный mock PASS этих проверок не заменяет.

## 11. Состав и границы поставки

Четыре HTML сохранены из существующего комплекта: две исходные страницы оболочки и два ролевых входа. Состояния не размножаются отдельными HTML: `?ticket=report`, `?ticket=second`, `?ticket=closed`, `?section=work`, `?recipient=501`; второе лицо агента `actor=sara`, сотрудника `actor=moderator`/`actor=admin`, клиентская projection и executor-fixture используют те же файлы. Основные входы — агент и сотрудник Support; другие роли доступны по ссылкам того же комплекта. Клиентский query служит только проверке изоляции, не дизайну нового клиентского интерфейса.

`js/internal-widget.js` целиком демонстрационный controller: синтетические роли, fixtures, localStorage и URL-персоны. Его не подключать как готовый production backend/authorization adapter. Переносить утвержденную разметку/стили и взаимодействия, связывая с текущими Yii-сервисами. `custom.js` содержит demo-ограничитель запросов; CSP запрет network/forms — только для preview, не шаблон production policy.

В ZIP: offline HTML, CSS, JS, vendor/fonts/images, это ТЗ, читаемый HTML ТЗ, README, third-party notices и manifest SHA-256. Внутренняя общая память, история задач, старые противоречивые MD, приватные реестры, тестовые мутации и QA-скриншоты не включены. QA-проверки и публикационные receipts хранятся отдельно локально.

Готовность этой поставки: макет и контракт интеграции. Серверная матрица, новые API/persistence рабочего чата, реальные transport, concurrency, финансовые/сессионные адаптеры, production локализация/доступность и итоговая пользовательская приемка остаются задачей внедрения и стендовой проверки, а не скрытым обещанием текущего HTML.
