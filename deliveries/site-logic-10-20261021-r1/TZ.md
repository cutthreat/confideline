# Логика Сайта Для Новой Вёрстки

Комплект подготовки по [карточке «Описание логики работы сайта к новой вёрстке»](https://trello.com/c/yTjEzv6y). Сборка материалов — 21.10.2026. Это требования и существующие макеты для передачи Игорю, не выполненное внедрение сайта и не отчёт QA.

## Что Передаём

- 78 экранов: назначение, вход, данные, действия, переходы и ограничения.
- Исторические настольные и мобильные снимки принятой вёрстки с привязкой к каждому экрану.
- Логику публичного сайта, входа, каталога, профиля, клиентского кабинета, чата, состояний консультации, платежей, уведомлений и справки.
- Поздние согласованные дополнения — в разделе «Уточнения к передаче». Не нужно собирать их по старым отчётам.
- Прежнее сопоставление с AskNebula перенесено в каждый паспорт с исходными датами и границами. Для 40 экранов соответствие не подтверждено прежними наблюдениями; новая упаковка не превращает его в полный сравнительный аудит.

[Все экраны и макеты](index.html). [Исходная нативная вёрстка из карточки](https://drive.google.com/file/d/1svzsVDIWQbcoymgqWqtqRAmEC8Ux-Sv3/view). Исполняемые HTML/CSS/JS находятся в исходном архиве; этот лёгкий комплект содержит ТЗ и иллюстрированные паспорта. Снимки сделаны ранее и не являются новым визуальным тестом. Соответствие текущего файла Drive локальной редакции final-r2 отдельно не проверялось.

## Границы Работы

Сохранить существующий дизайн и уже работающие возможности сайта. Подключение к backend, выбор обработчиков, моделей, API и способ реализации остаются за Игорем. Названия сущностей и маршруты в исходных описаниях — контекст, а не предписание переписать backend или создать параллельный сервис.

По каждому экрану требуется понятный результат для пользователя: что он видит, что может сделать, куда переходит и что происходит при ошибке. Связи с фактическим кодом, которые не подтверждены материалами, не выдаются за найденные обработчики. Одинаковое название элемента не доказывает одинаковые права или общий источник данных.

## Общие Правила

1. Гость просматривает разрешённые публичные страницы. Авторизация сохраняет выбранного эксперта, тему и допустимое назначение перехода. Клиент не входит в админку.
2. Агент и эксперт — один человек, работающий через разрешённые профили. Несколько профилей не дают дополнительных прав и не превращаются в нескольких сотрудников.
3. Открытие страницы, выбор эксперта, обычная переписка и раскрытие окна не запускают списание. Условия платной консультации и её запуска берутся из действующих согласованных правил, не из демонстрационного таймера.
4. Деньги, баланс, тариф, доступность и состояние консультации показываются по подтверждённым данным. Числа, отзывы, фото, видео и маркетинговые обещания исходного макета не становятся реальными данными только из-за наличия в HTML.
5. Формы сохраняют ввод при ошибке, показывают понятную причину и позволяют повторить действие без незаметного дублирования. Навигация и закрытие диалога не должны терять черновик без предусмотренного выбора.
6. Внутренняя переписка сотрудников, шаблоны оператора и служебная история не переносятся в клиентский чат. Публичные, клиентские и административные поверхности разделены.
7. Новые компоненты не меняют общую шапку, логотип, меню и стили остальных страниц. Локальные коллизии решаются отдельным ограниченным адаптером с сохранением исходников.

## Как Читать Детализацию

В навигаторе каждый экран имеет один паспорт. В нём находятся вход, данные, переходы, снимки и уже описанные действия элементов. Подробные предметные разделы ниже собраны из существующих документов 06–08.10; старые отчёты о проверках, служебные журналы и запросы к агентам в комплект не включены. Уточнения 20–21.10 имеют приоритет только в явно указанной области. Неподтверждённые предложения остаются предложениями, а не принятыми решениями.

## Что Пока Не Подтверждено

- Точные связи всех экранов и действий с текущей сборкой backend. Наличие описания и HTML не подтверждает, что функция уже реализована или отсутствует на сайте.
- Продуктовые развилки, явно отмеченные в паспортах и предметной логике: в частности, окончательное назначение главного CTA, применение приветственных минут и обещание Rewards. Старые предложения не утверждаются этой упаковкой; при наличии более позднего принятого решения применяется оно.
- Допустимость реальных маркетинговых чисел, цен, отзывов и медиа из демонстрационной вёрстки. Их нельзя переносить на сайт как подтверждённые факты.
- В прежних материалах нет открытого мобильного состояния фильтра каталога в кабинете и мобильного поиска в чате. Их отсутствие отмечено явно; эта упаковка не заменяет недостающие снимки новым аудитом.

Это не новые требования к архитектуре и не повод запускать общий аудит заново. Уточняется только конкретный вопрос, от которого зависит подключаемый экран.

## Уточнения К Передаче

### Фильтр каталога

Поверхность: Текущий /browse guest/auth; позже all-psychic.html и account/psychics.html.

Действие: Выбрать несколько направлений/тем, Поиск, Сбросить, пагинация и Back/Forward.

Результат: Явно применённый OR внутри групп / AND между ними, уникальные допущенные профили, верные total/page и выбранные ID; черновик не отправляется автоматически.

Граница: Сейчас только current-site; новая вёрстка позже. Не распространять автоматически новый фильтр на другие каталоги и лендинги.

[Актуальный комплект](https://cutthreat.github.io/confideline/deliveries/catalog-filter-21-20261015-r1/).

### Клиентский чат и консультация

Поверхность: account/chat-details.html, chatroom-active.html, chatroom.html.

Действие: Открыть выбранный диалог и данные/состояние консультации.

Результат: Один разрешённый conversation клиента с выбранным профилем; текущий service_session подтверждён сервером. Открытие/обычная переписка не начинают оплату.

Граница: Клиент не входит в admin-shell. Общую рабочую переписку и Support Internal сюда не копировать.

### Шаблоны оператора

Поверхность: Действующий admin Chat V2 и существующие global/personal/expert editors.

Действие: Вставить шаблон в непустой черновик.

Результат: Заменить / Добавить в конец / Отмена, сохранение исходного текста до выбора, фокус редактора; отправка только отдельным действием. Новая Взять себе не появляется.

Граница: Операторский каталог не добавляется клиенту SC-031 по совпадению слова Chat. Несколько профилей не расширяют права одного человека.

[Актуальный комплект](https://cutthreat.github.io/confideline/deliveries/chat-templates-70-20261015-r1/).

### Перевод текста

Поверхность: Документированный text-only POST /admin/translation/preview.

Действие: Перевести существующий текст либо ещё не отправленный composer draft.

Результат: Оригинал сохранён, preview transient, без создания message/ticket/conversation ради ID и без автоотправки.

Граница: Вызовы провайдеров только на backend; ключи не во frontend. service_session.internal_comment и внутренний timeline провайдеру не передаются. DeepL-first не закрывает цель трёх API.

### Права доступа

Поверхность: Клиентские и admin действия с закрытыми объектами; отдельные scopes каждого контура.

Действие: Прочитать/изменить объект, файл или экспорт; сменить назначение/отозвать доступ.

Результат: Раздельные свои/назначенные/чужие объекты, серверная проверка каждого действия и отказ после отзыва; меню не считается guard.

Граница: Не вводить новый RBAC и не требовать авторизацию для всех публичных экранов. admin-доступ клиента не создаётся.

[Актуальный комплект](https://cutthreat.github.io/confideline/deliveries/access-rights-49-20261015-r1/).

### Диалоговые окна

Поверхность: Существующий реестр dialog windows и его конкретные triggers.

Действие: Открыть/подтвердить/отменить окно; ошибка; Escape; возврат фокуса.

Результат: Согласованные loading/error/закрытие/фокус и адаптация без скрытой потери черновика или фонового опасного действия.

Граница: Не выдумывать наличие одинакового окна на всех78 страницах. Не заменять библиотеку и не перерисовывать готовый UI.

[Актуальный комплект](https://cutthreat.github.io/confideline/deliveries/dialog-windows-64-20261015-r1/).

### Внутренний чат сотрудников

Поверхность: Виджет Внутренний чат в admin-shell; пять HTML входов отдельного пакета.

Действие: Тикеты либо Рабочие чаты; выбрать адресата; обычное сообщение без тикета.

Результат: Рабочая переписка без открыто/закрыто и запроса обязательного ответа; адресные вопросы, закрытие и служебные действия остаются у тикета.

Граница: Клиенту не показываются админка, внутренняя переписка и служебные сведения. Адресные вопросы и служебные действия относятся к тикету, не к обычному рабочему чату.

[Актуальный комплект](https://cutthreat.github.io/confideline/deliveries/support-internal-20261013-r1/).

### Отзывы и рейтинг

Поверхность: account/consultation-review.html; отдельный опубликованный пакет отзывов/рейтинга.

Действие: Выбрать подходящую консультацию для отзыва, отправить/изменить отзыв в разрешённых границах.

Граница: История модерации доступна только разрешённым сотрудникам и не попадает в клиентский кабинет. Макет не является подтверждением серверных правил.

Результат: Подтверждённое состояние той же сборки и pack/version, а не только PDF или fake-DB результат.

Граница: Не пересобирать принятый курс L1–L7, не создавать конкурирующий Moodle и не смешивать прохождение курса с правом работать.

## 1. Главная

### Что Сохраняем

1. ConfideLine остается универсальной P2P-платформой; MakTaro является продуктом на ней. Функции знакомств не удаляются из платформы этим ТЗ.
2. Агент и эксперт являются одним человеком; внутренняя роль агента позволяет работать с несколькими закрепленными публичными профилями. На главной показывается профиль, а не внутренний логин человека.
3. Регистрация нужна до первого сообщения. Бесплатный диалог и платная консультация различаются. Принятие предложения не запускает списание: нужен предусмотренный серверным контрактом Start и условия готовности.

6. На странице не создаются заявка на выплату, оплаченная консультация или платеж при просмотре, переходе, раскрытии FAQ либо движении карусели.

`<base href="_unzipped/">` участвует в разрешении URL: `../home.html` и `../signup-create.html` не являются ошибками сами по себе. Для production отдельно сверяются deployment base path, реальные маршруты и якоря. `index.html` в поставке является индексом комплекта, а не домашним URL продукта.

### Состояния И Связанный Путь

- **Гость / вошедший клиент:** сохраняются тема, выбранный профиль и допустимое назначение после auth. Успешный вход не начинает оплату. Устаревшее/неразрешенное назначение проверяется сервером, а не слепо исполняется из return URL.
- **Эксперт недоступен / профиль снят:** действие не создает разговор от имени другого эксперта молча. Используется предусмотренная продуктом доступность/выбор; точное поведение проверяется в существующем контракте.
- **Пустые данные:** нет вымышленных карточек, online-статуса, цифр или рейтинга. Выбор эксперта и контент не должны зависеть от загрузки необязательных отзывов/видео.
- **Ошибка отдельных данных:** сохраняются работоспособные блоки; пользователь получает честный результат, не ложный успех. Loading/error/retry для фактически динамических блоков определяются интеграцией.
- **Карусель / FAQ / меню:** меняется только интерфейс; focus/aria, края карусели, Escape, возврат фокуса и responsive reset проверяются в новом нативном прогоне.
- **Video idle / playing / failed:** проигрывается записанный материал; нет скрытого старта консультации или списания.
- **После главной:** каталог/профиль → auth при необходимости → бесплатный диалог → предложение платной консультации → согласие → существующие проверки баланса/готовности → server Start → активная сессия/пауза/завершение. Это связанный контракт экранов, не все операции главной.

Клиент выбирает профиль и начинает свой разрешенный путь. Эксперт не редактирует CMS главной просто потому, что имеет внутреннюю роль агента. Сотрудник работает с контентом, публикацией и назначением только в существующих правах. Точную актуальную матрицу прав проверяет команда; новую роль или разрешение из HTML не вводим.

Админ-связи: существующие редакционные страницы/локали → тексты и FAQ; публичные профили/назначение/доступность → карточки; тарифы и welcome → коммерческие условия; публикация отзывов/разрешенных медиа → социальное доказательство. Карта функций называет CMS `page/index`, языки и SEO; это документальные кандидаты для сверки, не доказательство текущего RBAC или прямой записи в БД.


## 2. Вход и регистрация

### Путь И Данные

```text
каталог / выбранный public profile / разрешённый chat intent
  -> вход либо шаг 1 -> шаг 2 регистрации
  -> подтверждённый ответ существующего backend
  -> нужное состояние аккаунта: активен / требуется подтверждение
  -> безопасный возврат к тому же профилю и допустимому диалогу

вход -> восстановление -> нейтральный результат запроса
  -> письмо -> существующий reset/activation flow -> вход / возврат
```

Регистрация клиента не создаёт эксперта, роль сотрудника или дополнительные права. Агент/эксперт — одно лицо, внутренние назначения админки не определяются полем gender. Вход, регистрация и Let’s go не создают сообщений, offer, paid Start, начислений, выплат или расхода бесплатных минут. Открытие кабинета не заменяет отдельного согласия и старта платной консультации.

Вход получает намерение перехода и безопасный серверный return-контекст. Регистрация получает согласованные публичные данные клиента, locale и действующие серверные правила. После успеха статус/identity берутся только из ответа backend и его сессии. Баланс, welcome entitlement и permissions не создаются по DOM fixture.

Для return сохраняются стабильный profile ID и вид действия, а не lookup по имени эксперта. Клиентский URL не задаёт роль, чужой userId, тариф или право на private conversation. Допустимость адреса и объекта сервер проверяет повторно; внешний URL/`javascript:`/подмена IDs не принимаются. Истёкший/скрытый профиль даёт честное состояние недоступности, не заменяется Margo или первым доступным экспертом.

Source-состояния: `idle -> invalid` (client validation), `idle -> unavailable` (adapter отсутствует), `pending -> invalid/unavailable/accepted`, `pending -> unknown` (неподтверждённый исход). Pending блокирует контролы, accepted не делает сам redirect. Unknown запрещает повтор; host сверяет исход исходного request, затем `resolve` с тем же requestId. Чужой/stale requestId не применяет ответ. `requestId` source — счётчик в памяти страницы, не серверный idempotency key и не защита от дубля после reload.

Не копировать сырой backend response/error/stack в UI. Host нормализует fieldErrors/безопасное сообщение и отдельно реализует бизнес-ошибки: заблокирован/не подтверждён/уже зарегистрирован/просроченная ссылка/провайдер недоступен. Session/CSRF/лимиты попыток остаются существующими серверными механизмами; токены и credentials не включаются в отчёт.


## 3. Каталог экспертов

### Назначение И Путь

Клиент выбирает направление/тему и конкретный опубликованный профиль. Каталог не является оплаченной консультацией или списком внутренних сотрудников.

```text
главная / меню / тематическая страница
  -> каталог + разрешённый контекст
  -> профиль конкретного эксперта
  -> вход/регистрация, если нужны для сообщения
  -> тот же профиль / бесплатный диалог
  -> отдельно предложение, согласие и server Start платной сессии
```

Агент и эксперт — один человек с одним или несколькими публичными профилями. Каталог показывает профили, не внутренние логины. Их нельзя склеивать по имени, владельцу или фотографии. Внутренние роли, назначения и баланс сотрудника клиенту не выдаются.

### Фильтр И Возврат

1. Без параметров — разрешённая базовая выдача. Тематический вход — точный ID, не английский текст.
2. Chips становятся доступными toggle-контролами; повторное нажатие снимает выбор. Все 11 опций сохраняются. Taro не новый справочный ключ.
3. Следовать #21, не переопределять legacy GET. `areas[]`, `topics[]`, `catalog_filter_variant` — требования, не обнаруженный API.
4. Новый выбор начинает с первой страницы; поздний ответ прежнего query не заменяет новое состояние.
5. Reset очищает оба набора и возвращает baseline, не сбрасывает язык/тему или данные клиента.
6. Пагинация сохраняет IDs/вариант/sort; total не раскрывает закрытых профилей. Не добавлять новые sort/GEO/цену/язык как фильтры без требования.
7. Профиль сохраняет Back к каталогу с выбором/позицией; Back не повторяет Start. Доступность при возвращении обновляется.
8. Пустой необязательный параметр не запрещает публикацию сам по себе, но не совпадает с выбранным значением.

Legacy 07.10 показал AND для двух Areas: 6 профилей при Career, объединение — 19. Это не правило v1 и не legacy-дефект: новый OR реализуется отдельной strategy, старый запрос сохраняется. Четыре недостающих точных mapping остаются в объёме #21.

## 4. Профиль эксперта

### Назначение И Связанный Путь

Клиент проверяет сведения конкретного публичного профиля, доступность и стоимость, читает отзывы, добавляет в избранное или переходит к общению именно с ним.

```text
каталог с выбранным profile ID
  -> публичный профиль с тем же ID
  -> вход/регистрация при необходимости
  -> разрешённый постоянный диалог client + profile
  -> бесплатная переписка
  -> отдельно предложение / согласие / server Start / paid session
```

Агент/эксперт — один человек; несколько анкет не являются несколькими сотрудниками. Клиент видит выбранную публичную identity. Сотрудник действует только через закреплённый профиль и назначенный диалог; админская шапка не доказывает эти права. Переключение профиля не меняет авторство, отправителя и уже созданную сессию задним числом.

Профиль не создаёт оплату при открытии, клике избранного, раскрытии FAQ, переходе в чат, auth или просмотре календаря. Source Start chat — ссылка, не согласие/Start платной сессии. Перейти в chatroom и начать тарификацию — разные действия.

### Переходы И Состояния

1. Сервер разрешает ID профиля и видимость; отсутствующий/закрытый объект не заменяет другим экспертом.
2. Общая страница гостю не раскрывает account details; клиенту даёт только собственные favorite/balance/entitlement. Статус входа не выводится из одной видимой шапки.
3. При auth сохраняются stable profile ID, тип действия и безопасный return. После auth право/доступность проверяются заново; отмена не выполняет действие.
4. Chat request разрешает canonical client/profile conversation. Существующая история не копируется; повторная навигация не создаёт duplicate session.
5. Бесплатная переписка, welcome/trial, offer/consent и paid Start — отдельные состояния. Нельзя считать переход в chatroom началом billable секунд.
6. Нет опубликованных оценок — скрыть целиком rating под именем, без пустых звёзд/отступа. Recent review не показывать без настоящего отзыва. В reviews — «Отзывов пока нет» и допустимая кнопка; первая публикация обновляет все агрегаты.
7. Loading/error не подставляет demo profile, цену, Online или чужую информацию. Retry безопасен; данные профиля доступны даже при ошибке необязательных отзывов.
8. Favorite saving/error/persisted отличается от локального pressed; после отказа состояние согласуется с сервером и не обещает сохранение.
9. Busy/offline/withdrawn показываются честно; возможное ожидание не оплачивается. Конкретный допустимый CTA проверить по existing contract, не добавить новую queue самовольно.
10. Booking hidden/ready/loading/no slots/selected/submitting/confirmed/error применяется только к реально согласованному календарю. Дата/пояс/эксперт при подтверждении те же, что показаны, не ISO из browser assumption.

## 5. Клиентский чат

### Назначение И Общий Путь

Клиент открывает постоянный диалог с выбранным публичным профилем, читает историю, пишет бесплатное сообщение, отдельно принимает предложение консультации и наблюдает подтверждённое состояние сессии. Active и Details являются представлениями этого же контекста, не отдельными чатами или хранилищами.

```text
каталог / профиль / собственный список диалогов
  -> auth с сохранением выбранного public profile ID
  -> разрешённый conversation того же клиента и профиля
  -> обычная переписка
  -> предложение / явное согласие / операторский Start / готовность сторон
  -> active -> pause / reconnect / completed
  -> новая консультация в прежнем conversation с новым service_session
```

Ни открытие чата, ни отправка обычного текста, ни окно Details, ни выбор темы не запускают оплату. ### Сессия, Возвраты И Ошибки

1. `no_consent`, `offer_pending`, `ready`, `connecting`, `active`, `paused`, `reconnecting`, `completed` приходят с сервера; `billing_mode` none/trial/paid является отдельным полем. Названия local running/paused не заменяют этот контракт.
2. Offer и согласие сами не списывают credits. Start/Resume принадлежат разрешённому операторскому сценарию; `connecting` бесплатен, активность начинается после готовности сторон.
3. Документирована отдельная клиентская инициатива консультации; конкретная CTA новой верстки ещё должна быть согласована. Не приравнивать произвольный Send/Start chat к этой инициативе или согласию.
4. Pause/reconnect/reload не создают новый billable segment из browser timer. Клиент отображает returned snapshot/version и server elapsed baseline. Повтор действия, две вкладки и опоздавший ответ не возвращают старое состояние поверх нового.
5. Top-up возвращает в прежний conversation, обновляет server balance и не нажимает Accept/Start/Resume автоматически. Недостаток баланса отличается от network error; точные тариф/условия берутся из действующего контракта, не fixtures.
6. Completed терминален для данного `service_session`; новая консультация создаёт новую session в том же постоянном conversation и не переписывает старые начисления/историю.
7. Таймаут Send/End/session request означает неизвестный исход до сверки, а не гарантированный отказ. Сохраняются исходный operation key, адресат и текст; новая попытка не дублирует эффект.
8. Запрет доступа/снятое назначение/закрытый профиль проверяются повторно на сервере при запросе, а не только при показе controls. Ошибка необязательных Details/эмодзи не должна уничтожить draft/историю.

### Медиа: Решение Не Подменяется Макетом

Приоритетное правило из customer package от 14.08 разрешает text/system/emoji и одобренные images/documents; запрещает audio/voice/video/arbitrary files. Документация одновременно честно фиксирует temporary local override владельца реализации, сохраняющий audio/voice. Это расхождение, а не отмена продуктового запрета. Новый голосовой preview в final-r2 не является новым согласованием.

До production нельзя подключать voice/video upload только по наличию кнопки. Требуется подтвердить целевую policy и выполнить её на UI и direct server requests. Images/documents нуждаются в inspection/quarantine, защите контактных каналов и отказе при недоступности проверки; allowlist MIME/extension не заменяет scanner. Исторические объекты не стираются молча. Download повторно проверяет принадлежность conversation, revoked access и удаление сообщения.

Предложение П06 о записанном видео не является разрешением пользовательского video attachment: источник контента и opener отдельны. Эти три экрана не доказывают видеозвонки, microphone recording или private storage. Их не добавлять самовольно.


## 6. Состояния консультации

### Единый Контекст

Один долгоживущий `conversation` сохраняется после завершения консультации. Каждая консультация имеет отдельный `service_session`; `completed` терминален для данной записи. Следующее предложение создаёт новую сессию после серверных проверок, но не другой постоянный диалог. Разные анкеты одного сотрудника не сливаются по имени.

| Данные | Источник и использование |
| --- | --- |
| Клиент и права | Текущая серверная auth-сессия, не клиентский ID из query или DOM. Проверка принадлежности conversation/session на каждом чтении и действии. |
| Conversation и session | Стабильные ID, version, status, billing mode, readiness и разрешённые действия из canonical snapshot. Событие UI не является новым состоянием сервера. |
| Эксперт | Публичный profile ID и согласованный snapshot имени/фото. Видимый текст, desktop image и mobile source должны относиться к одной анкете. |
| Время | Серверные deadline и отметка времени snapshot. Browser countdown только отображает срок; не продлевает grace/offer, не завершает billing и не доказывает online. |
| Финансы | Connecting не оплачивается; pause/reconnect не создают новые оплачиваемые сегменты. Фактическое списание только по authoritative active intervals. Собственный кошелёк клиента и операторский balance signal имеют разные права. |
| Предложение | offer/request ID, version, срок, тариф/услуга, право принять и связь с conversation. Согласие отдельно от Start оператора и готовности обеих сторон. |
| Отзыв | Завершённая платная session, eligibility, existing review, rating и текст. Клиента/эксперта сервер определяет из session. Draft привязан к клиенту и session, не к имени. |
| Обращение | conversation/session/profile context, выбранная причина, описание, существующий request при повторе. Transcript передаётся по серверным правам, а не со слов текста макета. |

Имена событий ниже реально есть в baseline. Имена данных в таблице обозначают смысл, а не наличие поля БД или нового endpoint.

### Переходы

```text
conversation -> offer_pending -> клиентское согласие -> ready
  -> Start оператора -> connecting -> обе стороны готовы -> active
  -> paused -> подтверждённый Resume -> connecting
  -> reconnecting -> подтверждённое восстановление -> active
  -> completed -> прежний conversation / отзыв / Support
  -> новое предложение и новая service_session в том же conversation
```

Открытие/закрытие окна, `Wait`, `Stay`, отзыв, жалоба и пополнение сами по себе не запускают/возобновляют оплату. Не связывать клиентское `End chat` напрямую с операторским `complete` без утверждённого клиентского сценария, server permission и нужной причины. Предложение safe-pause из общей спецификации не становится утверждённым решением этим документом. Пауза #25 остаётся в силе: описание перехода Support не разрешает её реализацию или внешнюю отправку.

Adapter обязан явно сопоставить source `reconnect_grace` с canonical `reconnecting`; `expert_followup_offer_pending` является UI-проекцией конкретного предложения, а не уже доказанным новым серверным status. Смешивать эти строковые enum без mapping нельзя.

## 7. Платёжные состояния

### Общий Договор

1. Пополнение покупает credits собственного кошелька. Оно не является consent на консультацию, подпиской Premium, разрешением auto-refill или выплатой исполнителю. Курс выплаты исполнителю не переносится в цену клиентской покупки.
2. По общей спецификации базовое правило покупки: 1 USD = 15 credits. Пакеты/бонусы/скидки, иная валюта и округление задаются текущим серверным каталогом и утверждёнными условиями, не числами HTML. Fixtures 350/$24.99, 120/$9.99, 160/$2.99 и -85% не становятся коммерческим решением от наличия в макете.
3. Заказ фиксирует package ID/version, credits/bonus, subtotal/discount/total/currency и исходный контекст. Не читать сумму или право на скидку из DOM как доверенные входы. Изменение цены требует новой явной проверки/подтверждения, а не списания по старому экрану.
4. Eligible methods определяются сервером с учётом работающего подключения, настроек системы/метода, страны, валюты, пользователя и технической capability. Не требовать PayPal/Apple Pay/сохранённую карту только потому, что они нарисованы.
5. Одна попытка имеет устойчивый ID и ключ операции; pending/unknown не равны failed. Повторное открытие окна, reload, другая вкладка и callback не создают новую покупку. При неизвестном исходе сначала сверить исходную попытку; новый допустимый retry только после известного результата.
6. Browser return/click/закрытие окна не подтверждают оплату или начисление. Success требует авторитетного серверного результата платежа и соответствующего однократного зачисления; если эти этапы не завершились одновременно, показывать фактическое промежуточное состояние.
7. После зачисления обновить собственный кошелёк и вернуться в тот же разрешённый conversation. Не делать auto-accept, Start или Resume; серверный paused/completed не отменяется пополнением.
8. One-click является одной подтверждённой покупкой доступным сохранённым способом; auto-refill требует отдельного согласия на будущие пополнения, условий, лимитов и выключения. Сохранение карты не включает его.
9. Закрыть overlay не значит отменить provider attempt, вернуть деньги или убрать финансовый след. Support intent не refund. Пауза #25 сохраняется.
10. Секреты провайдера и карточные значения не включать в приложение-лог/DOM event/хранилище/QA. Использовать уже принятый provider-hosted/tokenized flow. Состояние сохранённого метода отображать разрешённым описанием сервера, не подставлять fixture-маску под новый ID. Это проектное требование, не заявление о выполненной compliance-сертификации.

### Данные И Связи

| Объект | Требуемые данные / источник |
| --- | --- |
| Auth/client | Текущий клиент сервера; только его wallet, checkout, order, attempt и сохранённые методы. Payload.authenticatedClient и скрытый DOM не заменяют RBAC. |
| Funding context | Conversation/profile, pre-start intent либо paused session/version/reason/deadline. Safe return разрешён только в свой контекст, не произвольный URL. |
| Каталог | Catalog/package versions, credits/bonus, цена/валюта, eligibility, период действия. Пустой/ошибочный каталог имеет отдельный UI, не fallback к demo-пакету. |
| Offer | Discount/one-click ID/version/expiry/entitlement, условия и capability. Дисконт и авто-пополнение имеют отдельное основание. |
| Checkout / order | Собственные ID/version/status, snapshot суммы и пакета, выбранный разрешённый метод. Payment attempt отдельно от order и session. |
| Method | Opaque ID/version/type и безопасное display label из сервера. Native wallet capability и сохранённая карта не считаются доступными по картинке. |
| Operation | Operation/action/idempotency key, ожидаемый контекст и точный pending result. Один ключ не превращает разные действия в одну финансовую операцию без backend-контракта. |
| Результат | Авторитетные состояния attempt/payment, связь с order, credits grant/transaction; только разрешённые redacted references. |

Source states (`pre_start_funding_required`, `continuation_topup_required`, `checkout_order_review` и другие) являются проекциями UI. Не вводить соответствующие backend enum или таблицы автоматически. Exact mapping определяет Игорь по действующим источникам и сборке.

```text
pre-start / paused funding / approved offer
  -> server catalog + selected package
  -> current order review + eligible method
  -> existing provider confirmation / secure form when required
  -> pending / requires action / succeeded / declined / unknown
  -> authoritative payment + one credits grant
  -> same conversation, without automatic Start or Resume

error or lost callback
  -> read/reconcile original attempt
  -> still pending / settled success / definitive failure
  -> only then an explicitly allowed alternative or retry
```

## 8. Выбор эксперта

### Данные И Правила

| Данные | Владелец и необходимая связь |
| --- | --- |
| Клиент | Серверная identity и собственные favorites/preferences/conversations. Скрытие кнопки или boolean payload не заменяет права. |
| Экспертный профиль | Устойчивый public profile ID, display name, допущенное фото/описание/специализации, тариф и источник рейтинга. Имя не является ID; одноимённые люди и несколько профилей не смешиваются. |
| Доступность | Серверное online/busy/offline, актуальность snapshot и возможность нового обращения. Статус карточки не резервирует слот, не обещает время ожидания и не гарантирует ответ. |
| Каталог и подбор | Фильтры с устойчивыми option IDs, действующие правила #21, сортировка/страница, собственный selection context и version. Не навязывать UI с ровно тремя результатами. |
| Избранное | Связь client/profile и подтверждённое желаемое состояние add/remove. Один профиль в нескольких секциях имеет согласованное состояние. |
| Trial/offer | Серверная eligibility, entitlement ID/version/остаток/условия. 3 минуты welcome и применение к первой начатой консультации не следует расширять до нового бонуса при каждой смене эксперта. Последнее применение остаётся предложением П01 общей спецификации. |
| Selection context | Выбранный профиль, тема, разрешённые предпочтения, источник входа, безопасный возврат, связанный conversation. Не переносить старую переписку другому эксперту. |
| Вопрос и черновик | Subject, разрешённые DOB/context, body и одобренные attachments. Черновик принадлежит собственному client + intended expert/conversation, не общей форме всех профилей. |
| Подтверждение действия | Operation/request ID и фактический серверный результат. Показ pending/ошибки/повтора не должен выдумывать созданное сообщение, подписку или сессию. |

1. Выбор, избранное, trial picker, отправка вопроса и открытие чата не дают consent на платную консультацию, не включают платный таймер и не расходуют бонус сами по себе. Paid Start остаётся отдельным действием оператора по действующему контракту.
2. Строки `45 credits/min`, `3 FREE`, баланс `120`, рейтинги/счётчики и рекламные подборки из HTML не становятся действующими обещаниями. Отображать авторитетный snapshot; изменение цены до consent требует нового подтверждения, не молчаливой подмены.
3. Целевой free question сохраняется как сообщение постоянного диалога после явной отправки. Открытие формы или Start chat, который пока только открывает диалог, не отправляет черновик автоматически.
4. Guest проходит auth с сохранением разрешённой цели. Нельзя после login терять выбранный профиль, открывать общий demo-chat или принимать произвольный return URL.
5. Online/busy/offline/нет совпадений/error различаются. Ошибка сети не является пустой выдачей, а отсутствие кандидатуры не разрешает silently выбрать другого эксперта или подставить demo.
6. Агент и эксперт по решению 05.10 один человек; его несколько профилей не являются дополнительными операторами. Внутренние назначения и права #46/#49 не выводятся из клиентского выбора и не раскрываются как служебные данные каталога.
7. Успех записи показывать по серверному результату. Timeout/переключение окна не удаляют pending; повтор сверяет исходную операцию. Локальный aria-pressed, сообщение live-region и событие `nebula:*` не являются сохранением.

```text
catalog / favorites / topics
  -> explicit expert selection + server revalidation
  -> ready: own permanent conversation / free-question form
  -> busy/offline: same selected context + explicit alternative/wait/notify
  -> no matches: change filter or approved wait path

details -> back to same picker OR close entire selection flow
trial picker -> eligibility recheck -> same conversation rules
question submit -> pending -> persisted message OR preserved draft/error
paid offer / funding / consent / operator Start remain separate transitions
```

Данные: selection ID/version, доступные кандидаты и текущий выбранный profile ID, реальный opener. Источник содержит ровно три fixture-профиля; переданное open-событие не обновляет список или selection из payload.

| Контрол | Действие | Результат |
| --- | --- | --- |

| SC-044-A02, SC-044-A06 | Previous / Next | Меняют выбранного кандидата в границах списка. При synthetic width320 минимум=1 даже с non-static flag: первый из трёх недоступен. Не переносить ограничение в live renderer. |
| SC-044-A03, SC-044-A04, SC-044-A05 | Выбрать карточку | Click/Left/Right обновляют один radio/selectedExpertId. Требуются актуальная доступность, полный динамический список и одинаковая возможность выбора на всех размерах. |

При числе карточек не равном трём source целиком прекращает binding; synthetic два кандидата не работают. На 0/1/2/много нужен штатный результат, не дополнение фиктивными людьми. Open игнорирует новый selectedExpertId/candidates; возвращение не должно молча выбирать прежний fixture.

### SC-045: Выбор С Trial

Данные обычного выбора плюс собственное право trial: entitlement ID/version, остаток, условия, допустимые кандидаты. Надпись «3 FREE with a new psychic» не расширяет одноразовый welcome bonus до каждого нового профиля. Бонус не расходуется на ожидание, отмену picker или смену выбора.

| --- | --- | --- |

| SC-045-A02, SC-045-A06 | Previous / Next | Выбор по допустимому списку; source имеет три карточки. Ограничение 320 действует только при staticProjection=true, в отличие от generic. Не заменяет native mobile proof. |
| SC-045-A03, SC-045-A04, SC-045-A05 | Кандидат | Radio, Left/Right/Up/Down. Выбор явный; сервер повторно проверяет доступность/eligibility в момент commit. |

Исходный root видим без open, commit не имеет этого guard; initial mount также требует реальной серверной проверки. Входные freeMinutes не обновляют «3 FREE», а commit не переносит entitlement ID. После загрузки/повторного клика нельзя выдавать эти свойства за интегрированную бонусную механику.

Данные: тот же selected profile ID/version, public profile snapshot, разрешённое избранное/отзывы, цена, picker opener и flow opener. Только публичные поля; административные заметки/назначения не включать.

| SC-043-A03 | Close / Escape / scrim | `nebula:expert-selection-flow-close-required`; закрыть весь selection flow и вернуть реальный flow opener. Отличается от Back. |
| SC-043-A04 | Favorite | Локальный pressed и `nebula:expert-favorite-intent-required`, expertId/localSelected/persisted=false. Подтверждение сохранения и синхронизация с каталогом/избранным отдельно. |

Host должен атомарно заменить весь snapshot и scoped state; нельзя отправить действие к B под изображением A. Два preflight клика дают два intent без блокировки.

### SC-068: Вопрос До Начала

Вход от выбранного профиля/диалога, включая offline/busy. Данные: профиль, собственный conversation/selection context, scoped draft и действующие правила body/DOB/attachments. Форма не должна подменять клиента, профиль или ранее данное согласие.

| Контрол | Действие | Результат |
| --- | --- | --- |
| SC-068-A01 | Close / Escape / scrim | Скрывает frame; `nebula:question-before-start-dismiss-required`. Сохранить либо явно отменить draft по принятой политике, не отправлять сообщение и не создавать session. |
| SC-068-A02 | Subject | Source допускает пустое, maxlength отсутствует. Target определяет нужность/лимит действующим message contract, сохраняет ввод при ошибке и не выводит raw текст небезопасно. |
| SC-068-A03 | DOB | Optional, формат DD.MM.YYYY, реальная календарная дата, не будущее. Source различает 31.02.2000/29.02.2000. Это не проверка возраста, identity или согласия; сервер независимо проверяет разрешённое поле. |
| SC-068-A04 | Detailed question | Trimmed nonempty, иначе focus/aria-invalid. Source не устанавливает maxlength. Target использует server limits и scoped draft, не теряет текст при отказе/unknown. |
| SC-068-A05 | Attach a file if required | Меняет только lastAction/live-status; нет file input, picker или CustomEvent для adapter. Подключение только принятой private attachment policy, не произвольных файлов/голоса/видео. |
| SC-068-A06 | Start chat | После проверки полей `nebula:question-before-start-submit-required` передаёт лишь lengths/hasDob и persisted=false/sessionCreated=false. Реального body/subject/DOB/recipient/operation нет. Host должен выполнить разрешённую отправку в правильный постоянный диалог и подтвердить серверный message ID, а не считать этот event отправкой. |

В baseline повтор выдаёт два submit-intent, pending отсутствует. Open не читает expertId/name/rate, не очищает и не разделяет поля: после A→Close→Open B остаётся draft A, прежний Margo и 45 credits/min. Это риск ошибочного адресата при подключении, но в проверке никакое сообщение не отправлялось.

Вложения должны использовать существующие `message/message_attachment`, защищённую выдачу и серверные проверки. Наличие attachment-кнопки не даёт право на произвольный файл. Customer rule разрешает только принятые изображения/документы с inspection/quarantine; audio/voice/video запрещены, существующий local override остаётся неснятым расхождением. Прямой upload API должен применять те же права и политику; неизвестные файлы не загружаем ради оживления этой формы.


## 9. Уведомления

### Общая Логика

| Объект | Данные и источник истины |
| --- | --- |
| Пользователь | Текущий клиент сервера; только его настройки, endpoints и разрешённые объекты. AuthenticatedClient=true в payload не заменяет серверную проверку. |
| Категория | Стабильный category/event key: ответ эксперта, offer, horoscope, system либо availability/reminder. Название страницы не является backend event. |
| Предпочтение | Сохранённое значение по категории/каналу, версия, доступность изменения и ошибка/pending. Не брать defaults из on/off SVG. |
| Канал | Только реально доступный и разрешённый email/SMS/Telegram либо существующий иной канал. Его наличие в HTML не означает настроенного отправителя или получателя. |
| Endpoint | Opaque ID, тип, безопасное display-описание, ownership/verification/revocation state. Адрес/телефон/аватар fixture не является контактом клиента. |
| Subject | Экспертный профиль, conversation или другое событие с ID/version и проверкой доступа. Нельзя подписать на одного эксперта под заголовком другого. |
| Intent / operation | ID/version намерения, точный scope выбранных каналов, request/operation ID, pending/result. Разные действия не склеиваются совпадением flow ID. |
| Подписка / напоминание | Серверное сохранённое правило и его состояние, разрешённая отмена/expiry. Не равно выбору checkbox или отправленному event. |
| Доставка | Trigger → разрешение/предпочтения → job → попытка → фактический результат провайдера. Saved, queued, sent, delivered и opened не подменяют друг друга. |

1. Настройки сообщений эксперта, marketing offers, horoscope, system events и уведомления о доступности не смешивать. Изменение одной категории не включает другие, не даёт согласие на консультацию/платёж и не меняет баланс.
2. Существующее правило почтового MVP из источника: `message.received` используется для ответа эксперта клиенту, чтобы вернуть клиента в кабинет. Отдельное письмо на сообщение клиента не заводится. Текущий trigger и переменные всё равно требуют проверки; не размножать событие при подключении новой формы.
3. Открыть Notifications или прочитать описание не значит изменить настройки либо отметить реальные события прочитанными. В этих пяти страницах показаны settings, не inbox.
4. Согласие на категорию, подтверждение принадлежности канала и subscription на конкретного эксперта различны. Надпись «By clicking» и картинка галочки не являются доказательством записанного согласия. Применять принятые условия/версию, без объявления legal/compliance-приёмки этим ТЗ.
5. Для сервисных сообщений backend определяет разрешённое изменение и обязательные категории. Нельзя обещать выключение всех security/payment/account сообщений только потому, что макет рисует общий switch. Точная classification и её влияние на `count_user_settings` требуют согласованной связи.
6. При unavailable/revoked/unverified endpoint показать фактическое состояние и разрешённый verification flow. Выбор Telegram или показ телефона не устанавливают связь с получателем; placeholder Email не подтверждает адрес.
7. Pending/unknown сохраняются при Close/reopen/reload. Повтор сначала сверяет исходную операцию. Ответ с чужим/старым operation ID не снимает ожидание нового запроса; два source intent не доказывают две реальные подписки.
8. Success показывать после серверного readback соответствующего действия. Предпочтение сохранено не означает письмо доставлено; попытка провайдера не равна прочтению. Ошибка отправки не должна автоматически включать другую категорию/канал.
9. При отказе сохранить выбор/черновик; отмена не отправляет уведомление. Назначенный эксперт, разговор и пользователь сохраняются при переходах. Содержимое приватного чата не копируется в публичные ссылки/логи/QA; действующая политика payload определяется backend.
10. Имена, бренд, баланс 120, счётчики 2/3 и телефон/контакты из baseline не являются текущими данными. Пауза #25 сохраняется: Support notification rules не используются для возобновления Support-реализации.

```text
own notification settings -> category -> allowed preference change
  -> pending -> saved version / preserved draft + error

selected expert / own conversation -> notification intent
  -> actual available channels + verified endpoint/consent state
  -> explicit selection -> required verification/consent step
  -> confirmed subscription/reminder -> return to same object

later real trigger -> existing notification pipeline -> actual delivery result
```

Это логический путь, не утверждение о существующих endpoints или очереди. Не вводить новую notification subsystem до проверки действующей реализации.
