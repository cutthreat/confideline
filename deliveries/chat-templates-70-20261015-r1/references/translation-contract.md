## 0. Существующий Контур И Граница Изменения

Архив Игоря 24.09 описывает **общий** `POST /admin/translation/preview`: `TranslationController::actionPreview`, `TranslationPreviewForm` и `TranslationPreviewService`. Запрос содержит только текст, языковое направление определяется сервером; нет разрешения произвольных message/conversation/ticket ID. В Chat V2 документированы обе точки: просмотр перевода реплики и ещё не отправленного composer draft. Контроллер (исторический или смежный источник; не входит в эту выдачу), матрица контролов (исторический или смежный источник; не входит в эту выдачу), Stage 1 (исторический или смежный источник; не входит в эту выдачу).

Это **local mock**, без provider credentials, а не работающий DeepL/Google/Amazon. `BACKEND_READY` в архивной матрице относится к UI/локальному request path, не к внешним API или текущему deploy. Источники dated; PHP-код и нынешняя реализация не проверены. Support #25 на паузе: его интеграцию и QA сейчас не исполняем.

Переиспользовать существующий общий сервис, не создавать второй переводчик. Для черновика не нужен фиктивный message ID или предварительная отправка. Добавление реальных provider adapters, прав, языков, конфигурации, отказоустойчивости и клиентского доступа требует технической сверки Игорем; admin-only preview нельзя объявить готовым API для клиента/эксперта. Указанные ниже DTO/поля/permission names — целевые предложения, не фактические route/schema/keys действующей сборки.

## 1. Решение v1

Перевод выполняется **только backend-сервисом MakTaro** по явному действию пользователя «Перевести» для конкретного сообщения. В настройках можно добавить персональный режим «переводить входящие автоматически», но он выключен по умолчанию до правовой и экономической проверки. Исходный текст сообщения остаётся каноническим; перевод — связанная проекция, а не новая реплика и не замена оригинала.

В целевой интеграции поддерживаются сообщения клиента и одного человека эксперт/внутренний агент; Support подключается только после снятия #25 pause. Внешний провайдер получает только минимальный текст разрешённой реплики/явно выбранного собственного черновика и нужную пару языков, без отдельного контекста имени, e-mail, номера, ID, истории, платежа или тикета. Сам текст может содержать персональные сведения: удаление metadata не делает его анонимным и не снимает DPA/consent/billing gates. Вложения, изображения и голосовые данные не переводятся в v1. `service_session.internal_comment` и внутренний paid-session timeline никогда не передавать провайдеру — даже если сотрудник вправе их читать; действующий предметный контракт (исторический или смежный источник; не входит в эту выдачу) прямо запрещает это.

**Почему backend:** DeepL прямо указывает, что вызовы из браузерных приложений блокируются CORS; ключ не должен попадать в frontend. [DeepL Help](https://support.deepl.com/hc/en-us/articles/9773914250012-About-DeepL-API)

## 3. Запрос и хранение результата

Следующий DTO — **предложение для перевода существующего сообщения**, не маршрут, найденный в реализации. Игорь связывает его с реальной message/channel model и тем же общим backend-сервисом либо предлагает совместимый контракт. Нельзя молча заменить существующий text-only admin preview этим DTO. Для unsent draft сохраняется отдельная text-only точка общего сервиса с обычными server guards; provider языки/ID/секреты не выводятся во frontend. Для оригинала и результата при Send применяется существующий `ChatV2MessageForm`/send path; translation preview сам по себе Send не вызывает.

```text
POST /messages/{messageId}/translations
{
  "targetLanguage": "en",
  "mode": "on_demand" | "auto_incoming"
}
```

Сервер до внешнего вызова проверяет: пользователь аутентифицирован; имеет право видеть исходную реплику; `messageId` принадлежит доступному диалогу/тикету; сообщение не удалено/не скрыто от роли; target language поддерживается. Источник языка берётся в порядке: явная метка сообщения -> сохранённая языковая настройка автора -> только затем отдельный разрешённый detection. Автоопределение не подменяет язык, если сервис сообщил низкую уверенность.

Рекомендуемые поля связанного результата после технической сверки. Не создавать новую таблицу/ledger автоматически: исходное сообщение уже каноническое, а текущий preview transient. Требование карточки сохранить оригинал не равно требованию сохранять каждый предпросмотр. Persistence, retention и cache/version policy должны быть согласованы и привязаны к существующему storage; для черновика результат остаётся transient до обычного разрешённого Send.

| Поле | Назначение |
| --- | --- |
| `message_id` + `message_version`/`source_content_hash` + `target_language` | уникальность результата сохранённой реплики; для unsent draft ID не выдумывается |
| `source_language`, `provider`, `provider_model` | воспроизводимость и контроль качества |
| `translated_text` | проекция, доступная лишь тем же ролям, что и оригинал |
| `status` | `pending`, `ready`, `failed`, `unsupported` |
| `attempt_count`, `created_at`, `completed_at` | диагностика без содержания сообщения |
| `source_content_hash`/`message_version` | не показывается клиенту; защищает от выдачи перевода после изменения исходника |

Не писать исходный или переведённый текст в application logs, exception traces, metrics, очередь retry или админский аудит. В аудит попадают только actor, `messageId`, provider code, language pair, статус/код ошибки и время. Результат удаляется/скрывается вместе с исходной репликой по принятому правилу хранения.

## 4. Fallback и ошибки

1. Авторизовать допустимый источник; получить/заблокировать один result key для `messageId + message_version + targetLanguage`. У собственного draft — отдельный transient key/version без создания реплики; он не даёт права переводить чужой объект.
2. Вызвать выбранный primary с коротким server-side timeout и ограничением размера текста по документации провайдера.
3. Fallback допустим только при транзиентной ошибке: network timeout, 429, 5xx или объявленной недоступности. Перед fallback перепроверить, не готов ли исходный запрос.
4. Не fallback автоматически при 4xx из-за невалидного запроса, запрете доступа, неподдерживаемом языке или правовой блокировке. Вернуть нейтральный статус и не пробовать случайно другой сервис.
5. При успехе одного провайдера остановить цепочку; не отправлять один текст всем трём «для проверки».
6. После исчерпания согласованного бюджета попыток отметить `failed`, сохранив оригинал доступным. Кнопка Retry запускает новый контролируемый запрос с тем же ключом результата, а не новую реплику чата. SDK retry не должен незаметно обходить этот бюджет. При позднем ответе первичного провайдера winner/result связывается с актуальной версией; поздний результат не заменяет чужой/изменённый draft или уже выбранный перевод. Серверная идемпотентность не доказывает exactly-once внешнего вызова или списания: после timeout провайдер мог обработать запрос. Это проверяется/учитывается отдельно, без обещания нулевого двойного расхода.

Fallback не является аварийным экспортом персональных данных: список разрешённых провайдеров включается только после оценки DPA, региона обработки, billing и правовой модели MakTaro.

## 5. UI и доступ

- У получателя есть исходный текст и явный control «Показать перевод». При успехе видны язык и provider-neutral подпись «машинный перевод».
- Переведённый текст не отправляется от лица автора, не заменяет оригинал и не влияет на цензуру/оплату/статус консультации.
- Если у роли нет доступа к исходной реплике, она не получает ни перевод, ни metadata о её существовании.
- Support сейчас не исполняется. После снятия паузы нужны отдельно согласованные допустимые источники и server scope для клиентской/participant ленты; право читать internal не даёт автоматического разрешения отправить заметку внешнему провайдеру. Сторонний Support не получает перевод чужой консультации. Запрет для `service_session.internal_comment` сохраняется независимо от роли.
- При обработке provider error не показывать имя провайдера, request ID, исходный текст или внутреннюю причину клиенту.

Support-часть T02/T03/T05/T08 остаётся held_by_user.

## 8. Пакет от Игоря и открытое решение

**До реализации:** Игорь указывает каждый реальный message/channel model, место вызова после проверки прав, secret store, лимиты/очередь, точные fallback-коды, доступные языковые пары, способ удаления и observability без текста. Ключи создаёт владелец аккаунта по отдельной процедуре; их не передают в чат.

**Вопрос Заказчику после технической и юридической сверки:** подтвердить default `on_demand` (рекомендация PM) либо включать auto-translation для входящих сообщений. Первый вариант минимизирует передачу личных текстов, стоимость и неверные переводы; второй быстрее для пользователя, но увеличивает обработку, расход и риск ошибочного перевода.

**Готовность карточки:** подготовлена source-сверка и уточнён рабочий проект интеграции; карточка не принята. Фраза «все три API подключены» допустима только после T01–T10 на известной сборке с проектным opaque wrapper, разрешёнными тестовыми данными/ролями, согласованным бюджетом и реальными provider receipts. Support пауза сохраняется; его NOT_RUN нельзя заменить общим PASS чата.
