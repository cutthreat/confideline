# Confideline QA Expert Testing Standard

## Цель

Каждый тест должен давать Игорю воспроизводимый дефект или Алексею доказанный PASS. Формулировки `не доказано`, `частично`, `ограничение`, `нужен второй пользователь` считаются не финальным результатом, а recheck-долгом.

## Обязательный минимум

1. Проверять фактический Yii2 flow: PHP view, AssetBundle JS, form submit/AJAX, CSRF, method POST/GET.
2. Перед кликом фиксировать before-state, после действия фиксировать after-state.
3. Для user-to-user действий проверять обе стороны: отправитель и получатель.
4. Для media/moderation не делать вывод только по admin queue. Нужна пользовательская видимость: автор и второй пользователь.
5. Для crop/modal/upload ждать readiness markers компонента, а не таймеры вслепую.
6. Для лимитов уменьшать лимит до 1-2, делать попытки сверх лимита и проверять, дошло ли действие до получателя.
7. Для действий с побочным эффектом предусматривать rollback или явно фиксировать, что состояние изменено намеренно.
8. Браузерная автоматизация должна идти в отдельной изолированной сессии: `chromium.launch(...)` + свой `storageState`/контекст. Подключение к общему CDP-браузеру допустимо только как явный диагностический режим через отдельный env-флаг, потому что текущие вкладки пользователя или других проектов могут испортить доказательство.
9. Публичный каталог должен показывать только актуальные источники правды в основном списке. Старые отчеты остаются доступны, но только как `АРХИВ` с указанием, каким новым отчетом они заменены.
10. Для финальных `FAIL/WARN` evidence screenshots должны иметь аннотацию: цветной статус, стрелка/рамка на проблемной области и короткая подпись, почему скрин является доказательством.

## Статусы

- `PASS`: поведение доказано end-to-end.
- `FAIL`: дефект воспроизведен, есть факт, ожидание, шаги, зона кода/UI.
- `WARN`: риск или UX debt доказан, но пользовательский функциональный FAIL не доказан.
- `RETEST`: старое доказательство неполное или неверное; нужен новый проход.
- `INVALID`: старый вывод нельзя использовать.

## Запрещено

- Называть багом route inventory без пользовательского сценария.
- Называть moderation bug по одной admin media queue.
- Называть limitation то, что можно снять выбором чистого пользователя, корректным CSRF/POST или ожиданием готовности JS-компонента.
- Оставлять live-сущности измененными после теста, если есть безопасный rollback.
- По умолчанию подключаться к общему `127.0.0.1:9224` CDP-браузеру для QA-проходов Confideline. Это может смешать Confideline с чужими активными вкладками и сделать evidence невалидным.

## Формат отчета

Каждый отчет должен содержать:

- Что тестировал.
- Что получил.
- Как воспроизвести.
- Что ожидалось.
- Где смотреть Игорю.
- Evidence: скриншот, network/server response, DOM/model state, author/viewer proof.
- Что не доказано и какой следующий recheck нужен.

## UX/UI минимум отчета

- Единый шаблон и общий CSS вместо разного inline CSS для каждого нового отчета.
- Длинные ID, URL, статусы и подписи должны переноситься и не ломать карточки/таблицы.
- В начале отчета должен быть явный статус и дата.
- В старом отчете, который больше не является source of truth, должен быть banner `ARCHIVE / replaced by ...`.

## BA фиксация по пути

Каждый существенный QA-проход должен оставлять не только баг-репорт, но и BA-след:

1. Что бизнес-логика должна делать по ТЗ.
2. Какой фактический пользовательский flow был проверен.
3. Где ТЗ подтверждено, где поведение расходится, а где нужен product decision.
4. Какие роли затронуты: автор, получатель, второй пользователь, админ, владелец группы.
5. Какой before/after state доказывает вывод.
6. Что Игорь должен чинить, а что Алексей может считать рабочей частью продукта.
7. Какой rollback выполнен или какое live-состояние намеренно оставлено.

BA-запись считается достаточной только если следующий человек может по ней понять:

```text
зачем проверяли -> какое правило продукта проверяли -> что доказано -> что делать дальше
```

## Learning / skill write-back

После каждого прохода, где найден новый класс ошибки, ложный старый вывод или слабое место тестового контура, нужно обновить durable knowledge:

- добавить запись в `qa-ba-autonomous-tester/reports/full-site-testing-ledger-2026-05-08.md`;
- если правило повторяемое, обновить этот standard или профильный playbook в `.ops/docs/playbooks`;
- если правило должно включаться автоматически в будущих задачах, обновить или создать skill;
- записать lesson через `.ops/learning/record-lesson.ps1`;
- при необходимости вынести старый отчет в архив и указать новый source of truth.

Минимальная формула lesson:

```text
trigger -> risk -> rule -> verification -> stop condition
```

Пример:

```text
Если stories тестируется по moderation mode, сначала доказать создание story и author-side carousel.
Только после этого проверять second-user visibility.
Admin media queue не является доказательством пользовательской публикации.
```

## Не закрывать как финал

Следующие формулировки нельзя оставлять финальным результатом без recheck backlog:

- `нужен второй пользователь`;
- `частично`;
- `не доказано`;
- `ограничение`;
- `скрипт не смог`;
- `похоже`;
- `на скрине видно что-то похожее`;
- `надо проверить Игорю`.

Если это появляется, тестер обязан либо создать условия для полного теста, либо оформить четкий `RETEST/WARN/product decision` с причиной, почему сейчас полный тест невозможен.
