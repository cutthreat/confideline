Справочник permission keys и scope-надстроек

В live-форме ролей найдено 93 permission values. В матрице теперь разделены реальные ключи админки и проектные backend-ограничения. Это важно: нельзя писать scoped chat assigned как будто это существующий ключ роли.

Открыть справочник

users-agent

Статус: есть в live permissions. Техническое право агентского пользовательского контура. Не заменяет проверку assigned expert ids.

chief_under-view

Статус: есть в live permissions. Дает просмотр связки агент -> экспертные анкеты. Должен дополнительно проверять own scope по текущей сессии.

messages-all

Статус: есть в live permissions. Крупное право на сообщения. Для agent опасно без backend-фильтра assigned sessions.

chat-all

Статус: есть в live permissions. Крупное право на chat workspace. Для agent опасно без canViewConversation.

scoped chat assigned

Статус: не найдено в live permissions. Это backend scope rule: агент видит только assigned conversations/sessions.

backend-scope

Статус: не permission key. Это архитектурное правило: роль проверяется вместе с конкретным объектом доступа.

Правильная формулировка для программиста

Выдать существующие keys users-agent и chief_under-view. messages-all/chat-all разрешать роли agent только при обязательном backend scope. Если команда хочет видеть assigned-only доступ в UI ролей, добавить новые granular permissions.

Что такое эталон ролей

Эталон — это ожидаемое поведение роли до практического тестирования. Он нужен, чтобы программист понимал, кому какую роль выставлять, а тестировщик сравнивал live-факт с заранее зафиксированным ожиданием.

Открыть полный эталон GitHub panel

Для программиста

  • Выставлять только существующие роли.
  • Если permission слишком широкий, добавлять backend-фильтр.
  • Не считать меню защитой.
  • Логировать sensitive actions: actor, role, action, target, timestamp.

Для тестировщика

  • Проверять allow-действия.
  • Проверять deny через прямые URL.
  • Сверять факт с эталоном.
  • Ставить PASS, FAIL, WARN или RETEST_AUTH_REQUIRED.

Критический дефект

  • agent видит unassigned expert/chat/session.
  • agent открывает settings/roles/payment/logs/pages.
  • support/payment видят global transcript без case.
  • content может редактировать raw PHP без защиты.

Готовность роли

  • Есть валидная тестовая учетная запись.
  • Allow-тесты пройдены.
  • Deny-тесты пройдены прямыми URL.
  • Row-level scope доказан.
  • Нет критических FAIL.

Почему не добавляем новые роли

Live-страница уже содержит 11 ролей и назначение через Admin[role_id]. Поэтому ТЗ должно требовать настройки существующих ролей, а не новой терминологии.

Почему Агент — главный риск

У agent уже есть messages-all и chat-all. Для платного сервиса это безопасно только при жесткой серверной фильтрации по назначенным экспертным анкетам.

Почему support не равен модератору

Поддержке нужны доказательства по конкретному заказу: SLA, статус оплаты, обращение, transcript по причине. Ей не нужен глобальный просмотр всех консультаций.

Почему content отделен от raw PHP

Live-форма прямо предупреждает, что право страниц позволяет редактировать raw PHP. Значит, контентные страницы и технический raw PHP должны быть разными правами.

Почему роли распределяются по процессам

Support, финансы, content и модерация решают разные задачи. Если смешать их в одной широкой роли, будет невозможно понять, кто отвечал за чат, возврат, баланс или raw PHP.

Почему root нужно минимизировать

super-admin с All нужен для владения и аварийного доступа. Для ежедневной работы чаты, деньги, роли, настройки и raw PHP должны расходиться по более узким ролям.

Продуктовая логика платного чата

Клиент выбирает экспертную анкету, оплачивает текстовый разбор, отправляет вопрос, получает ответ через назначенного агента, после чего система хранит transcript, SLA, follow-up и support/refund evidence. Каждая роль получает только нужный кусок процесса.

Отвергнутые варианты

  • Не создаем новые роли поверх 10 ролей в ТЗ: это усложнит систему без пользы.
  • Не оставляем agent с глобальным чатом без backend-scope: это риск чужих клиентов и чужих анкет.
  • Не даем support глобальную переписку: доступ должен быть по обращению и причине.
  • Не даем content raw PHP: риск подтвержден live-формой.

1. Scope для agent

  • Маршруты агента берут текущего пользователя из сессии, а не request userId.
  • Чаты, пинги и анкеты режутся через chief_under.
  • Чужой userId или expertId дает 403 или пустую выборку.

2. Наполнить пустые роли

  • support: обращения, заказ, reason-доступ к transcript.
  • support-moder: эскалации и спорные возвраты.
  • content-moder: безопасный контент без raw PHP.
  • payment-moderator: платежи и возвраты по workflow.
  • user-moderator: жалобы, блокировки, проверки.

3. Разделить опасные права

Нужны отдельные granular-права: чат назначенных анкет, отправка сообщения от назначенной анкеты, чтение transcript по обращению, согласование возврата, evidence export, raw PHP, юридическое согласование, AI-резюме.

4. Доработать UI ролей

В `/en/admin/settings/role` показывать не только ключи, но и русское пояснение: что роль может, какие риски несет, какие права опасные, какие ограничения обязательны для платного чата.

Что проверено сейчас

  • Deep admin crawl: 54/54 live admin routes под super-admin.
  • Settings dictionary: 207 fields.
  • Controller map: 23 admin controllers.
  • /en/admin/settings/role: 11 существующих ролей.
  • Kristy baseline: 5/5 URL под super-admin, ids валидны.
  • Матрица показывает целевое распределение, а не текущие назначения.

Риски

  • agent имеет messages-all и chat-all; без backend-scope это опасно.
  • Несколько ролей существуют, но пустые.
  • admin в live-таблице не равен автоматически super-admin.
  • Raw PHP риск подтвержден текстом live-формы.
  • Нужно проверить effective-доступ каждой роли.
