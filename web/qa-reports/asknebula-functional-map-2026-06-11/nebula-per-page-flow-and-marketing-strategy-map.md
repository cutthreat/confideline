# Nebula per-page flow and marketing strategy map

Дата: 2026-06-11

Источник: публичный QA-проход askNebula.com и перенос логики на Nebula/Confideline.

## Цель документа

Для каждой будущей страницы Nebula описать все ключевые flow:

- пользовательский flow;
- conversion flow;
- backend/data flow;
- money flow;
- support/refund flow;
- notification flow;
- analytics/KPI flow;
- QA flow;
- маркетинговая стратегия и логика страницы.

Этот документ нужен, чтобы Oracle-верстка не стала просто красивым макетом. Каждая страница должна иметь понятную роль в продукте, backend-данные, события аналитики, маркетинговый смысл и проверяемый сценарий.

## Общая логика askNebula, которую переносим

askNebula ведет клиента не сразу в оплату, а через доверительную воронку:

витрина -> оффер free minutes / discount -> тема проблемы -> тип чтения -> optional birth data -> подбор экспертов -> карточка эксперта -> Start Free Chat / Start chat -> регистрация / чат / деньги.

Для Nebula это переводится так:

витрина -> выбор темы или эксперта -> вопрос клиента -> условия консультации -> карточка консультации -> чат -> поминутные списания -> support/refund -> отзыв -> аналитика качества.

## Страница 1. Главная / витрина

### Роль страницы

Главная должна за 10-20 секунд объяснить клиенту: это поминутные эзотерические консультации с живыми экспертами, можно начать с понятного оффера, выбрать эксперта или пройти подбор.

### User flow

1. Клиент попадает из рекламы, SEO, соцсетей или прямой ссылки.
2. Видит понятный оффер: консультация с экспертом, цена/мин, стартовый бонус или бесплатные минуты.
3. Понимает направления: таро, астрология, нумерология, отношения, карьера, духовное руководство.
4. Видит несколько экспертов и доверительные сигналы.
5. Выбирает: пройти подбор, открыть каталог или начать чат с конкретным экспертом.

### Conversion flow

- Primary CTA: `Начать консультацию` / `Получить первые минуты`.
- Secondary CTA: `Выбрать эксперта` / `Пройти подбор`.
- Не вести холодного клиента сразу в оплату, если он еще не понял продукт.

### Backend/data flow

- Подтянуть список экспертов.
- Подтянуть статусы доступности.
- Подтянуть цену за минуту.
- Подтянуть рейтинг/отзывы, если они уже есть.
- Подтянуть промо-условия: free minutes, discount, bonus.

### Money flow

- На главной показываем только понятные условия: цена от/за минуту, есть ли бесплатные минуты, что списание идет только во время консультации.
- Не раскрываем сложные расчеты начислений агенту/эксперту.

### Support/refund flow

- На главной должен быть быстрый доступ к FAQ, правилам, дисклеймеру и support.
- Не нужно грузить клиента юридическим текстом в hero, но условия должны быть доступны до старта.

### Notification flow

- На главной уведомлений нет.
- Нужны только согласия/баннеры, если есть cookies/marketing tracking.

### Analytics/KPI flow

- `page_view_home`;
- `hero_cta_click`;
- `expert_card_click`;
- `quiz_start_click`;
- `catalog_click`;
- `pricing_block_view`;
- `trust_block_view`.

### Marketing strategy

Главная продает не “чат”, а понятную помощь: ясность, поддержка, быстрый ответ, живой эксперт. Главное обещание должно быть честным: не “гарантируем судьбу”, а “помогаем разобраться через эзотерическую консультацию”.

### QA acceptance

- Клиент понимает, что покупает.
- Видны цена/мин или стартовые условия.
- CTA ведет в подбор/каталог/старт консультации.
- Нет чужих цифр askNebula.
- Все экспертные блоки динамические или явно временные.

## Страница 2. SEO / категории консультаций

### Роль страницы

Приводить клиента по конкретному намерению: таро, астрология, любовь, отношения, карьера, бесплатная консультация, дешевый старт, psychic chat analog.

### User flow

1. Клиент приходит из поиска или рекламы по конкретной теме.
2. Видит страницу, которая отвечает именно на его запрос.
3. Понимает, какие эксперты подходят под тему.
4. Переходит к подбору или конкретным экспертам.

### Conversion flow

- Primary CTA: `Подобрать эксперта по теме`.
- Secondary CTA: `Смотреть экспертов`.
- Для страниц free/cheap: CTA должен объяснять условия, а не обещать невозможное.

### Backend/data flow

- Категория консультации.
- Список экспертов, связанных с категорией.
- SEO-текст / контент.
- FAQ по теме.
- Цена/мин и промо-условия.

### Money flow

- Для коммерческих страниц показывать: цена за минуту, free minutes, скидка или стартовый бонус.
- Для “free” страниц обязательно объяснить, что бесплатно ограничено минутами/условиями.

### Support/refund flow

- Ссылки на правила и дисклеймер.
- FAQ по ожиданиям от консультации.

### Notification flow

- Нет прямых уведомлений.

### Analytics/KPI flow

- `seo_page_view`;
- `topic_cta_click`;
- `expert_from_topic_click`;
- `quiz_start_from_topic`;
- `topic_to_chat_conversion`.

### Marketing strategy

Категорийные страницы нужны для SEO и рекламных связок. Каждая страница должна говорить языком боли клиента: “отношения”, “карьера”, “неопределенность”, “быстрый вопрос”, “первый раз хочу попробовать”.

### QA acceptance

- Страница не выглядит как общий шаблон.
- Есть релевантные эксперты.
- Есть CTA в подбор/каталог.
- Условия free/cheap не вводят в заблуждение.

## Страница 3. Каталог экспертов

### Роль страницы

Дать клиенту возможность выбрать эксперта вручную.

### User flow

1. Клиент открывает каталог.
2. Видит список экспертов.
3. Фильтрует по теме, цене, доступности, рейтингу, языку.
4. Открывает карточку эксперта или сразу стартует консультацию.

### Conversion flow

- Primary CTA на карточке: `Начать чат`.
- Secondary CTA: `Подробнее`.
- Для холодного клиента можно вести в quiz, если он не знает, кого выбрать.

### Backend/data flow

- Эксперт ID.
- Имя/псевдоним.
- Фото.
- Статус online/offline/available soon.
- Цена/мин.
- Рейтинг.
- Отзывы.
- Количество консультаций.
- Специализации.
- Языки.
- Агент, если эксперт обслуживается агентом.

### Money flow

- Цена/мин видна до клика.
- Если есть free minutes, карточка должна показать, применимы ли они к этому эксперту.

### Support/refund flow

- Непрямой: каталог должен вести к правилам консультации и дисклеймеру через footer/FAQ.

### Notification flow

- Нет прямых уведомлений.
- Можно заложить P1: уведомить клиента, когда offline-эксперт будет доступен.

### Analytics/KPI flow

- `catalog_view`;
- `filter_used`;
- `expert_card_view_from_catalog`;
- `start_chat_from_catalog`;
- `sort_used`;
- `no_results`.

### Marketing strategy

Каталог должен снижать тревогу выбора. Основные trust-сигналы: экспертность, цена, отзывы, опыт, доступность, понятные направления.

### QA acceptance

- Нет “мертвых” карточек.
- Фильтры меняют список.
- Цена и статус не противоречат карточке эксперта.
- CTA ведет в старт консультации или авторизацию/quiz с сохранением выбранного эксперта.

## Страница 4. Карточка эксперта

### Роль страницы

Убедить клиента, что конкретному эксперту можно доверить вопрос.

### User flow

1. Клиент открывает карточку из каталога/главной/quiz.
2. Смотрит специализацию, опыт, методы, отзывы, цену.
3. Понимает ограничения и стиль работы эксперта.
4. Нажимает `Начать чат` или возвращается к каталогу.

### Conversion flow

- Primary CTA: `Начать консультацию`.
- Если есть free minutes: `Начать с бесплатных минут`.
- Secondary CTA: `Задать вопрос` / `Вернуться к экспертам`.

### Backend/data flow

- Профиль эксперта.
- Направления.
- Tools/methods.
- Опыт.
- Количество консультаций.
- Рейтинг/отзывы.
- Цена/мин.
- Статус допуска.
- Доступность.
- Агент-владелец анкеты.
- Claims moderation status.

### Money flow

- Клиент видит стоимость минуты до старта.
- При старте создается консультация с зафиксированной ценой.
- Если действует promo/free minutes, оно применяется к этой консультации.

### Support/refund flow

- На карточке должны быть правила и дисклеймеры через ссылку.
- После консультации отзывы/жалобы связываются с экспертом и конкретной консультацией.

### Notification flow

- Если эксперт offline: P1 уведомление о доступности.
- Если клиент начал консультацию: уведомление эксперту/агенту.

### Analytics/KPI flow

- `expert_profile_view`;
- `expert_cta_click`;
- `expert_review_view`;
- `expert_price_view`;
- `expert_to_chat_start`;
- `expert_profile_bounce`.

### Marketing strategy

Карточка эксперта продает доверие. Нельзя перегружать мистическими обещаниями. Нужны честные сигналы: чем помогает, с какими темами работает, какой опыт, что говорят клиенты, сколько стоит минута.

### QA acceptance

- Цена есть.
- CTA виден.
- Reviews не фейковые или промаркированы как тестовые.
- Claims модерируются.
- Статус эксперта не противоречит возможности стартовать чат.

## Страница 5. Quiz / подбор эксперта

### Роль страницы

Помочь клиенту, который не знает, какого эксперта выбрать, и собрать первичный контекст консультации.

### User flow

1. Клиент нажимает `Try now` / `Начать`.
2. Отвечает на короткие вопросы.
3. Выбирает тему: любовь, карьера, путь, будущее, духовное руководство.
4. Выбирает тип чтения: таро, нумерология, астрология и т.д.
5. При необходимости вводит дату рождения.
6. Видит подобранных экспертов.
7. Переходит к старту консультации.

### Conversion flow

- Каждый шаг должен быть коротким.
- Нельзя требовать регистрацию слишком рано, если можно сначала показать ценность.
- Результат quiz должен вести к экспертам, а не в тупик.

### Backend/data flow

- Quiz session ID.
- Ответы клиента.
- Matching rules.
- Recommended experts.
- Сохранение выбранного эксперта.
- Возможность создать консультацию на основе quiz.

### Money flow

- На финальном шаге показать free minutes / цену/мин.
- Не списывать деньги до явного старта консультации.

### Support/refund flow

- Нет прямого support, но правила и disclaimer должны быть доступны до старта.

### Notification flow

- Нет внешних уведомлений.
- После выбора эксперта может создаваться internal event для analytics.

### Analytics/KPI flow

- `quiz_start`;
- `quiz_step_completed`;
- `quiz_abandoned`;
- `quiz_completed`;
- `recommended_expert_view`;
- `start_chat_from_quiz`.

### Marketing strategy

Quiz снижает страх выбора и повышает конверсию холодного трафика. Это особенно важно для рекламы: человек может не знать “таролог или астролог”, но знает свою проблему.

### QA acceptance

- Каждый шаг понятен без объяснений.
- Можно завершить quiz без технического тупика.
- Рекомендации не пустые.
- Выбранная тема передается дальше в консультацию.

## Страница 6. Старт консультации

### Роль страницы

Финальная точка перед чатом: клиент понимает условия и фиксирует вопрос.

### User flow

1. Клиент приходит из эксперта, каталога или quiz.
2. Видит выбранного эксперта/агента.
3. Пишет вопрос или подтверждает ранее введенную тему.
4. Видит цену/мин и условия.
5. Подтверждает disclaimer.
6. Нажимает `Начать чат`.

### Conversion flow

- Primary CTA: `Начать чат`.
- Если баланс нулевой, CTA ведет к free minutes или пополнению.
- Если эксперт недоступен, предложить другого эксперта или ожидание.

### Backend/data flow

- Создание карточки консультации.
- Привязка клиента.
- Привязка эксперта/агента.
- Сохранение вопроса.
- Фиксация цены/мин.
- Согласие с условиями.
- Стартовый статус: draft / ready_to_chat / waiting_payment / active.

### Money flow

- Проверить баланс/free minutes.
- Не списывать до старта активного чата.
- Зафиксировать цену, чтобы она не изменилась в процессе.

### Support/refund flow

- Условия возврата доступны до старта.
- Если клиент отменил до начала, не должно быть списания.

### Notification flow

- Клиент: консультация создана.
- Эксперт/агент: новый запрос.
- Админ: только для проблемных или manual review кейсов.

### Analytics/KPI flow

- `consultation_start_page_view`;
- `question_entered`;
- `terms_accepted`;
- `start_chat_click`;
- `payment_required`;
- `consultation_created`.

### Marketing strategy

Эта страница должна убрать последний страх: “что будет после клика?”, “сколько стоит?”, “когда начнут списывать?”, “можно ли вернуть деньги?”.

### QA acceptance

- Без вопроса нельзя стартовать, если вопрос обязателен.
- Условия видны.
- Цена видна.
- После клика создается карточка консультации.

## Страница 7. Чат консультации

### Роль страницы

Главный продукт сервиса.

### User flow

1. Клиент входит в чат.
2. Эксперт или агент получает запрос.
3. Начинается активная консультация.
4. Идет поминутное списание.
5. Клиент видит баланс/минуты/статус.
6. Эксперт/агент отвечает.
7. Консультация завершается.

### Conversion flow

- Если free minutes закончились, показать мягкий переход к оплате/пополнению.
- Если баланс заканчивается, предупредить заранее.

### Backend/data flow

- service_session.
- Chat thread.
- Message events.
- Participant roles.
- Timer state.
- Balance lock/debit.
- Expert/agent assignment.
- Status: active, paused, ended, blocked, refunded.

### Money flow

- Старт списания только при активной консультации.
- Списание по минутам.
- Stop при нехватке средств.
- Начисление эксперту/агенту по правилам.

### Support/refund flow

- Из чата должна быть кнопка обращения в support.
- Жалоба привязана к конкретной консультации и сообщениям.

### Notification flow

- Новое сообщение.
- Эксперт подключился.
- Баланс заканчивается.
- Консультация остановлена.
- Консультация завершена.

### Analytics/KPI flow

- `chat_opened`;
- `first_message_sent`;
- `expert_first_response_time`;
- `paid_minute_started`;
- `balance_low_warning`;
- `chat_ended`;
- `support_from_chat`;
- `review_prompt_shown`.

### Marketing strategy

Чат должен подтверждать рекламное обещание: быстро, понятно, с живым экспертом, без ощущения обмана по деньгам. Это не просто messenger, а платная консультационная среда.

### QA acceptance

- Все роли видят свой правильный интерфейс.
- Списания соответствуют времени.
- Нельзя уйти в минус без правил.
- История сохраняется.
- Support доступен.

## Страница 8. Баланс / оплата / пополнение

### Роль страницы

Дать клиенту прозрачное понимание денег и обеспечить пополнение для продолжения консультации.

### User flow

1. Клиент видит баланс.
2. Выбирает пакет/пополнение.
3. Видит бонусы/free minutes, если есть.
4. Оплачивает.
5. Возвращается в консультацию.

### Conversion flow

- Основной CTA: `Пополнить баланс`.
- В чате: `Продолжить консультацию`.

### Backend/data flow

- Balance account.
- Transaction.
- Payment status.
- Promo/free minutes.
- Refund status.
- Accruals for expert/agent.

### Money flow

- Пополнение.
- Списание.
- Refund.
- Manual adjustment by admin.
- Commission split.

### Support/refund flow

- Любая спорная транзакция должна открывать support case.

### Notification flow

- Успешное пополнение.
- Неуспешная оплата.
- Возврат.
- Низкий баланс.

### Analytics/KPI flow

- `payment_page_view`;
- `topup_started`;
- `payment_success`;
- `payment_failed`;
- `refund_requested`;
- `refund_completed`;
- `revenue_per_session`.

### Marketing strategy

Деньги должны выглядеть прозрачно. Клиент должен понимать, что платит за минуты консультации, а не за скрытую подписку.

### QA acceptance

- Баланс читаемый.
- Условия списания понятны.
- Ошибки оплаты не ломают чат.
- Refund traceable.

## Страница 9. Support / жалоба / refund

### Роль страницы

Дать клиенту безопасный способ решить проблему и дать администратору управляемый процесс решения.

### User flow

1. Клиент открывает support из чата, кабинета или footer.
2. Выбирает причину.
3. Support автоматически связывается с консультацией.
4. Агент/админ рассматривает.
5. Клиент получает решение.

### Conversion flow

- Support не продает, но защищает доверие и снижает негатив.

### Backend/data flow

- Support ticket.
- service_session ID.
- Messages evidence.
- Refund request.
- Decision.
- Owner.
- Status.

### Money flow

- Refund full/partial.
- No refund decision.
- Manual balance correction.

### Notification flow

- Ticket created.
- Ticket assigned.
- Decision made.
- Refund completed/rejected.

### Analytics/KPI flow

- `support_ticket_created`;
- `refund_requested`;
- `refund_approved`;
- `refund_rejected`;
- `support_resolution_time`;
- `complaint_rate_by_expert`.

### Marketing strategy

Support - часть доверия. Для эзотерики важно показать: сервис не бросает клиента, есть правила и ответственность.

### QA acceptance

- Жалоба не теряется.
- Есть связь с консультацией.
- Есть решение и история.
- Refund отражается в деньгах.

## Страница 10. Личный кабинет клиента

### Роль страницы

Собрать историю клиента: консультации, баланс, support, отзывы, повторные обращения.

### User flow

1. Клиент входит в кабинет.
2. Видит активные и завершенные консультации.
3. Может продолжить чат, повторить консультацию, оставить отзыв, открыть support.

### Backend/data flow

- User profile.
- service_session list.
- Balance.
- Payment history.
- Support tickets.
- Reviews.

### Money flow

- Баланс.
- История списаний.
- Refunds.

### Notification flow

- Новые сообщения.
- Статус support.
- Баланс.
- Промо/bonus, если разрешено.

### Analytics/KPI flow

- `client_dashboard_view`;
- `repeat_consultation_click`;
- `review_submitted`;
- `support_opened_from_dashboard`.

### Marketing strategy

Кабинет удерживает клиента и ведет к повторной консультации. Основная логика: “у меня есть история, я могу вернуться к эксперту, сервис помнит мой контекст”.

### QA acceptance

- Клиент не видит чужие консультации.
- История полная.
- Повторный старт не создает дубликаты без подтверждения.

## Страница 11. Кабинет эксперта

### Роль страницы

Рабочее место эксперта для проведения консультаций.

### User flow

1. Эксперт видит новые запросы.
2. Принимает/открывает консультацию.
3. Отвечает в чате.
4. Видит SLA, статус, начисления.
5. Завершает или передает проблему.

### Backend/data flow

- Assigned service_sessions.
- Expert availability.
- Chat threads.
- SLA timer.
- Accruals.
- Quality status.

### Money flow

- Эксперт видит начисления, но не должен управлять клиентским балансом.

### Support/refund flow

- Эксперт видит жалобы по своим консультациям в ограниченном формате.
- Спор решает агент/админ.

### Notification flow

- Новый запрос.
- Новый клиентский ответ.
- SLA warning.
- Жалоба/support.
- Начисление.

### Analytics/KPI flow

- `expert_request_received`;
- `expert_first_response_time`;
- `expert_session_completed`;
- `expert_quality_score`;
- `expert_complaint_rate`.

### Marketing strategy

Экспертский кабинет напрямую влияет на обещание рекламы: если эксперт медленно отвечает, реклама сгорит. Поэтому SLA и доступность - часть маркетинга, не только операционки.

### QA acceptance

- Эксперт видит только свои консультации.
- SLA работает.
- Ответы сохраняются.
- Начисления traceable.

## Страница 12. Кабинет агента

### Роль страницы

Операторский контур для агента, который ведет несколько анкет экспертов.

### User flow

1. Агент видит назначенных экспертов.
2. Видит консультации своего контура.
3. Ведет коммуникацию, если роль агента это предполагает.
4. Эскалирует спор админу.
5. Следит за SLA и качеством.

### Backend/data flow

- Agent profile.
- Assigned experts.
- Assigned service_sessions.
- Chat access scope.
- Support tickets.
- Balance/transaction visibility only within permitted scope.

### Money flow

- Агент видит начисления/мотивацию по своему контуру.
- Агент не должен иметь полный финансовый доступ супер-админа.

### Support/refund flow

- Агент может принять/обработать обращение в своем контуре.
- Refund final decision может оставаться у супер-админа.

### Notification flow

- Новый вопрос по его эксперту.
- SLA риск.
- Жалоба.
- Решение админа.

### Analytics/KPI flow

- `agent_queue_view`;
- `agent_response_time`;
- `agent_escalation_created`;
- `agent_sessions_completed`;
- `agent_quality_issue`.

### Marketing strategy

Агентский контур нужен, чтобы масштабировать с 5 до 25 экспертов без падения качества. Для рекламы это означает способность принять больше лидов.

### QA acceptance

- Агент видит только свой контур.
- Нет лишних прав.
- Может работать без супер-админа в каждом шаге.

## Страница 13. Админ-дэшборд / операционный центр

### Роль страницы

Супер-админ видит весь сервис: консультации, деньги, SLA, support, качество, проблемы.

### User flow

1. Админ открывает дашборд.
2. Видит очереди: новые, активные, просроченные, спорные, refund, low balance, failed payment.
3. Открывает карточку консультации.
4. Принимает решение: назначить, эскалировать, вернуть деньги, заблокировать, проверить качество.

### Backend/data flow

- Все service_sessions.
- Users.
- Experts.
- Agents.
- Payments.
- Support.
- Refunds.
- Events.
- Reviews.
- QA scores.

### Money flow

- Полная видимость денег.
- Manual correction только с логом.
- Refund workflow.
- Accrual audit.

### Notification flow

- Critical alerts.
- SLA breach.
- Payment/refund issue.
- Complaint.
- Expert quality risk.

### Analytics/KPI flow

- `admin_dashboard_view`;
- `sla_breach_count`;
- `active_sessions_count`;
- `refund_rate`;
- `revenue`;
- `expert_quality_score`;
- `support_resolution_time`.

### Marketing strategy

Админ-дэшборд отвечает на вопрос “можно ли включать рекламу”. Если админ не видит проблемы, маркетинг нельзя масштабировать.

### QA acceptance

- Админ видит полный путь консультации.
- Есть очереди проблем.
- Деньги и support связаны с консультацией.
- Есть audit trail решений.

## Страница 14. Legal / правила / дисклеймеры

### Роль страницы

Защитить продукт и честно объяснить клиенту ограничения эзотерических консультаций.

### User flow

1. Клиент открывает правила из footer, start consultation или support.
2. Понимает ограничения консультации.
3. Видит refund/support policy.
4. Подтверждает условия до старта.

### Backend/data flow

- Версии документов.
- Consent timestamp.
- Consent per consultation.
- Links in service_session.

### Money flow

- Правила refund должны быть связаны с деньгами.

### Support/refund flow

- Support decisions опираются на правила.

### Notification flow

- Если правила обновились, нужны уведомления/повторное согласие для важных изменений.

### Analytics/KPI flow

- `legal_page_view`;
- `terms_accepted`;
- `disclaimer_viewed`;
- `refund_policy_viewed`.

### Marketing strategy

Legal не должен убивать конверсию, но должен снимать риск. Для эзотерики обязательно избегать медицинских/финансовых/гарантийных обещаний.

### QA acceptance

- Условия доступны до оплаты/чата.
- Версия согласия сохраняется.
- Нет противоречия между рекламой и disclaimer.

## Страница 15. Join as Expert / набор экспертов

### Роль страницы

Привлечь и отфильтровать экспертов для запуска и масштабирования.

### User flow

1. Кандидат открывает страницу.
2. Понимает требования и формат работы.
3. Заполняет заявку.
4. Проходит модерацию/обучение/допуск.

### Backend/data flow

- Expert application.
- Profile draft.
- Specializations.
- Experience.
- Documents/proof, если нужны.
- Moderation status.
- Training status.
- Activation status.

### Money flow

- Условия начислений/комиссий должны быть понятны, но детали можно давать после заявки.

### Support/refund flow

- Нет клиентского refund.
- Нужен internal support for expert onboarding.

### Notification flow

- Заявка получена.
- Нужны документы.
- Одобрено/отклонено.
- Обучение назначено.

### Analytics/KPI flow

- `join_expert_page_view`;
- `expert_application_started`;
- `expert_application_submitted`;
- `expert_approved`;
- `expert_activated`.

### Marketing strategy

Эта страница продает экспертам не клиентский продукт, а возможность работать. Для запуска нужно 5 активных экспертов, для масштабирования - pipeline до 25.

### QA acceptance

- Заявка отправляется.
- Статус заявки виден админу.
- Нельзя активировать эксперта без допуска.

## Сквозные flow, которые должны связывать страницы

### Клиентский paid consultation flow

Главная/SEO -> quiz или каталог -> карточка эксперта -> старт консультации -> чат -> списание минут -> завершение -> отзыв/support.

### Деньги flow

Промо/free minutes -> цена/мин -> старт чата -> timer -> списание -> low balance warning -> stop/topup -> начисления -> refund, если спор.

### Командный flow

Новый запрос -> назначение эксперта/агента -> SLA -> ответ -> качество -> спор/support -> админское решение -> обучение/санкция, если нужно.

### Marketing flow

Реклама/SEO -> посадочная под боль -> trust -> quiz/expert -> chat start -> paid minutes -> repeat/review -> lookalike/retargeting data.

### Analytics flow

Все страницы должны отдавать события в единую таблицу взаимодействий:

- источник трафика;
- страница входа;
- CTA;
- quiz steps;
- expert viewed/chosen;
- consultation created;
- chat started;
- paid minutes;
- support/refund;
- review;
- repeat.

## Приоритет внедрения

| Очередь | Страницы | Почему |
|---|---|---|
| P0 | Главная, каталог, карточка эксперта, старт консультации, чат, баланс, support, админ-дэшборд | Без этого нельзя принять платного клиента |
| P1 | Quiz, SEO-категории, кабинет клиента, кабинет эксперта, кабинет агента, legal pages | Нужно для конверсии, качества и масштабирования; часть legal должна быть P0 до денег |
| P2 | Rewards, расширенная библиотека контента, продвинутые калькуляторы, глубокая персонализация | Можно после базового запуска |

## Anton gate

Перед передачей в дизайн/backend по каждой странице должен быть ответ:

1. Клиент понимает, что делать дальше?
2. CTA ведет в реальное действие, а не в макет?
3. Цена/условия не скрыты?
4. Нет неподтвержденных claims?
5. Ошибки/пустые состояния описаны?
6. События аналитики определены?
7. Есть QA-сценарий?

Если по странице нет этих ответов, страница не готова к натягиванию на backend.
