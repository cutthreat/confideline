G1.2 Чат для клиента, эксперта, агента и админа

P0Цель 1: Глобальный чатSpec handoff ready / runtime open

Навигационная карточка: эта страница кратко показывает принятую логику G1.2 и не заменяет документы реализации. Открыть полное ТЗ для Игоря, контекст для Codex, каноническую сверку G1, повторную сверку HTML и контрактов архива, канонический MD бейджей, таблицу бейджей CSV и приложение production-поверхностей admin-chat. Спецификация и runtime/ACL proof не смешиваются: production-интеграция принимается только по серверным доказательствам.

Роли
  • Эксперт = публичная анкета/личность;
  • Агент = внутренний человек, ведущий назначенные анкеты;
  • модератор выполняет support-функции;
  • клиент не видит Агента.
Путь пользователя
  • клиент бесплатно и асинхронно общается с Экспертом;
  • клиент создаёт запрос или принимает предложение Эксперта;
  • paid session создаётся только после явного подтверждения клиента;
  • после завершения диалог возвращается в бесплатный режим;
  • недоступный Эксперт: выбрать другого или запросить уведомление через G1.4; платной очереди нет.
Данные и правила
  • один постоянный диалог для пары клиент + Эксперт;
  • каждая платная консультация — отдельная session внутри диалога;
  • Агент видит только назначенную пару без контактов, платежных данных и внутренних ID;
  • точный баланс: client и super-admin; Agent получает только operational signal;
  • внутренний audit хранит реального автора, роль, assignment и версию правила.
Сообщения MVP
  • текст, системные сообщения, emoji, изображения и документы;
  • аудио, видео и произвольные файлы запрещены;
  • Эксперт может редактировать с edited marker и сохранением прошлой версии;
  • staff может только скрыть запрещённый контент с причиной и audit.
Настройки чата
  • максимальная длина сообщения и rate limit;
  • attachment/document policy, censorship categories, allowlist, replacement label и version/audit;
  • in-chat templates/system messages и client-visible delivery/edit/censorship outcomes;
  • hide-message reason dictionary;
  • typing/delivered/read не влияют на credits;
  • шаблоны и AI — только редактируемые подсказки, автоматическая отправка запрещена.
Бейджи: область действия
  • chats_* показываются только в Chats, pings_* — только в Pings;
  • Paid = любой подтверждённый исторический top-up кошелька клиента;
  • PP = текущий checkout/top-up, пока он не завершён;
  • Coupon = фактически выданный действующий bonus/compensation grant;
  • Live остаётся при pause/reconnect; первое сообщение клиента сразу создаёт Chats с Reply.

Место в админ-панели
  • страница «Настройки чата»;
  • route: /ru/admin/settings/chat;
  • в существующем списке /ru/admin/settings/index;
  • сразу после «Основные настройки» и перед «Настройки фото»;
  • MVP-доступ только для super-admin;
  • assignment/RBAC, prices/payments, reconnect/session timers, consultation end reasons, history retention, global photo limits, premium dating-message settings, email templates, message monitoring, support и logs здесь не дублируются.
Цензура контактов
  • проверка действует для клиента и Агента;
  • отправитель видит original и policy warning;
  • получатель видит запрещённые фрагменты как «ЦЕНЗУРА»;
  • каждая попытка попадает в существующий операционный контур «Сообщения»;
  • MVP-просмотр попыток и originals — только super-admin;
  • для consultation message вместо physical delete доступно только hide с причиной/audit;
  • категории можно включать и выключать в админ-панели с version/audit.
Связь и SLA
  • G1.2 получает из G1.3/G6 reconnect, technical end и SLA facts;
  • чат не считает deadline, не завершает session и не выдаёт компенсацию сам;
  • client grace — отдельные управляемые 60 секунд без новой paid minute;
  • при SLA failure уже начатая минута завершается, следующая не начинается, создаётся incident;
  • retry и realtime-доставка не создают дубли.
Завершение и история
  • G1.3 владеет lifecycle и причинами завершения, а чат отображает разрешённый server snapshot;
  • все сообщения находятся в постоянном dialogue;
  • в «Историю консультации» попадают сообщения и системные события связанной session;
  • в MVP история клиента read-only, без скачивания/export;
  • retention задаётся в G1.3/G4.3, предварительное значение 24 месяца, до legal/privacy review.
Проверка
  • клиент видит только Эксперта и safe content;
  • Агент не открывает чужие анкеты и не отправляет от неназначенной анкеты;
  • super-admin видит полный audit, restricted censorship evidence и причины emergency actions;
  • moderator/emergency super-admin видны клиенту как «Поддержка Nebula».
Операторские поверхности handoff
  • attachments pre-upload/scan; voice/audio остаются запрещёнными;
  • AI Refresh/Use draft без auto-send;
  • private Notes, Follow, Assign, Note, Resolve;
  • Pay/package card, compact/sound preferences и keyboard shortcuts;
  • подробные backend-контракты находятся в приложении для Codex.

Макет: рабочий чат по ролям

Клиент: free dialogue → consultation request Агент: одна active paid/pause session Эксперт: виден клиенту Поддержка Nebula: отдельное авторство
Левая колонка чата
  • номер консультации и статус;
  • роль и доступный контекст зависят от actor;
  • server status, timer и цена — только в разрешённом scope;
  • Agent видит operational balance signal, client — свой баланс, super-admin — точные данные/audit;
  • SLA/risk-индикаторы внутренние и не показываются клиенту.
Основное окно
  • сообщения клиента и эксперта/агента;
  • внутренняя заметка не видна клиенту;
  • кнопки макета: ответить; Offer/Start paid session; Pause/Resume/Complete по snapshot G1.3; AI Refresh/Use draft; Notes/Follow/Pay; support route;
  • Copy history в MVP доступен только super-admin; позднее право выдаётся staff через существующие permissions: копируется recipient-safe текущий контекст, без private notes, hidden original, payment/internal IDs и client export; действие журналируется;
  • сообщения сохраняются в permanent dialogue, а session history показывает только связанные сообщения и события.
Статус доказательств: статический макет подтверждает только UI-модель. Исторический runtime-срез разделяет клиентское сообщение, ответ Эксперта и внутреннюю заметку, но найденный доступ к чужой анкете по прямому URL остаётся незакрытым ACL-gate. Production-ready статус возможен только после server-side RBAC, persistence, idempotency, censorship, audit и role-scoped readback proof.
