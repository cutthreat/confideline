Developer start guide for email templates

This is the primary entry point for implementation. English is the main product language. Russian templates remain in the package only as a second localization and for easier review by the product owner.

Main rule: a value in the admin dropdown is not proof that the email can be sent. For each template, confirm the backend event, render payload, queue-binding, delay rules, and cancellation/suppression logic.

Implementation route

Start with the file structure

Open File structure. Every scenario has one folder with two language folders: en/ and ru/.

Find the real EmailTemplate mechanism

Confirm the model/table, language storage, fields, queue, delay handling, and event binding in the current codebase.

Update existing live templates first

Start with registration and email confirmation because they already exist and are easiest to render-test safely.

Do not fake missing backend events

If an event or variable is missing, implement the backend first instead of importing a nice-looking but non-working template.

Render-test both languages

English is primary. Russian is a second localization. Both must render without empty links, undefined variables, or broken Handlebars blocks.
