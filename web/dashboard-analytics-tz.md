# ТЗ: аналитический дашборд для Confideline

## Результат
- В админке есть дашборд под эзотерические консультации в живом текстовом чате с поминутной оплатой.
- Экран реализован на существующем админском стеке YouDate/Yii2, без нового UI-фреймворка.
- Разработчик может натянуть бекенд-данные без потери структуры, блоков, метрик и логики чтения экрана.

## Источник правды
- Активный файл:
  - `Chat/youdate-2.0.2-yii2/Source/youdate_extracted/application/modules/admin/views/default/index-admin.php`
- Архивные версии:
  - `index-admin-v1.php`
  - `index-admin-v2.php`
  - `index-admin-v3.php`
- Визуальные артефакты для передачи:
  - `web/dashboard-analytics-mockup.html`
  - `web/dashboard-analytics-spec.html`

## Область задачи
- Только консультации / эзотерика.
- Только живой текстовый чат.
- Только модель `free -> first paid -> repeat`.
- LTV вынесен в отдельный слой, а не встроен в основную воронку.
- Используются только существующие админские компоненты YouDate/Yii2:
  - `box`
  - `info-box`
  - стандартные таблицы
  - `ChartJs`

## Технический стек и ограничения
- Боевой дашборд в админке строится на текущем стеке `Yii2 + yii\\bootstrap + AdminLTE 2`.
- Основа админских ассетов подключается через:
  - `application/modules/admin/assets/AdminAsset.php`
  - `admin.min.css`
  - `adminlte.min.js`
- Внутри боевого дашборда нельзя подменять этот стек на отдельный `Bootstrap 4.6`-layout.
- `Bootstrap 4.6` присутствует в публичной теме сайта `youdate`, но это другой контур, не источник правды для текущей админ-панели.
- Публичные страницы в `web/` являются только навигацией и ТЗ для программиста. Они не задают стек боевого файла дашборда.

## Не входит в задачу
- Любая дейтинговая логика:
  - лайки
  - мэтчи
  - подарки как ядро продукта
  - приватные фото
  - премиальные дейтинговые воронки
- Переключатель `dating / esoterics`
- Новый дизайн-системный слой поверх текущей админки

## Главная бизнес-ось
- Сколько пользователей дошло до бесплатных минут.
- Сколько пользователей перешло в первую оплату.
- Сколько пользователей вернулось в повторную оплату.
- Как эти переходы складываются в GMV и LTV.

## Контракт верстки

### 1. Верхний блок
- Заголовок `Дашборд живых консультаций`
- Системные статусы:
  - Cron
  - Очередь
  - Платежи
  - Realtime
  - Ошибки (5м)
- Информационные чипы:
  - период
  - контур
  - домен
  - почасовой cron
  - размер очереди
- Кнопки действий:
  - `Обновить`
  - `CSV`
  - `Определения`

### 2. Панель фильтров
- Период
- Гранулярность
- Сравнение
- Дата с
- Дата по
- Страна
- Тип клиента
- Кнопки `Применить` и `Сбросить`

### 3. Первый ряд KPI
- `Старт бесплатных минут`
- `Конверсия в первую оплату`
- `Доля повторных оплат`
- `GMV / чистая выручка`

### 4. Второй ряд KPI
- `Запросы на консультацию`
- `Доля принятия`
- `Медианный первый ответ`
- `Потери между бесплатным этапом и оплатой`

### 5. Порядок секций
1. `Продуктовый контур`
2. `Воронка и unit-экономика`
3. `Повторы и выручка`
4. `LTV и когорты`
5. `Драйверы роста`
6. `Риски и операционка`

Секции не переставлять без отдельного продуктового решения.

## Контракт продуктовой воронки
- `Просмотр эксперта / каталога`
- `Создан запрос на консультацию`
- `Принято экспертом`
- `Старт бесплатных минут (presales)`
- `Бесплатные минуты исчерпаны / показан экран оплаты`
- `Первая оплаченная минута`
- `Списанные оплаченные минуты`
- `Повторная платная сессия`

Для каждого шага в таблице нужны:
- название
- количество
- конверсия
- операционный смысл

## Контракт LTV
LTV не является шагом основной воронки.

Он должен жить отдельным блоком и включать:
- `LTV D7`
- `LTV D30`
- `LTV D90`
- окупаемость привлечения
- `LTV по сильной когорте экспертов`
- `LTV по слабой когорте перехода в оплату`

## Контракт данных

### KPI
Каждая KPI-карточка должна поддерживать:
- `title`
- `value`
- `description`
- `icon`
- `color`

### Строки таблиц
Табличные блоки должны быть готовы к бекенд-привязке как массивы строк.

Минимальные наборы:
- воронка:
  - `step`
  - `count`
  - `conversion`
  - `meaning`
- экономика минут:
  - `metric`
  - `value`
  - `comment`
- повторы:
  - `metric`
  - `value`
  - `meaning`
- LTV:
  - `metric`
  - `value`
  - `meaning`
- очередь:
  - `incident`
  - `waiting`
  - `oldest`
  - `statusColor`
  - `statusText`

### Графики
Каждый график должен принимать:
- labels
- datasets
- legend labels
- colors

## Примечание по бекенд-привязке
- Это ТЗ достаточно для качественной реализации верстки, порядка секций, набора блоков и поведения экрана.
- Для полной реализации без смысловых потерь разработчик еще должен зафиксировать маппинг:
  - из каких таблиц/моделей берется каждая метрика;
  - как считаются `старт бесплатных минут`, `показ экрана оплаты`, `первая оплаченная минута`, `повторная платная сессия`;
  - как считается `LTV D7 / D30 / D90`;
  - что является источником для `размера очереди`, SLA, платежных инцидентов и `refund / dispute`.
- Иначе риск будет не в верстке, а в неправильной бизнес-формуле метрик.

## Контракт поведения
- Пустые данные не должны ломать верстку.
- Если нет значений, показывать `0`, `—` или пустое состояние, но не скрывать весь блок.
- Слишком длинные подписи не должны ломать сетку.
- Таблицы и графики должны рендериться в тех же секциях и порядке, даже если часть данных пустая.
- Фильтры в первой итерации могут быть макетными контролами, но их DOM-место и набор полей должны сохраниться.

## Чеклист приемки
- Экран визуально повторяет структуру макета и handoff-страницы, а не только набор данных.
- Верхний экран читается как `free -> paid -> repeat`.
- Есть отдельный блок потерь и отдельный блок рисков.
- Есть отдельный LTV-слой.
- Нет дейтинговых терминов.
- Сохранен текущий порядок секций.
- Разработчик не заменяет существующие админские компоненты на новый UI-слой.
- Разработчик не переносит в боевой файл внешний стиль handoff-страниц из `web/`.

## Готово, когда
- Верхний экран показывает спрос, выход в бесплатные минуты, первую оплату и повтор.
- Есть продуктовый контур, воронка, unit-экономика, повторы, LTV и риски.
- Нет дейтинговых метрик и сущностей.
- Все блоки можно привязать к реальным данным без изменения контракта верстки.

- Открыть `http://127.0.0.1:8092/admin`
- Проверить `index-admin.php`
- Убедиться, что рендерятся:
  - `Дашборд живых консультаций`
  - `Фильтры и период`
  - `Продуктовый контур`
  - `Воронка и unit-экономика`
  - `Повторы и выручка`
  - `LTV и когорты`
  - `Драйверы роста`
  - `Риски и операционка`
- При необходимости сравнить с `index-admin-v1.php`, `index-admin-v2.php`, `index-admin-v3.php`
