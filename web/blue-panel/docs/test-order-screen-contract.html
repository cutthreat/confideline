Экранный контракт контрольного заказа

Это цепочка экранов и состояний, которую нужно доказать перед тем, как считать платный путь Nebula готовым к первым тестовым продажам и трафику.

Главный PM-вывод

Макеты Oracle/Nebula и backend Confideline рассматриваются вместе. Экран готов только тогда, когда есть действие, backend-связь, текст, состояние ошибки и QA-proof.

Приоритет

Не весь дизайн сразу. Сначала контрольный заказ: оффер, checkout, вопрос, назначение, workspace, ответ, уведомления, support и админская видимость.

Маршрут глазами человека

1. ОфферПонимает услугу, цену, срок, формат.2. ПокупкаСоздает безопасный тестовый заказ.3. ВопросПишет вопрос, который не теряется.4. АдминкаВидит заказ, клиента, вопрос, статус.5. ИсполнительВидит задачу, срок, контекст, поле ответа.6. ОтветКлиент получает результат и next step.7. ПроблемаSupport видит кейс и может решить его.
Критерий: если хотя бы один красный шаг не доказан, трафик и реальные платежи не включаются.

Как использовать в задачах

Для Антона: каждая правка дизайна должна ссылаться на ID шага и показывать нужные состояния: обычное, пустое, ожидание, ошибка, успех, problem state.
Для Игоря: каждая backend-задача должна возвращать proof: route, id сущности, скрин admin/workspace, event log или QA-воспроизводимость.
Для QA: тест проходит не “страницу”, а цепочку: клиент → заказ → вопрос → админка → исполнитель → ответ → уведомления → support → отчет.
