Платная консультация как единый заказ услуги

Пакет для связки Codex + people: Игорь должен получить не абстрактное “сделать checkout”, а понятный контур, который связывает заказ, вопрос клиента, исполнителя, чат, support, события и QA-доказательство.

главный красный разрывбез реальных платежейготово к постановке
Решение PM

Начинать надо не с платежного провайдера, а с test/sandbox lifecycle. Если один тестовый заказ не проходит весь путь, подключение Stripe/PayPal ничего не решит.

Граница

Этот пакет не меняет backend сам. Он задает конечный результат, поля, статусы, роли, приемку и QA proof для внедрения.

Что должно заработать одним маршрутом

1. ОфферКлиент понимает услугу, цену, срок и ограничения.
2. Test checkoutСоздается заказ без реального списания.
3. ВопросВопрос привязан к заказу и клиенту.
4. Service sessionЕдиная карточка услуги в админке.
5. НазначениеЭксперт/агент получает задачу и SLA.
6. ОтветОтвет в чате связан с этой услугой.
7. SupportПроблемы связаны с заказом и чатом.
8. QA proofСкрины, логи, PASS/WARN/STOP.

Минимальные состояния услуги

created

Клиент начал заказ, есть источник/utm и выбранная услуга.

payment_pending

Ждем тестовый success/failed/canceled/pending.

question_required

Оплата имитирована, клиент должен написать вопрос.

awaiting_assignment

Вопрос есть, исполнитель еще не назначен.

assigned / in_work

Исполнитель назначен, SLA запущен, ответ готовится.

answered / closed

Ответ отправлен, начисление и аналитика зафиксированы.

overdue / disputed

Просрочка, жалоба, спор или refund review.

refunded / canceled

Возврат/отмена в test-mode с причиной и логом.

Что нельзя считать готовностью

Нельзя считать готовым: отдельно существующий order, отдельно credits, отдельно dating-chat, отдельно экспертская анкета. Готовность появляется только когда это связано в одну service_session и подтверждено сквозным QA.

Следующий шаг после внедрения

QA/tester проходит тестовый маршрут без реального платежа: клиент → заказ → вопрос → админка → назначение → эксперт → ответ → уведомления no-send → support/failure state → отчет. Итог должен быть публичной proof-страницей Blue Panel.
