# Как лучше использовать Codex в запуске проекта

## 1. Codex как PM-ядро, не просто исполнитель

Использовать Codex для регулярной сборки картины проекта: Trello, Blue panel, QA-отчеты, локальная база, backend-карта, макеты, документы. Результат каждого прохода должен быть не “мысли”, а обновленный реестр/страница/задача.

## 2. Один P0-пакет за раз

Не смешивать email, чат, школу, legal, аналитику и маркетинг в одну карточку. Для каждого направления нужен пакет: бизнес-смысл, текущий proof, недостающее, интерактивный HTML-макет, ТЗ, backend-связь, QA-документ.

## 3. Trello только после Blue panel

Сначала решение фиксируется в Blue panel и мастер-плане. Потом из него создается человеческая карточка Trello на месяц: задача, контекст, шаги, ожидаемый результат, срок, ссылка на результат.

## 4. Ксения как ревизор, не как архитектор

Ксения полезна для проверки понятности обучения, примеров ответов, бытовой применимости и эзотерического тона. Методологию, структуру школы, регламент и контроль качества должен собирать PM-контур, а Ксения проверяет и комментирует.

## 5. Программист работает через co2p

Передача программисту: не “сделай страницу”, а пакет: зачем функция нужна, кто пользователь, макет, поля, состояния, права, связь с backend/admin, acceptance criteria, тест-кейсы.

## 6. Тестировщик подключается до внедрения

Для каждой задачи заранее писать документ ожидаемого результата. После внедрения тестировщик проверяет не абстрактно, а по сценариям: клиент, эксперт, агент, модератор, админ, support, финансы.

## 7. Ежедневный контроль после появления июньских Trello карточек

Утро: что должно двигаться сегодня. Вечер: что изменилось, что зависло, что влияет на срок. До публикации карточек на июнь это не запускать, чтобы не имитировать деятельность.

## 8. Чего не делать Codex

Не менять production, не запускать платежи, не слать письма, не публиковать внешние материалы, не править Trello без команды, не притворяться, что закрытый источник прочитан.
