# Критический аудит PM-контура

Дата: 2026-06-04
Цель: понять, чего не хватает PM, чтобы автономно закрывать вопросы по проекту без постоянного ручного наведения.

## 1. Текущий уровень готовности PM-контура

PM-контур уже может:

- читать Trello через API;
- снимать карточки, списки, архивные карточки, чек-листы, вложения, комментарии справа;
- редактировать чувствительные данные в локальных артефактах;
- строить карту ссылок и проверять внешнюю доступность;
- отличать Blue panel как мастер-план от Trello как месячной доски исполнения;
- связывать стратегию, мастер-план, P0-матрицу, co2p-пакеты и QA;
- читать локальный банк знаний Nebula/Confideline/PbExpert;
- формировать документы и страницы Blue panel на русском языке.

## 2. Чего PM-контуру не хватает

| Недостаток | Почему это мешает | Что нужно сделать |
|---|---|---|
| Нет постоянного реестра Trello intake | PM может повторно “забыть”, что уже снято | Вести карту `card -> desc/comments/attachments/checklists/links/status` |
| Внешние документы не все доступны | Google/Figma/Drive могут быть закрыты | Вести список access blockers и просить доступ только по конкретным ссылкам |
| Вложения Trello сняты как метаданные, но не все прочитаны по содержанию | Вложения могут содержать ключевые ТЗ/уроки/скрины | Сделать отдельный pipeline скачивания и извлечения текста/скринов по приоритетным вложениям |
| Нет единой project taxonomy | Trello кросс-проектный: YouDate/S, YouDate/D, YouDate/N, Nebula, Hugs, старые задачи | Классифицировать карточки по проекту, слою, статусу и применимости |
| Нет полного reading-status по ссылкам | Проверка доступности не равна чтению документа | Для каждой важной ссылки поставить статус: доступна, прочитана, извлечена, использована, заблокирована |
| Нет автоматического обновления Blue panel из Trello-map | Риск ручного расхождения | Делать Trello intake как source artifact, а Blue panel как понятную витрину |
| Нет отдельного decision log | Решения могут теряться между чатами | Вести PM decision register: вопрос, источники, факт, вывод, решение, дата |
| Нет полного QA-runner ownership map | Есть тестировщик и отчеты, но не все сценарии привязаны к P0 | Связать P0 функции с QA сценариями и отчетами |
| Нет финальной карты доступов | PM не должен угадывать, где не хватает прав | Вести access request list: URL, карточка, зачем нужен, статус |

## 3. Что нужно считать обязательным перед каждым крупным PM-проходом

1. Открыть текущий `Trello intake summary`.
2. Проверить, не изменились ли новые карточки/комментарии/вложения.
3. Посмотреть `important link blockers`.
4. Посмотреть `thin cards`.
5. Открыть `project taxonomy / area map`.
6. Сверить с Blue panel: стратегия, мастер-план, P0-матрица.
7. Только после этого готовить новые задачи или выводы.

## 4. Главный критический вывод

Главный недочет был не в отсутствии данных, а в отсутствии устойчивого реестра того, что уже изучено. Теперь такой реестр создан. Следующий проход должен быть не “искать все заново”, а работать от карты:

`Trello full intake -> link/access map -> project taxonomy -> strategy board -> master plan -> co2p task packages`.

## 5. Блокеры для автономности

Сейчас реальные блокеры:

- закрытые Google Docs/Sheets/Drive/Figma ссылки;
- не скачанные и не распознанные вложения Trello;
- часть старых Confideline ссылок ведет на 404 или старые `/ru/admin/...` маршруты;
- часть карточек пустые/тонкие и требует контекстной реконструкции;
- проектная классификация пока первичная, keyword-based, ее нужно уточнить вручную по смыслу.
