QA перед рекламой должен доказать один рабочий заказ

Эта страница задает правила приемки тестирования до первого трафика. QA не стартует от желания “прокликать сайт”. QA стартует только после accepted R01/R02 и возвращает публичный отчет, по которому PM может изменить светофор запуска.

Маршрут до QA

Текущий статус: QA не запускать. R01 safe order и R02 E01 еще не приняты как accepted proof.

PASS / WARN / STOP

PASSКонтрольный заказ проходит end-to-end без критических разрывов: заказ, вопрос, эксперт, ответ, no-send, support, аналитика и админка связаны одним ID.
WARNЕсть некритичный дефект или ручной workaround, который не ломает оказание услуги. Ограниченный запуск возможен только после решения PM/founder.
STOPНет safe order, нет E01, есть риск реального платежа/отправки, нет связки order→question→expert→answer/support/analytics или нет публичного QA-отчета.

Формат результата тестировщика

QA-отчет должен содержать: 1. Короткий вердикт: PASS / WARN / STOP. 2. test_run_id, order_id, question_id, performer/profile_id, answer_id, event_id, support_case_id. 3. Скриншоты с подписями: что проверено и почему это важно. 4. Таблицу QAC01-QAC14: статус, proof, дефект, владелец, следующий шаг. 5. Отдельный блок для Игоря: факт, ожидаемое поведение, как воспроизвести, где смотреть, как ретестить. 6. Отдельный блок для Алексея: продуктовый риск, решение PM, что делать дальше. 7. Список STOP-блокеров, если запуск запрещен. 8. Публичную ссылку GitHub Pages на отчет.
Правило для PM: без публичного QA-отчета статус запуска не меняется. Устное “проверили” или набор скринов в чате не считается доказательством.
