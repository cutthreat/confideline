Постановка задачи Игорю по первому контрольному заказу

Это готовый текст для карточки Trello в человеческом формате: конечная цель, постановка, шаги, результат, часы и progress checklist. Саму Trello-доску эта страница не меняет.

Зачем это нужно

Чтобы не отдавать Игорю весь мастер-план. Нужна одна узкая задача: безопасно провести test order без реального списания и без реальных писем.

Статус

Готово как постановка. Реализация и runtime QA еще не выполнены.

Заголовок карточки

Подготовить безопасный тестовый заказ платной консультации

Описание карточки для Trello

Постановка задачи: Нужно подготовить на сайте безопасный тестовый маршрут платной консультации Nebula/YouDate, чтобы команда могла проверить первый заказ без реального списания денег и без отправки реальных писем клиентам. Смысл задачи: Мы должны доказать, что платная консультация может пройти полный путь: клиент создает тестовый заказ, задает вопрос, заказ превращается в консультацию/задачу, эксперт или агент получает ее, отвечает, админ видит весь маршрут, события фиксируются в no-send режиме, support может создать проблемный сценарий. Шаги выполнения: 1. Подтвердить или сделать safe test checkout: заказ создается как test/sandbox/mock, без реального платежного провайдера и без real charge. 2. Связать test order с вопросом клиента, услугой, языком и test_run_id. 3. Показать единую карточку консультации или задачи: order, question, client, status, deadline, performer, chat, support. 4. Сделать ручное назначение эксперта/агента на тестовую консультацию. 5. Показать рабочее место исполнителя: вопрос, срок, контекст, чат, действие ответа. 6. Проверить, что ответ исполнителя виден клиенту и админу по правам и меняет статус консультации. 7. Сделать no-send события: order_created, payment_test_success, question_submitted, expert_assigned, answer_sent, support_ticket_created, consultation_closed. 8. Создать один support/problem state по тестовому заказу: клиент недоволен ответом или эксперт просрочил ответ. 9. Отделить тестовые данные от реальных продаж, выплат, аналитики и support через test_run_id или аналогичный marker. 10. Передать PM/QA скрины или ссылки на разделы, чтобы QA мог пройти маршрут и сделать публичный отчет. Конечная цель: Один тестовый заказ платной консультации проходит полный безопасный маршрут без реального платежа и без реальных писем. QA может проверить клиентскую сторону, админку, исполнителя, no-send события и support-сценарий. Временные затраты: Ориентир 24-40 часов, если используем существующие backend/admin кирпичи Confideline и не переписываем платформу с нуля. Результат выполнения: Ссылка на Blue Panel результат: https://cutthreat.github.io/confideline/web/blue-panel/docs/igor-test-order-acceptance-contract.html (by Codex) После реализации: ссылка на QA-отчет test order добавляется сюда же.

Комментарий в карточку после постановки

PM-комментарий: Задача не про общий рефакторинг сайта и не про запуск платежей. Цель — безопасный тестовый маршрут, который QA сможет доказать скринами. Реальные платежи, реальные письма клиентам и рекламный трафик запрещены до отдельного решения.
