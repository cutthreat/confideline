PM-решение

Клиентский путь нельзя принимать по макетам. Он принимается только связкой: экран → действие клиента → backend/admin object → текст/документы → no-send/support → QA proof.

Что делать первым

Не расширять customer journey. Сначала доказать один путь: оффер → checkout/test order → вопрос → E01 → ответ → no-send → support → QA report.

Готовый запрос Антону/Игорю по клиентскому пути

Цель: довести один клиентский путь Nebula до проверяемого состояния. Антону / фронту: 1. Оффер должен ясно говорить: платная текстовая консультация, срок ответа, формат, ограничения, support. 2. CTA должен вести в конкретный package/order path, а не в абстрактную страницу. 3. До оплаты должны быть видны disclaimer, Terms/Privacy/Refund/support links. 4. После checkout клиент должен видеть статус, вопрос, срок ожидания, support link. 5. Экран ответа должен иметь next step: задать follow-up, открыть support, вернуться. Игорю / backend: 1. CTA/package должен создавать order/session marker. 2. Auth не должен терять выбранную услугу. 3. Question_id должен быть связан с order_id. 4. Assignment/deadline/status должны быть видны клиенту и админу. 5. Answer_id должен быть виден клиенту, эксперту и админу. 6. No-send events, support_case и analytics row должны быть связаны с тем же order_id. QA принимает только связанный путь, где один test marker проходит через все шаги.
