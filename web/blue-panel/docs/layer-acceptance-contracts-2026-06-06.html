Что считается готовым по каждому слою

Эта страница фиксирует приемочный стандарт: какие факты переводят слой из красного или желтого статуса дальше. Она нужна для PM, Заказчика, Игоря, QA, Антона и Ксении, чтобы “готово” означало одно и то же.

текущий запуск: STOP12 контрактов приемкиединый стандарт proof
Главное правило

Мы не принимаем “готово” по словам, карточке Trello, макету или ТЗ. Нужен факт: ID, скрин, лог, QA-отчет, no-send событие, заполненный журнал или утвержденное решение владельца.

Как меняется статус

Красный или желтый слой меняется только после accepted proof. Если proof неполный, слой остается в текущем статусе, а задача возвращается владельцу с причиной.

1Слой имеет статус и владельца
2Контракт говорит, что считается готовым
3Команда приносит proof
4PM принимает accepted / returned / blocked

Контракты приемки

красный

Backend и админка Confideline

Принимаем как готово: Один безопасный заказ имеет order_id, клиента, вопрос, назначенного исполнителя, ответ, admin timeline, события и связанный support/failure marker.

Не принимаем: Есть только описание/ТЗ без прохода на рабочем сайте; заказ виден частично; нет связи order/session/expert/answer.

Доказательство: ID заказа, скрины админки, timeline, no-send events, support_case_id, QA-ссылка.

 красный

Клиентский платный путь

Принимаем как готово: Клиент проходит offer -> order/checkout -> question -> wait -> answer -> follow-up/support без ручного вмешательства вне оговоренных admin actions.

Не принимаем: Путь описан, но не пройден мышкой; часть шагов подтверждена только словами.

Доказательство: Скрины клиентского пути, order/session/question/answer IDs, QA report PASS/WARN.

 желтый

Фронт Oracle/Nebula

Принимаем как готово: Для критичных экранов есть дизайн-источник, сверстанная/доступная страница, backend-связь, контент, ошибки/failure states и QA-скрин.

Не принимаем: Есть только Figma/PNG без backend; есть верстка без контента/ошибок; экран не связан с заказом.

Доказательство: Screen contract, скрин макета, скрин реализации, route, backend field/action, QA verdict.

 красный

Эксперты и школа

Принимаем как готово: E01-E05 имеют заполненный журнал допуска: обучение, регламент, тест, пробный ответ, SLA, роль/доступ, анкета, финальный статус accepted.

Не принимаем: Есть материалы обучения, но нет конкретных допущенных людей; Ксения посмотрела общо без scorecard.

Доказательство: Admission journal, scorecard, пробные ответы, скрины доступа/роли, ревизия Ксении.

 красный

Рабочее место эксперта/агента

Принимаем как готово: Исполнитель получает задачу по заказу, видит вопрос/SLA/контекст, отправляет ответ, статус и начисления фиксируются в системе.

Не принимаем: Есть макет кабинета, но нет runtime assignment; эксперт работает вне сайта.

Доказательство: Скрины workspace, assignment_id, answer_id, timestamps, начисления/статус, admin confirmation.

 красный

Email, уведомления и события

Принимаем как готово: Все обязательные события по заказу зафиксированы в no-send режиме без реальной отправки клиентам: order, assignment, answer, support, follow-up.

Не принимаем: Есть шаблоны без триггеров; есть отправка без no-send proof; события не связаны с заказом.

Доказательство: event_id, template, recipient role, trigger, preview, external_send=false, linked order_id.

 красный

Support и проблемные ситуации

Принимаем как готово: По одному заказу создан problem/support case с причиной, владельцем, решением, статусом закрытия и видимостью в админке.

Не принимаем: Правила описаны, но нет case; refund/retry/credit не имеют владельца и статуса.

Доказательство: support_case_id, order_id, reason, owner, decision, client/admin screenshots, QA verdict.

 желтый

Документы, доверие и checkout

Принимаем как готово: Terms, Privacy, Disclaimer, Refund, FAQ и checkout consent готовы в HTML-разметке, согласованы с legal/payment decisions и привязаны к LP/checkout.

Не принимаем: Документы общие или dating legacy; нет seller/provider/descriptor/refund/geography; нет checkout consent.

Доказательство: HTML-ready package, approved variables, checkout screenshots, legal/founder decision record.

 красный

Маркетинг и первый трафик

Принимаем как готово: Есть QA PASS/WARN, 5 accepted experts, документы/checkout, purchase analytics, capacity rules, daily report и stop-сигналы.

Не принимаем: Запускать paid traffic до runtime proof; считать LTV/CAC без source/session/order/value данных.

Доказательство: Go/no-go sheet, QA report, expert journal, tracking links, daily report template, CAC/LTV calculator.

 красный

Аналитика покупки и LTV

Принимаем как готово: Заказ связан с источником, сессией, клиентом, стоимостью, валютой, услугой, экспертом, support и повторным действием.

Не принимаем: Есть выручка без источника; есть source без заказа; CAC/LTV считаются гипотезой.

Доказательство: purchase event, source/campaign, order_id, value/currency, service_id, expert_id, support marker, report row.

 красный

QA перед рекламой

Принимаем как готово: QA проходит утвержденный сценарий и выдает PASS/WARN/STOP с публичным отчетом, скринами, ID и списком исправлений.

Не принимаем: QA стартует без R01/R02; отчет без скринов/ID; проверка только локальных документов.

Доказательство: Public QA report, verdict, screenshots, IDs, defect list, retest notes.

 желтый

Управление решениями владельца

Принимаем как готово: По legal seller, payment provider, descriptor, refund path, launch geography и bootstrap boundary есть зафиксированное решение владельца.

Не принимаем: PM сам утвердил юридический/платежный путь; решение осталось в чате без фиксации.

Доказательство: Decision record: вариант, дата, владелец, последствия, где применено.

PM-вывод: эта матрица не запускает работу сайта сама по себе. Она делает приемку честной: если нет перечисленного proof, слой нельзя переводить в зеленый и нельзя включать трафик.
