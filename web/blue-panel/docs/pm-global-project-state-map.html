Где проект готов, где частично готов, а где запуск запрещен

Это верхний PM-срез по всем слоям Nebula/YouDate: backend, frontend/design, Trello, документы, обучение, эксперты, клиентский путь, админка, support, уведомления, QA, маркетинг, аналитика и запуск.

2 зеленых12 желтых8 красныхтрафик пока нельзя
Главный вывод

Проект собран как PM-система и план запуска, но не доказан как работающий платный сервис. Красный центр — контрольный заказ: без него нельзя честно говорить, что клиентский путь, эксперт, админка, уведомления, support и QA готовы.

Как использовать

Эта страница отвечает “что у нас есть и чего не хватает”. Для деталей кликай в область: внутри лежит proof, пакет, acceptance criteria или следующий рабочий ресурс.

2области можно использовать как основу
12областей частично готовы или требуют решения
8областей блокируют запуск/рекламу
0контрольных заказов с QA verdict
PM-решение: не добавлять хаотично новые функции. Сначала закрыть runtime proof базовой услуги: безопасный test order, вопрос, назначение исполнителя, ответ, admin visibility, no-send события, support case и QA verdict. После этого пересчитать светофор и решать первый трафик.

Карта по слоям

L01Стратегия платформыPM + основательДоказано: Платформа сначала: универсальная paid P2P-система, Nebula/Oracle как первая коммерческая ниша.Не хватает: Стратегия не доказывает, что текущий сайт готов к клиентам.Следующий шаг: Держать все июньские задачи привязанными к универсальному пути услуги. L02Мастер-план и управление месяцемPMДоказано: Есть план июня, execution-маршрут, backlog блокеров, очередь команды и публичные proof-ссылки.Не хватает: Нужно поддерживать актуальность после каждого результата команды.Следующий шаг: Каждый факт обновлять в Blue Panel и ссылать из Trello. L03Trello как доска согласованияPMДоказано: Текущие названия карточек сохраняются как источник истины; карточки июня связаны с Blue Panel.Не хватает: Не все карточки доказывают внедренную функцию, часть — подготовленные PM-пакеты.Следующий шаг: Не менять названия; результат задачи фиксировать ссылкой на Blue Panel. L04Backend Confideline и админкаИгорь + PMДоказано: Confideline принят как backend/admin база; есть карты заказов, ролей, chat/admin/email/support.Не хватает: Нет runtime proof единого пути: заказ → вопрос → исполнитель → ответ → события → support.Следующий шаг: Передать Игорю safe test order и получить admin route proof. L05Frontend Oracle/Nebula и дизайнPM + Антон + ИгорьДоказано: Есть карта экранов и сценариев: frontend/design, backend, контент, QA, владелец.Не хватает: 0 зеленых paid-flow; дизайн не доказан как работающая платная услуга.Следующий шаг: Закрывать экранные контракты вокруг контрольного заказа. L06Контент страниц, оффер и FAQPM + АнтонДоказано: Структура оффера, услуги, disclosure, FAQ и checkout wording подготовлена.Не хватает: Финальный текст зависит от legal/payment/founder решений и экранной сверки.Следующий шаг: Подготовить HTML-ready тексты, но не считать финальными до решений. L07Клиентский путь платной консультацииИгорь + QA + PMДоказано: Путь описан: оффер → test checkout → вопрос → ожидание/чат → ответ → support.Не хватает: Нет полного прохода мышкой и QA verdict.Следующий шаг: Закрыть gate и провести безопасный контрольный заказ. L08Платежный/тестовый заказИгорьДоказано: Подготовлены gate, cockpit, acceptance contract и QA brief.Не хватает: Нет order id в test/sandbox/mock режиме без реального списания.Следующий шаг: Получить safe order proof до любых QA/трафика. L09Рабочее место эксперта/агентаИгорь + QAДоказано: Пакет рабочего места описан: задача, вопрос, срок, чат/ответ, статус, начисления.Не хватает: Не доказано, что исполнитель реально получает и закрывает задачу в админке.Следующий шаг: Проверить workspace на контрольном заказе. L10Первые 5 экспертов и школаPM + КсенияДоказано: Материалы обучения извлечены, школа v1 и журнал допуска опубликованы.Не хватает: Нет ревизии Ксении, тестов, пробных ответов и статуса допуска каждого эксперта.Следующий шаг: Заполнить журнал допуска по 5 реальным экспертам. L11Регламент качества экспертовPM + Ксения + QAДоказано: Регламент v1 собран: SLA, тон, качество, запреты, эскалация, санкции.Не хватает: Не проверен на реальном/пробном ответе.Следующий шаг: Оценить пробный ответ по регламенту и внести правки. L12Модерация, баны, качество и видимость экспертовPM + Игорь + QAДоказано: Область описана через quality/support/failure state и экспертский регламент.Не хватает: Не доказаны admin-инструменты: предупреждения, скрытие, теневой/явный бан, ручное поднятие/понижение.Следующий шаг: Сформировать отдельный admin-quality package после test order workspace. L13Ранжирование и поднятие экспертовPM + ИгорьДоказано: Потребность зафиксирована: сильные эксперты должны быть выше, видимость должна управляться.Не хватает: Нет формулы ранжирования, admin override, правил promo/boost и защиты от серой накрутки.Следующий шаг: Добавить ranking/visibility model после подтверждения экспертского workspace. L14Email, уведомления и событияИгорь + QAДоказано: Пакет событий/no-send/preview подготовлен.Не хватает: Нет no-send event log на одном контрольном заказе.Следующий шаг: Проверить события заказа, вопроса, назначения, дедлайна, ответа, support и follow-up. L15Support, тикеты и проблемные сценарииИгорь + QA + PMДоказано: Сценарии просрочки, плохого ответа, жалобы и review описаны.Не хватает: Нет runtime support case, связанного с заказом/чатом/исполнителем.Следующий шаг: Смоделировать один problem state на контрольном заказе. L16Документы, дисклеймеры, refund, checkout legalPM + founder/legalДоказано: Структура public docs и HTML-ready подход подготовлены.Не хватает: Юрлицо, provider, descriptor, refund window, geography не утверждены.Следующий шаг: Готовить пакет как draft, финализировать после founder/legal/payment gate. L17Финансы, начисления и мотивация командыPM + основательДоказано: Модель выплат/начислений/удержаний подготовлена как PM-пакет.Не хватает: Нет финального founder decision и тестового начисления на реальном заказе.Следующий шаг: После test order показать preview начисления без реальной выплаты. L18Аналитика продукта и работы командыPM + Игорь + QAДоказано: Go/no-go метрики, CAC/LTV поля и stop-сигналы описаны.Не хватает: Нет runtime events, dashboard по expert/agent/admin, capacity и качеству.Следующий шаг: Связать аналитику с test order и минимальными KPI экспертов. L19Языки, переводы и коммуникация эксперт-клиентPM + ИгорьДоказано: Потребность в языках и переводах зафиксирована в PM-контуре как риск многоязычного сервиса.Не хватает: Нет P0-решения: какие языки запуска, кто переводит, где хранится язык клиента/эксперта, как проверяется качество.Следующий шаг: Сформировать language/translation decision pack после базового test order. L20QA перед рекламойQA + PMДоказано: QA brief, preflight и report shell подготовлены.Не хватает: Нет PASS/WARN/STOP по текущему runtime.Следующий шаг: Запускать QA после READY gate контрольного заказа. L21Маркетинг, LTV/CAC и первый трафикPM + основательДоказано: Рамка каналов, go/no-go и stop-сигналов подготовлена.Не хватает: Нет QA PASS, capacity 5 экспертов, legal/payment proof, фактической экономики.Следующий шаг: Не покупать трафик до контрольного заказа и QA verdict. L22Операционный режим после запускаPM + командаДоказано: Очередь команды и роли описаны: PM, Игорь, QA, Ксения, Антон, основатель.Не хватает: Нет daily operating routine на реальных заказах: утро/вечер, SLA breach, escalation, weekly report.Следующий шаг: Оформить daily ops checklist после первого контрольного заказа.
