Как разбирать дизайн, backend, контент и QA по каждому экрану

Для запуска нельзя оценивать экран только по картинке или только по маршруту backend. Рабочая единица PM — это экранный контракт: дизайн-источник, backend-связь, контент, состояния и проверка.

Что уже есть

Локальная карта Oracle/Nebula подтверждает public pages, money pages, auth, FAQ/legal/refund/payment surfaces и 19 экранов ЛК/кабинета.

Главный пробел

Дизайн сильный в discovery/chat UI, но неполный для paid consultation MVP: не хватает платных состояний, результата, support/refund и notification return states.

Как использовать PNG

PNG/экспорт можно использовать как визуальный proof и для “разбора глазами”, но не как единственный источник правды. Для внедрения нужен manifest/screen spec/Figma node или явный blocker.

Пятислойная проверка каждого экрана

1. Страницаесть ли экран в Oracle/Nebula дизайне, PNG/export/Figma/source path
2. Backendкакой Confideline route/admin модуль обслуживает функцию
3. Контентготовы ли тексты, FAQ, legal, переменные, переводы, AskNebula analog
4. Состоянияempty/error/success/loading/offline/payment/refund/SLA
5. QAкакой proof покажет, что экран можно пускать в трафик

PM-решение

В JUN-08 добавляем обязательную content/design/backend/QA сетку. Следующий проход по дизайну делается не хаотично: берем экран из Oracle/Nebula project map, сверяем с AskNebula-паттерном и правками Антона, связываем с backend route, проверяем наличие контента из Trello/AskNebula/Google, фиксируем проблемные сценарии и только потом формируем задачу Антону, Игорю или Ксении.

Карта связи будущих страниц и бекенда: что есть в макетах Oracle/Nebula, что есть в Confideline backend/admin и где нужен proof перед задачей Игорю.
