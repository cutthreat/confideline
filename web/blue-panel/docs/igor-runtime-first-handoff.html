Первый пакет Игорю для запуска QA контрольного заказа

Это короткая постановка не на всю платформу, а на минимальный backend/admin-срез, после которого тестировщик сможет пройти один безопасный заказ и выдать доказанный PASS/WARN/STOP.

не реальные платежине реальные письматолько test/no-send контур
Результат для команды

Игорь показывает test order, связанный вопрос, назначение исполнителю, рабочее место, no-send события и support state. QA получает order id/session id и проходит сценарий.

Почему это первый пакет

Без этого нельзя честно сказать, что сервис готов к покупке трафика: документы и макеты есть, но реальный путь заказа еще не доказан.

Игорь: внедрениеPM: фикстурыQA: проверка

Границы задачи

Делаем сейчас

Один безопасный контрольный заказ: клиентский вопрос, заказ, админская видимость, назначение, workspace, no-send timeline, support/problem state.

Не делаем в этом пакете

Боевые платежи, массовые рассылки, внешний трафик, полную переделку личного кабинета, полный экспертский marketplace и автоматическое масштабирование.

Когда считается готово

Есть доказательства по каждому deliverable: route/ID, скрин admin, связка question-session, workspace, event log, support state, QA-ready вывод.

Стоп-условие

Если нет safe order или no-send режима, QA не стартует. Сначала закрываем безопасность теста, затем проверяем пользовательский путь.

PM-решение: это первый минимальный handoff. Если Игорь закрывает эти 6 пунктов, дальше можно запускать QA контрольного заказа и только после QA пересчитывать готовность запуска.

Что получает каждый участник

Игорь

Короткий список того, что показать в backend/admin, без чтения всего мастер-плана. Для каждого пункта есть ожидаемый proof.

QA

Order id, session/task id, роли, маршруты, список evidence и критерий PASS/WARN/STOP.

PM

Факты для обновления Blue Panel, Trello-результата и решения, можно ли двигаться к трафику.

Алексей/Заказчик

Понятный вывод: готов ли сервис принять первый безопасный заказ или где конкретно он ломается.
