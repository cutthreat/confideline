Требования PM-цели: что доказано, что нет

Это актуальный аудит исходной большой задачи. Он проверяет все слои запуска: backend, frontend/design, Trello, Blue Panel, документы, обучение, экспертский контур, клиентский путь, админку, support, уведомления, QA, маркетинг и запуск.

5 зеленых7 желтых7 красныхцель не закрыта
PM-решение

Управленческая структура стала сильной: есть proof-страницы, очередь действий, автономность PM, проверенные ссылки. Но цель нельзя закрывать, пока нет runtime proof сайта: контрольного заказа, admin route, workspace, no-send log, support-case, допуска 5 экспертов и QA verdict.

Как читать

Зеленый = можно опираться как на PM-контур. Желтый = пакет есть, но нужен внешний факт, решение или runtime. Красный = блокирует MVP/трафик.

Правило завершения: цель можно закрывать только после доказательств по каждому требованию. Текущий аудит показывает прогресс, но не доказывает запусковую готовность продукта.

Требования исходной PM-цели

REQ01Доказательная база текущего состоянияЖелтыйЕсть: Собраны proof ledger, аудит PM-цели, индекс покрытия, source gap summary, аудит ссылок.Не хватает: Нет runtime-фактов по рабочему сайту: контрольный заказ, QA-скрины, no-send log, support-case.Дальше: Продолжать добавлять только проверяемые proof-страницы и не считать документы runtime-готовностью. REQ02Backend ConfidelineЖелтыйЕсть: Backend/admin принят как база; есть admin/backend maps, runtime gaps и контракт Игорю.Не хватает: Не доказан сквозной путь order -> question -> session -> assignment -> answer -> support -> events.Дальше: Закрыть AC01-AC09 на контрольном заказе. REQ03Frontend/design Oracle/NebulaЖелтыйЕсть: Есть screen/backend/content gate и карта критичных экранов.Не хватает: Нет proof, что ключевые экраны сверстаны и связаны с backend на рабочем пути.Дальше: Сначала связать offer, order, question, answer, support с backend/content/QA. REQ04Trello и план июняЖелтыйЕсть: Есть снимок Trello, план июня, правило не менять названия без команды, факт-статусы.Не хватает: Не все карточки имеют внедренный результат и proof-ссылку.Дальше: После каждого результата вставлять Blue Panel proof в карточку, не перетирая постановку. REQ05Blue Panel как инфраструктура контроляЗеленыйЕсть: Главная панель, страница для Алексея, индекс покрытия, автономность PM, аудит ссылок опубликованы.Не хватает: Нужно поддерживать актуальность после новых фактов.Дальше: Каждый новый proof публиковать и проверять внешний доступ. REQ06Документы, legal, policy, disclaimer, checkoutЖелтыйЕсть: PM-пакет public docs и checkout wording подготовлен.Не хватает: Финал зависит от seller/payment/descriptor/refund/geography/legal review.Дальше: Держать HTML-ready пакет без финальной публикации до legal/payment gate. REQ07Обучение и школа экспертовЖелтыйЕсть: Материалы обучения, школа v1, регламент и gate допуска собраны.Не хватает: Нет ревизии Ксении и фактических результатов обучения первых экспертов.Дальше: Провести ревизию и проверить пробные ответы. REQ08Первые 5 экспертовКрасныйЕсть: Есть gate и журнал допуска.Не хватает: Нет заполненного допуска каждого эксперта: тест, пробный ответ, SLA, ручное решение.Дальше: Заполнить статус готов/доработка/не допущен по каждому из 5 экспертов. REQ09Экспертский/агентский контурКрасныйЕсть: Workspace handoff и PF05-PF07 proof register подготовлены.Не хватает: Не доказано, что исполнитель получает задачу и отвечает внутри системы.Дальше: Проверить workspace на контрольном заказе. REQ10Клиентский путь платной консультацииКрасныйЕсть: PF00-PF12 и test order route описаны.Не хватает: Нет фактического прохода offer -> checkout -> question -> answer -> support/follow-up.Дальше: После READY gate провести безопасный контрольный заказ. REQ11Админка и операционная видимостьКрасныйЕсть: Admin control gate и backend/admin maps подготовлены.Не хватает: Нет скриншотов/логов, что админ видит весь заказ без ручного поиска.Дальше: Показать order, question, assignment, events, support в admin route. REQ12Support, тикеты, просрочки, возвратыКрасныйЕсть: Failure states и support gate описаны.Не хватает: Нет runtime support-case, связанного с order/session/chat/expert.Дальше: Включить один problem state в контрольный заказ. REQ13Email, уведомления, рассылки, no-sendЖелтыйЕсть: События и no-send gate подготовлены.Не хватает: Нет no-send event log на тестовом заказе.Дальше: Проверить order/question/assignment/answer/support/follow-up events. REQ14QA перед трафикомКрасныйЕсть: QA brief, public report shell и proof naming есть.Не хватает: Нет PASS/WARN/STOP по рабочему сайту.Дальше: После READY от Игоря запустить QA и опубликовать отчет. REQ15Маркетинг, экономика, первый трафик и запускКрасныйЕсть: Go/no-go, capacity/economy gate и CAC/LTV preflight есть.Не хватает: Нет QA PASS, capacity proof, legal/payment решений и фактической экономики.Дальше: Готовить материалы, но не покупать трафик до runtime proof. REQ16Классификация красный/желтый/зеленыйЗеленыйЕсть: Светофор есть в readiness, coverage, objective audit, autonomy matrix.Не хватает: Статусы должны обновляться только по фактам.Дальше: После каждого runtime proof пересчитывать связанные страницы. REQ17Пробелы, блокеры и владельцыЗеленыйЕсть: Есть owner map, team queue, handoff queue, autonomy boundaries.Не хватает: Красные блокеры остаются до external/runtime proof.Дальше: Двигаться по current next action board. REQ18Понятный мастер-план с proof-ссылками и next stepsЗеленыйЕсть: Есть страница для Алексея, план июня, индекс покрытия, очереди и проверенные ссылки.Не хватает: После runtime QA нужно обновить месяцы, Trello-факт и go/no-go.Дальше: Использовать мастер-план как основу разговора с Заказчиком. REQ19Автономная работа PMЗеленыйЕсть: Матрица автономности показывает, что PM закрывает сам, что готовит для команды и где нужен внешний proof.Не хватает: Автономность не заменяет действия Игоря, QA, Ксении и решений основателя.Дальше: Продолжать автономно по желтым PM-пакетам, не закрывая красный runtime без фактов.
