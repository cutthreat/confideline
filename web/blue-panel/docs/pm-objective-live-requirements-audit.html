Требования PM-цели: что доказано, что нет

Это верхний аудит большой PM-задачи. Он показывает, какие слои проекта уже оформлены как управляемая доказательная база, а какие остаются красными до фактов на сайте, действий команды или решений основателя.

5 зеленых6 желтых8 красныхцель не закрыта
PM-решение

Инфраструктура контроля проекта уже собрана: Blue Panel, мастер-план, Trello-снимок, источники, legal/checkout, обучение, burn-down и стандарт доказательств. Но цель нельзя закрывать, пока нет runtime proof: контрольного заказа, admin route, workspace, no-send log, support-case, допуска 5 экспертов и QA verdict.

Как читать

Зеленый = можно опираться как на PM-контур. Желтый = пакет есть, но нужен внешний факт, решение или runtime. Красный = блокирует MVP/трафик.

6требований частично закрыты
8требований остаются красными
0контрольных заказов с QA verdict
Почему цель активна: документы, Trello, макеты и PM-выводы теперь систематизированы, но не доказывают работу платной консультации. Зеленый запусковый статус появится только после runtime/QA evidence.
Кратчайший путь: идти по очереди снятия блокеров: один безопасный заказ, админская видимость, рабочее место эксперта, ответ, no-send события, support и публичный QA-отчет.

Требования исходной PM-цели

REQ01Доказательная база текущего состоянияжелтыйДоказано: Есть proof ledger, source coverage, trust standard, blocker burn-down, link audit и опубликованные реестры по слоям.Не хватает: Нет runtime-фактов сайта: order id, session id, no-send log, support case, QA report.Дальше: Двигаться по очереди снятия блокеров и добавлять только фактические proof. REQ02Backend Confideline как база платформыжелтыйДоказано: Есть backend/admin inventory, admin gate, контракт Игорю и runtime evidence kit.Не хватает: Не доказан сквозной путь order -> question -> session -> assignment -> answer -> support -> events.Дальше: Игорь показывает AC01-AC09 на одном безопасном тестовом заказе. REQ03Frontend/design Oracle/NebulaжелтыйДоказано: Есть дизайн-источники, screen/backend/content inventory и экранные gates.Не хватает: Нет полного screen-by-screen proof для P0 paid-flow и runtime-связки с backend.Дальше: Сначала закрыть оффер, checkout, вопрос, ответ, support и FAQ через screen contract. REQ04Trello и план июняжелтыйДоказано: Есть снимок Trello, план июня, правило “обновить”, запрет менять названия без команды, факт-статусы.Не хватает: Не все карточки имеют внедренный результат и proof-ссылку.Дальше: После результата добавлять Blue Panel proof в карточку, не перетирая постановку. REQ05Blue Panel как инфраструктура контролязеленыйДоказано: Есть главная панель, страница для Алексея, PM coverage, readiness, proof стандарт, burn-down, опубликованные ссылки.Не хватает: Требует регулярного обновления после каждого факта.Дальше: Поддерживать как stakeholder cockpit, не превращать в склад мыслей. REQ06Документы, policies, дисклеймеры и checkoutжелтыйДоказано: Есть public docs/checkout PM-пакет и отдельный реестр документов, правил, blockers и мест размещения.Не хватает: Финал зависит от seller/payment/descriptor/refund/geography/legal review и checkout runtime proof.Дальше: Готовить HTML-ready пакет, но не публиковать финал и не запускать оплату. REQ07Обучение и школа экспертовжелтыйДоказано: Материалы AskNebula/PbExpert извлечены; есть школа v1, регламент, scorecard и admission gate.Не хватает: Нет ревизии Ксении по готовому пакету и нет результатов прохождения первыми экспертами.Дальше: Выдать ревизию Ксении и подготовить тестовый кейс для пробных ответов. REQ08Первые 5 экспертовкрасныйДоказано: Есть gate и журнал допуска.Не хватает: Журнал не заполнен по каждому из 5: обучение, тест, пробный ответ, SLA, PM verdict.Дальше: Заполнить статус каждого эксперта: допущен / доработка / не допущен. REQ09Экспертский/агентский контуркрасныйДоказано: Есть workspace handoff и expert runtime proof register.Не хватает: Не доказано, что исполнитель получает задачу и отвечает внутри системы.Дальше: Проверить assignment, workspace и answer delivery на контрольном заказе. REQ10Клиентский путь платной консультациикрасныйДоказано: PF00-PF12 описаны; есть runtime proof master и evidence capture kit.Не хватает: Нет фактического прохода offer -> checkout/test order -> question -> answer -> support/follow-up.Дальше: После READY gate провести безопасный контрольный заказ. REQ11Админка и операционная видимостькрасныйДоказано: Есть admin control gate и backend/admin inventory.Не хватает: Нет скринов/логов, что админ видит весь заказ без ручного поиска.Дальше: Показать order, question, assignment, events, support и final status в admin route. REQ12Support, тикеты, просрочки, возвратыкрасныйДоказано: Есть support/failure gate и problem proof register.Не хватает: Нет runtime support-case, связанного с order/session/chat/expert.Дальше: Включить один problem state в контрольный заказ. REQ13Email, события, уведомления, no-sendкрасныйДоказано: Есть no-send gate, event matrix и требования к preview/log.Не хватает: Нет no-send event log на тестовом заказе.Дальше: Проверить created/question/assigned/answered/support/resolved events без отправки. REQ14QA перед трафикомкрасныйДоказано: Есть QA brief, public report shell, proof naming и evidence kit.Не хватает: Нет PASS/WARN/STOP по рабочему сайту.Дальше: После READY от Игоря пройти QA и опубликовать отчет. REQ15Маркетинг, экономика и первый трафиккрасныйДоказано: Есть go/no-go, CAC/LTV, capacity/economy gates и marketing inventory.Не хватает: Нет QA PASS, capacity proof, legal/payment decisions и фактической экономики.Дальше: Готовить материалы, но paid traffic запрещен до runtime proof. REQ16Классификация красный/желтый/зеленыйзеленыйДоказано: Есть readiness, coverage, objective audit и trust standard, который фиксирует вес доказательств.Не хватает: Статусы должны пересчитываться только по новым фактам.Дальше: После каждого runtime proof обновлять связанные страницы. REQ17Пробелы, блокеры и владельцызеленыйДоказано: Есть owner map, team queue, current next actions и launch blocker burn-down board.Не хватает: Красные блокеры остаются до runtime/external proof.Дальше: Двигаться по burn-down board: кто, действие, результат, proof. REQ18Понятный мастер-план с proof-ссылкамизеленыйДоказано: Есть страница для Алексея, июньская карта, мастер-план, PM coverage и proof-ссылки.Не хватает: После runtime QA нужно обновить go/no-go и Trello result links.Дальше: Использовать как основу разговора с Заказчиком. REQ19Автономная работа PMзеленыйДоказано: Есть матрица автономности, стандарт доказательств и очередь PM-действий.Не хватает: Автономность не заменяет runtime от Игоря, QA, Ксении и решений founder/legal/payment.Дальше: PM закрывает все подготовительные желтые пакеты сам, красное закрывается только фактами.
