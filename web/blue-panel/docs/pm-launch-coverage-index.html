Карта покрытия проекта по слоям

Это верхний контроль PM: что уже собрано, что доказано, где не хватает фактов и какое следующее действие переводит слой к запуску. Страница нужна, чтобы мы не путали подготовленный документ с работающей функцией сайта.

2 зеленых слоя5 желтых зон10 красных блокеровитог запуска: STOP
Главный вывод

PM-инфраструктура уже управляемая: есть мастер-план, proof-порядок и Blue Panel. Но запуск сервиса остается красным, пока нет контрольного заказа, QA-отчета, допуска экспертов, no-send событий, support-case и базовых legal/payment решений.

Как использовать

Открывай слой как карточку. Внутри сразу видно: доказано, не хватает, дальше, владелец и proof-ссылка. Если слой красный, его нельзя считать готовым для трафика.

Слои проекта

зеленый

Стратегия и мастер-план

Доказано: Зафиксирована логика: сначала универсальная paid P2P-платформа, Nebula как первая ниша; есть короткий мастер-план и план июня.

Не хватает: Стратегия не доказывает работу сайта и первые продажи.

Дальше: Поддерживать связь стратегия -> мастер-план -> июнь -> proof.

 зеленый

Blue Panel и PM-контроль

Доказано: Есть публичная панель, светофор, чек-лист запуска, proof-control, link-health, автономная очередь PM.

Не хватает: Нужна постоянная актуализация после фактов команды.

Дальше: После каждого результата обновлять конкретную proof-страницу и ссылку результата.

 желтый

Trello и месячное управление

Доказано: Есть понимание регламента Trello: заголовки не трогаем без команды, результат через ссылку Blue Panel, статус через метки/чек-листы.

Не хватает: Не все карточки имеют подтвержденный результат, weekly update и proof-ссылку.

Дальше: Вести Trello как план месяца, но не считать Trello proof внедрения.

 красный

Backend Confideline и админка

Доказано: Есть карта backend/admin gates и запрос R01 по безопасному заказу.

Не хватает: Нет доказанного order_id -> question -> session -> assignment -> answer -> admin timeline -> support/events.

Дальше: Получить R01 от Игоря и принять его только по фактам.

 желтый

Frontend и дизайн Oracle/Nebula

Доказано: Есть дизайн-источники и принцип экран -> backend -> контент -> failure states -> QA.

Не хватает: Нет полного proof, что ключевые экраны сверстаны и связаны с backend.

Дальше: Разбирать критичные экраны paid-flow и делать screen contracts.

 красный

Клиентский платный путь

Доказано: Путь описан: оффер, выбор, оплата/заказ, вопрос, ожидание, ответ, follow-up, support.

Не хватает: Нет прохода реальным тестом на рабочем сайте.

Дальше: Провести безопасный контрольный заказ после READY.

 красный

Админская видимость и операционка

Доказано: Описано, что админ должен видеть: заказ, клиента, эксперта, SLA, события, support, возврат, качество.

Не хватает: Нет скриншотов/логов по одному заказу.

Дальше: Проверить admin route в рамках R01/QA.

 желтый

Школа и регламент экспертов

Доказано: Материалы обучения, школа v1, регламент и контур ревизии Ксении собраны.

Не хватает: Нет принятого прохождения экспертами и финальной ревизии.

Дальше: Довести пакет до приемки и запустить допуск E01.

 красный

Допуск первых 5 экспертов

Доказано: Есть журнал допуска и условия EP01-EP10.

Не хватает: 0 из 5 экспертов accepted proof-фактами.

Дальше: E01 нужен до QA; E01-E05 нужны до первого трафика.

 красный

Рабочее место эксперта/агента

Доказано: Собран handoff по задаче, вопросу, SLA, чату, ответу, начислениям и качеству.

Не хватает: Не доказано назначение и закрытие задачи в runtime-заказе.

Дальше: Проверить assignment и answer delivery на safe order.

 красный

Email, уведомления и события

Доказано: Есть no-send gate и список обязательных событий.

Не хватает: Нет no-send event log на одном order_id.

Дальше: Проверить события без реальной отправки писем.

 красный

Support и проблемные ситуации

Доказано: Описаны failure states: просрочка, плохой ответ, жалоба, refund review, retry/credit, зависание.

Не хватает: Нет support_case_id, owner, decision и closure proof.

Дальше: Включить один problem state в контрольный заказ.

 желтый

Документы сайта и checkout-тексты

Доказано: PM может готовить HTML-ready пакет: Terms, Privacy, Disclaimer, Refund, FAQ, checkout consent.

Не хватает: Финал зависит от seller/provider/descriptor/refund/geography/legal approval.

Дальше: Готовить пакет без публикации до founder/legal/payment gate.

 красный

Маркетинг, привлечение и LTV

Доказано: Есть preflight, stop-сигналы, CAC/LTV логика и запрет трафика до QA.

Не хватает: Нет QA PASS, capacity 5 экспертов, purchase analytics и фактической экономики.

Дальше: Готовить материалы, paid traffic budget = 0 до proof.

 красный

Аналитика покупки и ежедневный контроль

Доказано: Есть шаблоны daily report и capture sheets.

Не хватает: Нет source/session/order/value/currency/service/support связки на реальном заказе.

Дальше: Привязать аналитику к safe order и первому тесту.

 красный

QA перед рекламой

Доказано: Есть QA runbook, QA contract и публичный report shell.

Не хватает: Нет PASS/WARN/STOP по рабочему сайту.

Дальше: Старт QA только после accepted R01/R02.

 желтый

Решения владельца и запуск

Доказано: Список решений и блокеров зафиксирован: legal seller, payment provider, descriptor, refund path, launch geography.

Не хватает: Решения не утверждены; PM не должен утверждать их сам.

Дальше: Готовить decision pack, но не закрывать без владельца.

Правило PM: зеленый статус получает только управленческий контур, проверяемый факт или принятое решение. Макет, ТЗ, карточка Trello или черновик документа без runtime/approval не переводит запуск в зеленый.
