Первый runtime-срез service_session

Это короткая исполнительная карта поверх полного ТЗ. Она показывает минимальный кусок, который нужно реализовать или подтвердить первым, чтобы получить главный proof: тестовый заказ платной консультации без реального платежа и без реальной отправки писем.

1главный красный блокер
7минимальных связей для первого proof
0реальных платежей и писем
PASS/WARN/STOPформат приемки QA
PM-решение: не внедрять всю большую ERP/CRM-логику сразу. Первый срез должен доказать только базовую цепочку: order → service_session → вопрос → назначение → чат/ответ → события/no-send → support case → QA report. Все остальное после этого уточняется по фактам.

2Создать service_sessionПосле fake success создается сущность услуги: service_session_id, order_id, клиент, тип услуги, статус.Карточка консультации или блок внутри order.Видна связь order → service_session.не доказано
3Сохранить вопрос клиентаВопрос хранится в service_session или связанной таблице. Есть язык/локаль и время отправки.В карточке консультации и рабочем месте исполнителя.Вопрос не теряется и доступен исполнителю.не доказано

5Ответить в чатеИсполнитель открывает связанный чат и отправляет тестовый ответ. Клиент видит ответ как от экспертной анкеты.Admin chat / agent workspace + история сообщений.Ответ связан с service_session, а не просто с обычным dating-диалогом.не доказано

Acceptance criteria для закрытия первого proof

КритерийДоказательствоСтоп-условие
Есть test order без реального списания.Скрин/ID заказа + отметка test mode.Если заказ создается как обычное пополнение credits без услуги.
Есть service_session, связанная с order.Скрин/ID service_session + order_id.Если вопрос и чат живут отдельно от order.
Вопрос клиента виден исполнителю.Скрин карточки и workspace.Если вопрос надо искать вручную в сообщениях.
Исполнитель назначен и видит SLA.Скрин назначения и дедлайна.Если нет ответственного или срока.
Ответ связан с консультацией.Скрин чата + session/order context.Если это обычный message thread без контекста услуги.
События и no-send уведомления записаны.Event timeline + preview/log.Если нет доказательства статусов или отправляются реальные письма.
Support/problem state связан с услугой.Скрин тикета/статуса решения.Если support не видит order/session/chat/expert.
