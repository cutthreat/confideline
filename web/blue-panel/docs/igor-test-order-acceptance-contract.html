Контракт приемки для первого контрольного заказа

Эта страница переводит PM-задачу в проверяемый контракт для Игоря: какие красные gate-блокеры нужно закрыть, что считается готовым, какие доказательства нужны и что не принимается как результат.

без этого QA не стартуетбез реальных платежейприемка только по proof
Главное правило

Результат Игоря — не “реализовано”, а проверяемый safe route: test order → question → service session/task → assignment → chat answer → no-send events → support case → QA report.

Что не принимается

Устное подтверждение, скрин только одного экрана, заказ без вопроса, вопрос без заказа, чат без service session, реальные письма, реальные платежи или неотделенные test data.

Контракт приемки

PM-решение: Игорю можно переиспользовать текущие кирпичи Confideline: Order, Message/Conversation, admin MessageController, NotificationManager, Report. Но приемка идет только по сквозной связи, а не по наличию отдельных моделей.
IDБлокерЧто сделать / подтвердитьТекущая базаПринимается, еслиНе принимается, еслиProof для QA
AC01Safe test orderСоздать test/sandbox/mock заказ услуги без реального списания.models/Order.php, payment fields, admin OrderController.Есть order id, test marker, сумма, валюта, статус; real charge отсутствует.Используется реальный provider, непонятно test/real, нет order id.Скрин client success + admin order + отметка no real charge.
AC02Order → questionСвязать вопрос клиента с заказом, услугой, языком и клиентом.Order.data, Message/Conversation можно переиспользовать как базу.Из заказа открывается вопрос; из вопроса видно order/session.Вопрос хранится отдельно, QA вручную сопоставляет сущности.Скрин order/question с одним id/marker.
AC03Service session/taskПоказать единую карточку консультации или task поверх заказа.Order statuses есть; доменный слой консультации не доказан.Карточка связывает order, question, client, status, deadline, performer, chat, support.Есть только order или только chat без единой карточки услуги.Скрин admin queue/card.
AC04AssignmentНазначить эксперта/агента вручную на test session.User/profile/admin база; MessageController actions.Админ видит назначенного исполнителя; исполнитель видит свою задачу.Назначение только в тексте/comment, без роли/статуса/истории.Скрин назначения + workspace исполнителя.
AC05Expert/agent workspaceДать исполнителю задачу: вопрос, срок, контекст, чат, кнопка ответа.Admin chat workspace/handoff и MessageController могут быть базой.Ответ меняет статус session/task и виден клиенту/админу по правам.Исполнитель отвечает в обычный чат без связи с оплаченной консультацией.Скрин workspace, отправки ответа и результата у клиента.
AC06No-send eventsПисать события в журнал/preview без отправки реальных писем/push/SMS.NotificationManager, appMailer, user.tag=fake как возможная база.Для ключевых событий виден no_send marker, получатель, шаблон, переменные.Письма реально ушли, нет preview, нет delivery_mode/marker.Скрин event log + preview переменных.
AC07Support/failure stateСоздать обращение по test order: недовольство ответом или просрочка.Report/ReportController есть как база жалоб.Support видит order, session, chat, performer, причину и решение review_needed.Жалоба не связана с заказом/чатом/исполнителем.Скрин support card.
AC08Test data isolationОтделить test_run_id от реальных заказов, выплат, аналитики, support.Order.data и tagged users могут быть базой.test_run_id виден в order/session/events/support; есть фильтр или правило cleanup.Тестовые данные смешиваются с реальными метриками и выплатами.Скрин marker/filter + rollback note.
AC09Quality/compensation previewПоказать тестовое начисление/quality note без реальной выплаты.Order/balance/user база есть, compensation package описан.Видно, как ответ влияет на quality и test compensation preview.Есть только расчет в голове/таблице без связи с session.Скрин preview или admin note по session.

Минимальная последовательность сдачи

ШагЧто показывает ИгорьКто принимаетВердикт
1Safe order + test marker + no real charge.PM + QAЕсли нет — STOP, дальше не проверяем.
2Order связан с question и service session/task.PM + QAЕсли нет — FAIL основного маршрута.
3Admin route и assignment.PM + QAЕсли админ не видит, запуск операционно не готов.
4Workspace исполнителя и ответ клиенту.QAЕсли ответ не связан с session, консультация не доказана.
5No-send events и support case.QA + PMЕсли нет no-send/support, трафик запрещен.
6QA-report PASS/WARN/STOP.PMТолько после отчета обновляется launch readiness.
