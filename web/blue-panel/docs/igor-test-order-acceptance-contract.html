Контракт приемки первого контрольного заказа

Это не общий список пожеланий. Это проверяемый контракт для Игоря: что должно быть показано, что принимается, что не принимается и какой proof нужен, чтобы QA мог стартовать без догадок.

без этого QA не стартуетбез реальных платежейприемка только по proofFX08/FX09 = STOP
Главное правило

Результат Игоря — безопасный сквозной маршрут: контрольный заказ → question → service session/task → assignment → chat answer → no-send events → support case → QA report. Этот контракт напрямую закрывает FX08/FX09 и факты PF01-PF09.

Что не принимается

Устное подтверждение, скрин одного экрана, заказ без вопроса, вопрос без заказа, чат без консультации, реальные письма, реальные платежи или тестовые данные без маркировки.

Короткая карта AC01-AC09

AC01 · Безопасный тестовый заказ

Создать test/sandbox/mock заказ услуги без реального списания.

Приемка: Есть order id, test marker, сумма, валюта, статус; реальное списание отсутствует.
AC02 · Order → question

Связать вопрос клиента с заказом, услугой, языком и клиентом.

Приемка: Из заказа открывается вопрос; из вопроса видно order/session.
AC03 · Service session/task

Показать единую карточку консультации или task поверх заказа.

Приемка: Карточка связывает order, question, client, status, deadline, performer, chat, support.
AC04 · Assignment

Назначить эксперта/агента вручную на test session.

Приемка: Админ видит назначенного исполнителя; исполнитель видит свою задачу.
AC05 · Expert/agent workspace

Дать исполнителю задачу: вопрос, срок, контекст, чат, кнопка ответа.

Приемка: Ответ меняет статус session/task и виден клиенту/админу по правам.
AC06 · No-send events

Писать события в журнал/preview без отправки реальных писем/push/SMS.

Приемка: Для ключевых событий виден no_send marker, получатель, шаблон, переменные.
AC07 · Support/failure state

Создать обращение по контрольному заказу: недовольство ответом или просрочка.

Приемка: Support видит order, session, chat, performer, причину и решение review_needed.
AC08 · Test data isolation

Отделить test_run_id от реальных заказов, выплат, аналитики, support.

Приемка: test_run_id виден в order/session/events/support; есть фильтр или правило cleanup.
AC09 · Quality/compensation preview

Показать тестовое начисление/quality note без реальной выплаты.

Приемка: Видно, как ответ влияет на quality и test compensation preview.

Трассировка FX → AC → PF

PM-граница приемки: Игорь не сдает “кусок админки” отдельно. Он сдает proof-цепочку: фикстура или STOP-условие → acceptance criterion → факт в листе контрольного заказа. Если строка не закрывает PF, она не меняет готовность запуска.

PM-решение: Игорю можно переиспользовать текущие кирпичи Confideline: Order, Message/Conversation, admin MessageController, NotificationManager, Report. Но приемка идет только по сквозной связи, а не по наличию отдельных моделей.

Минимальная последовательность сдачи

1. Безопасный тестовый заказЕсли нет test marker и no реальное списание, дальше не проверяем.
2. Order + question + sessionЕсли вопрос не связан с заказом, основной маршрут не доказан.
3. Admin route + assignmentЕсли админ не видит маршрут, запуск операционно не готов.
4. Workspace + answerЕсли ответ не связан с session, консультация не доказана.
5. No-send + supportЕсли нет событий и problem state, трафик запрещен.
6. QA reportТолько после отчета обновляется готовность запуска.
