Карта связи фронта, backend и проверки

Эта страница показывает, как сопоставлять то, что нужно для запуска Nebula, с тем, что уже есть в дизайне Oracle/Nebula, backend Confideline, админке, контенте и проверочных отчетах. Она нужна, чтобы передавать Игорю не абстрактные идеи, а проверяемые задачи.

Решение PM

Сейчас проект нельзя оценивать одним статусом “готов/не готов”. Нужно смотреть по слоям: экран есть, backend есть, контент есть, админка управляет, проблемные состояния описаны, сквозная проверка пройдена. Если хотя бы один слой не доказан, статус остается желтым или красным.

дизайн и база есть сквозная связь не доказана перед рекламой нужен proof

Frontend Oracle/Nebula

Есть 14 экранных групп и 89 блоков из экранного контракта, плюс публичная верстка Nebula pages.

Backend Confideline

Есть платформа и админка как база: пользователи, сообщения, заказы, роли, страницы, support, email, bans и связанные модули.

Главный пробел

Не доказан единый путь: экран клиента связан с backend, админкой, событиями, поддержкой и проверкой.

Следующее действие

Каждую задачу Игорю формировать как screen contract: экран, backend, контент, состояния, acceptance, proof.

Как читать статус

1. Экранесть ли макет/верстка и ссылка на источник
2. Backendесть ли функция и админский маршрут
3. Контентготовы ли тексты, FAQ, legal, письма, переводы
4. Состоянияуспех, ошибка, пусто, нет оплаты, спор, просрочка
5. Proofесть ли скрин/отчет/test/no-send доказательство

Итог

Проект имеет серьезную базу, но готовность нужно доказывать по связкам. Самая важная следующая работа: пройти строки этой карты и для каждой красной/желтой функции сделать co2p-пакет для Игоря: экран, backend/admin, контент, состояния, тестовый proof. Только после этого можно говорить о переходе от PM-проектирования к внедрению и приемке.
