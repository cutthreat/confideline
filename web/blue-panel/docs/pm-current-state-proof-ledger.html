Главный вывод PM

Проект хорошо подготовлен как план, ТЗ и proof-хранилище. Но это еще не доказательство работы сервиса. Запуск клиентов и рекламы остается красным, пока нет реального сквозного runtime-теста: test order → вопрос → эксперт → ответ → support → события → отчет.

Как читать статус

Зеленый = можно использовать как основу. Желтый = PM-пакет есть, но нужна ревизия/внедрение/проверка. Красный = блокирует запуск клиентов или рекламы.

4слоя можно использовать как основу
5слоев подготовлены, но требуют внедрения или ревизии
7слоев блокируют запуск до runtime proof
1главный следующий proof: test order
Правило оценки: опубликованная страница Blue Panel или co2p-пакет доказывает, что задача продумана и готова к передаче. Она не доказывает, что функция работает на сайте. Функция становится зеленой для запуска только после runtime proof: скрин, лог, маршрут в админке, QA PASS/WARN/STOP или другое прямое подтверждение.

Что это означает для запуска

PM-решение: сейчас нельзя маркировать проект как готовый к клиентам или рекламе. Можно считать готовой PM-инфраструктуру и набор co2p-пакетов для передачи команде. Главная следующая работа — получить runtime proof тестового заказа и только затем запускать сквозной QA.

Следующие действия по порядку

ПорядокДействиеПочему первымКритерий закрытия
1Передать Игорю пакет test order / paid consultation.Без него нельзя проверить ни клиента, ни эксперта, ни support, ни события.Есть тестовый заказ без реального списания, видимый в админке.
2Проверить рабочее место эксперта на этом заказе.Нужно доказать, что 5 экспертов смогут реально работать.Эксперт/агент видит задачу, отвечает, статус меняется.
3Пройти support/failure state на том же заказе.Первые продажи всегда создают проблемы; support должен видеть контекст.Есть тикет с order/session/chat/expert и решением.
4Снять события/no-send журнал по тому же маршруту.Без статусов клиент и команда будут работать вслепую.Есть timeline и preview без реальных писем.
5Выполнить сквозной QA и опубликовать отчет.Только отчет дает право обсуждать малый трафик.Публичный PASS/WARN/STOP с задачами.
6Принять founder/legal/payment решения.Checkout и реклама не должны идти с placeholders.Утверждены entity/provider/descriptor/refund/geography.
7Только после этого решать go/no-go первого рекламного теста.Иначе мы покупаем жалобы, а не данные.Есть QA PASS, daily limit, stop-сигналы и метрики.
