Что отправить Игорю, чтобы получить runtime proof

Это не Trello-редактирование и не новая архитектура. Это готовый бриф для Игоря: один безопасный контрольный заказ, что показать, что вернуть, что считается accepted/rejected и куда QA заносит доказательства.

QA пока STOPможно отправлять как брифреальные платежи запрещеныреальные письма запрещены
PM-решение

Без этого результата нельзя запускать тестировщика и нельзя обсуждать первый трафик. Игорь должен вернуть не обещание, а ID, маршруты, скрины и подтверждение no real charge/no real send.

Граница

Если Игорь видит, что часть невозможно сделать на текущем backend, он должен вернуть конкретный STOP: какой AC не закрывается, почему и какая минимальная доработка нужна.

Копируемый текст запроса

Игорь, нужна одна проверяемая задача: показать безопасный контрольный заказ платной текстовой консультации Nebula/YouDate на текущем backend Confideline. Цель: QA должен получить один test order, который можно пройти от клиента до ответа исполнителя и support, без реального списания денег и без реальной отправки писем/сообщений. Что нужно показать: 1. Safe test order: order_id, сумма, валюта, test/sandbox/mock marker, подтверждение no real charge. 2. Order -> question: вопрос клиента связан с order_id, client_id, service/session/task id и языком. 3. Service session/task: одна карточка консультации связывает order, question, client, status, deadline, performer, chat, support, events. 4. Assignment: админ назначает эксперта/агента на test session, назначение видно в истории/статусе. 5. Workspace исполнителя: исполнитель под своей ролью видит вопрос, срок, контекст, поле ответа и отправляет ответ. 6. Answer visibility: ответ виден клиенту и админу, связан с session/task, есть answer_id/timestamp/author. 7. No-send events: события order/question/assignment/answer/support создаются в event log/preview, но реальные письма/SMS/push не уходят. 8. Support case: создан problem state по этому же заказу: reason, owner, decision/status, связь с order/session/chat/performer. 9. Test isolation: у всех сущностей есть test_run_id или другой marker, чтобы не смешивать тест с реальными продажами/выплатами/аналитикой. Что вернуть PM/QA: - test_run_id; - order_id; - question_id; - session/task id; - performer_id/profile_id; - answer_id; - support_case_id; - admin URL/route на order/session/support/event log; - скрины client view, admin order, admin session/task, performer workspace, answer, event log, support case; - короткое подтверждение: реальные платежи не запускались, реальные письма/сообщения не отправлялись. Accepted: - есть один сквозной marker/test_run_id; - заказ, вопрос, исполнитель, ответ, события и support связаны между собой; - QA может открыть маршруты без ручного поиска; - нет real charge и real send; - результат можно проверить скринами/логами. Rejected: - только устное “работает”; - один скрин без ID; - заказ без вопроса или вопрос без заказа; - чат без связи с оплаченной консультацией; - реальные платежи или реальные письма; - тестовые данные смешаны с реальными; - support case не связан с заказом. Ссылки: - Контракт приемки: https://cutthreat.github.io/confideline/web/blue-panel/docs/igor-test-order-acceptance-contract.html - Gate старта QA: https://cutthreat.github.io/confideline/web/blue-panel/docs/qa-start-readiness-checklist.html - Лист фиксации proof: https://cutthreat.github.io/confideline/web/blue-panel/docs/test-order-proof-capture-sheet.html

Что считается результатом

AcceptedЕсть один test_run_id, связаны order/question/session/performer/answer/events/support, QA открывает route, нет real charge/send.
RejectedУстное “работает”, один скрин без ID, real charge/send, вопрос без заказа, чат без консультации, тест смешан с real data.
Если невозможноВернуть STOP с номером AC, причиной и минимальной доработкой. Это тоже полезный proof, но не READY для QA.
