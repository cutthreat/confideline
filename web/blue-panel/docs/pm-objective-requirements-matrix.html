Большая PM-цель разложена на проверяемые требования

Эта страница нужна, чтобы не терять ни один слой задачи. Здесь видно: какие требования цели уже имеют надежную основу, какие частично закрыты документами, а какие требуют runtime proof перед запуском клиентов и рекламы.

4 зеленых7 желтых7 красныхцель не закрыта
PM-вывод

Инфраструктура управления уже есть. Но цель нельзя закрыть, пока красные runtime-требования не будут подтверждены фактами: контрольный заказ, админская видимость, экспертский ответ, support, no-send события, QA и готовность первых 5 экспертов.

Как использовать

Если требование желтое или красное, оно остается в работе. Если появляется новый proof, статус меняется только после ссылки на страницу, скрин, лог, CSV или QA-отчет.

4требований имеют рабочую основу
7требований частично закрыты
7требований блокируют завершение цели
0runtime QA PASS по платному пути
Правило завершения цели: цель может быть закрыта только когда по каждому требованию есть достаточный proof. Сейчас доказательная база полезна и структурирована, но не завершена.

Требования цели и статус

R01

Автономно собрать доказательную базу текущего состояния

желтый

Что есть: Есть Blue Panel, реестр доказательств, аудит PM-цели, screen/backend/content map, gate контрольного заказа, owner map.

Чего не хватает: Доказательная база еще не полная: runtime proof сайта, реальные QA-скрины, no-send log и допуск экспертов отсутствуют.

Следующий шаг: Продолжать сбор только через proof-страницы: каждый новый факт получает ссылку, статус и владельца.

Proof: pm-current-state-proof-ledger.html; pm-objective-completion-audit.html

R02

Backend Confideline

желтый

Что есть: Backend/admin принят как база проекта; есть карты admin/backend readiness и контракт контрольного заказа Игорю.

Чего не хватает: Нет доказанного end-to-end пути order -> question -> session -> assignment -> answer -> support -> events.

Следующий шаг: Закрыть AC01-AC09 на контрольном заказе.

Proof: backend-admin-readiness-map.html; igor-test-order-acceptance-contract.html

R03

Frontend/design Oracle/Nebula

желтый

Что есть: Есть карта экранов/сценариев и понимание frontend поверх Confideline backend.

Чего не хватает: Не все макеты и сверстанные страницы сопоставлены с backend-функцией, контентом, пустыми/ошибочными состояниями и QA.

Следующий шаг: Довести каждый ключевой экран по формуле: экран -> backend -> контент -> состояние -> proof.

Proof: screen-backend-content-control.html; anton-oracle-nebula-design-fixes.html

R04

Trello как источник задач месяца

желтый

Что есть: Есть план июня, факт-статус Trello и правило: текущие названия карточек не менять без команды.

Чего не хватает: Не все карточки имеют фактический результат внедрения; часть является постановкой или PM-пакетом.

Следующий шаг: После выполнения карточки добавлять ссылку на Blue Panel, не подменяя исходную постановку.

Proof: june-plan.html; trello-june-fact-status.html; june-card-fact-readiness.html

R05

Blue Panel как инфраструктура контроля

зеленый

Что есть: Панель опубликована, есть главный маршрут, страницы для Алексея, стратегии, июня, готовности, доказательств, аудит ссылок.

Чего не хватает: Требуется поддерживать актуальность после каждого изменения, иначе панель снова станет устаревшей.

Следующий шаг: Каждый PM-результат публиковать как страницу/CSV и проверять ссылки перед внешней ссылкой.

Proof: index.html; alexey-master-plan.html; blue-panel-link-audit.html

R06

Документы, legal, policy, disclaimer, checkout wording

желтый

Что есть: Есть структура public docs и legal/checkout пакета.

Чего не хватает: Финальные тексты зависят от legal seller, payment provider, descriptor, refund window и launch geography.

Следующий шаг: Готовить HTML-ready пакет, но не публиковать финал до founder/legal/payment gate.

Proof: legal-docs-readiness.html; legal-content-package.html; co2p-legal-checkout-public-docs.html

R07

Обучение и школа экспертов

желтый

Что есть: Материалы обучения извлечены, собраны школа v1, регламент и задача Ксении на ревизию.

Чего не хватает: Нет финальной ревизии, тестовых результатов и подтверждения, что обучение применимо на ответах первых экспертов.

Следующий шаг: Провести ревизию, проверить пробные ответы и обновить регламент по факту.

Proof: expert-training-materials-register.html; expert-school-v1-operational-pack.html; ksenia-expert-school-review-task.html

R08

Первые 5 экспертов

красный

Что есть: Есть журнал допуска и процесс ручного допуска.

Чего не хватает: Нет заполненного допуска каждого эксперта: тест, пробный ответ, качество, SLA, решение о допуске.

Следующий шаг: Заполнить журнал по каждому из 5 экспертов и присвоить готов/доработка/не допущен.

Proof: first-five-expert-admission-journal.html

R09

Экспертский/агентский контур

красный

Что есть: Есть handoff рабочего места эксперта/агента.

Чего не хватает: Нет доказательства, что исполнитель реально получает задачу, видит вопрос/срок и отправляет ответ в системе.

Следующий шаг: Проверить workspace на контрольном заказе.

Proof: expert-agent-workspace-handoff.html; co2p-expert-agent-workspace-service-session.html

R10

Клиентский путь платной консультации

красный

Что есть: Путь описан и есть QA/handoff для контрольного заказа.

Чего не хватает: Нет фактического прохода: оффер -> checkout -> вопрос -> ожидание -> ответ -> support/follow-up.

Следующий шаг: Запускать контрольный заказ только после READY gate.

Proof: test-order-readiness-gate.html; qa-test-order-execution-brief.html

R11

Админка и операционная видимость

красный

Что есть: Есть admin/backend maps и список обязательных proof-точек.

Чего не хватает: Не доказано, что админ видит один заказ во всех нужных местах без ручного поиска.

Следующий шаг: Снять proof по order, question, session, assignment, chat, events, support.

Proof: backend-admin-runtime-gap-matrix.html; backend-admin-readiness-map.html

R12

Support, тикеты, просрочки, возвраты

красный

Что есть: Есть support/refund launch control и problem acceptance matrix.

Чего не хватает: Нет рабочего support-case, связанного с заказом, чатом, экспертом и решением.

Следующий шаг: Смоделировать просрочку или недовольство клиента в рамках test order.

Proof: support-refund-launch-control.html; support-problem-acceptance-matrix.html

R13

Email, уведомления, рассылки, no-send

желтый

Что есть: Есть пакет событий, уведомлений и no-send proof matrix.

Чего не хватает: Нет журнала событий на одном контрольном заказе; реальные письма запрещены.

Следующий шаг: Проверить no-send события order/question/assignment/answer/support/follow-up.

Proof: events-notifications-launch-control.html; nosend-event-proof-matrix.html; email-notifications-handoff.html

R14

QA перед трафиком

красный

Что есть: Есть QA brief, template, public report shell и evidence naming.

Чего не хватает: Нет фактического QA PASS/WARN/STOP по рабочему сайту.

Следующий шаг: После READY gate провести QA и опубликовать отчет.

Proof: qa-test-order-execution-brief.html; test-order-runtime-public-report-shell.html

R15

Маркетинг, первый трафик, LTV/CAC

красный

Что есть: Есть go/no-go логика, stop-сигналы и рамка первого теста.

Чего не хватает: Нет QA PASS, capacity proof 5 экспертов, legal/payment решений и подтвержденной экономики.

Следующий шаг: Готовить материалы, но не покупать трафик до контрольного заказа и пересчета готовности.

Proof: co2p-marketing-first-traffic-gonogo.html; launch-before-traffic-action-plan.html

R16

Классификация красный/желтый/зеленый

зеленый

Что есть: Светофор есть в PM audit, launch readiness, proof ledger, этой матрице и CSV.

Чего не хватает: Статусы должны меняться только по новым фактам, а не по ожиданиям.

Следующий шаг: После каждого proof обновлять все связанные светофоры.

Proof: pm-objective-completion-audit.html; launch-readiness-master-control.html

R17

Выявить пробелы и блокеры

зеленый

Что есть: Есть red route, owner map, current next action board, team action queue.

Чего не хватает: Часть блокеров требует runtime-доказательств от Игоря/QA, PM не может закрыть их только документами.

Следующий шаг: Двигаться по красному маршруту до снятия STOP gate.

Proof: red-route-execution-plan.html; red-blockers-owner-map.html; current-next-action-board.html; team-action-queue.html

R18

Понятный мастер-план с proof-ссылками и next steps

зеленый

Что есть: Есть страница для Алексея, план июня, готовность запуска, ближайшие действия и proof ledger.

Чего не хватает: Мастер-план остается живым: после runtime QA нужно пересчитать месяцы и статусы.

Следующий шаг: После контрольного заказа обновить мастер-план и Trello-факт.

Proof: alexey-master-plan.html; june-plan.html; launch-readiness-master-control.html
