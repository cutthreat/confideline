Матрица требований большой PM-цели

Это прямая сверка исходной задачи с текущим состоянием проекта. Каждая строка показывает: требование, что уже доказано, чего не хватает и какой следующий шаг нужен.

6 зеленых6 желтых10 красныхцель активна
Главный вывод

PM-инфраструктура, мастер-план, классификация и proof-порядок уже собраны. Но цель нельзя закрыть, пока runtime-слои не подтверждены фактами: safe order, E01-E05, no-send, support, QA, analytics и решения владельца.

Как использовать

Если требование красное или желтое, оно остается в работе. Зеленый PM-статус не означает, что сайт готов к клиентам, если требование относится к runtime.

Требования цели

REQ01

Автономно собрать доказательную базу текущего состояния

Доказано: Есть Blue Panel, светофор, proof-control, индекс покрытия, quality map и daily control.

Не хватает: Нет runtime-доказательств сайта: safe order, no-send, support, QA, E01-E05.

Дальше: Продолжать сбор только через accepted proof и владельцев.

 REQ02

Backend Confideline как база сервиса

Доказано: Есть backend/admin gates, capture sheets и запрос R01 Игорю.

Не хватает: Нет order_id/question/session/assignment/answer/admin/support/events на одном marker.

Дальше: Получить R01 safe test order от Игоря.

 REQ03

Frontend/design Oracle/Nebula

Доказано: Есть design/source coverage, screen contracts и правило экран -> backend -> content -> QA.

Не хватает: Нет принятого screen-by-screen proof по критичному paid-flow.

Дальше: Закрывать критичные экраны через screen contract.

 REQ04

Trello как источник задач и правок

Доказано: Есть план июня, Trello fact status и правило: названия карточек не менять.

Не хватает: Не все карточки имеют result proof и актуальный accepted статус.

Дальше: Результаты вести ссылкой Blue Panel после приемки.

 REQ05

Blue Panel как центр управления

Доказано: Главная, Для Алексея, статус, proof, качество proof, контракты, owners, daily control опубликованы.

Не хватает: Нужно поддерживать актуальность после каждого accepted/returned/blocked.

Дальше: Обновлять панель как источник состояния запуска.

 REQ06

Документы, policy, disclaimer, checkout wording

Доказано: Есть public docs/checkout contracts и понимание нужных текстов.

Не хватает: Нет founder/legal/payment decisions: seller, provider, descriptor, refund, geography.

Дальше: Готовить HTML-ready пакет, финал после decisions.

 REQ07

Обучение и школа экспертов

Доказано: Есть школа v1, регламент, материалы Nebula/PbExpert, scorecard.

Не хватает: Нет accepted прохождения и пробного ответа по E01-E05.

Дальше: Получить R02/E01 и затем E01-E05 admission proof.

 REQ08

Первые 5 экспертов

Доказано: Есть gate, journal и proof contract допуска.

Не хватает: 0/5 экспертов accepted фактами.

Дальше: Минимум E01 accepted для QA; E01-E05 для первого трафика.

 REQ09

Экспертский/агентский рабочий контур

Доказано: Есть workspace handoff и runtime proof register.

Не хватает: Не доказано назначение задачи и ответ исполнителя внутри системы.

Дальше: Проверить assignment/answer/workspace на safe order.

 REQ10

Клиентский путь платной консультации

Доказано: Путь и paid-flow contract описаны.

Не хватает: Нет фактического прохода offer -> order -> question -> answer -> support.

Дальше: Пройти контрольный заказ после READY.

 REQ11

Админка и операционная видимость

Доказано: Есть admin visibility contract и capture sheet.

Не хватает: Нет скринов/логов admin route по одному заказу.

Дальше: Включить admin timeline в R01 и QA.

 REQ12

Support, тикеты, просрочки, жалобы, возвраты

Доказано: Есть support/failure contracts и problem state packages.

Не хватает: Нет support_case_id/owner/decision/closure по order_id.

Дальше: Включить problem state в контрольный заказ.

 REQ13

Email, уведомления, рассылки, no-send

Доказано: Есть no-send gate и матрица обязательных событий.

Не хватает: Нет event_id/preview/external_send=false на safe order.

Дальше: Проверить no-send events без реальной отправки.

 REQ14

QA перед трафиком

Доказано: Есть QA contract, runbook и report shell.

Не хватает: Нет PASS/WARN/STOP по рабочему сайту.

Дальше: Запуск QA только после accepted R01/R02.

 REQ15

Маркетинг, первый трафик, CAC/LTV

Доказано: Есть traffic preflight, stop-сигналы и CAC/LTV рамка.

Не хватает: Нет QA, capacity 5 экспертов, purchase analytics, docs/payment decisions.

Дальше: Готовить материалы, paid traffic budget = 0.

 REQ16

Классификация красный/желтый/зеленый

Доказано: Есть светофор, readiness map, quality proof map и правило “документ не равен runtime”.

Не хватает: Статусы должны пересчитываться после новых фактов.

Дальше: Менять только затронутый слой по accepted proof.

 REQ17

Выявить пробелы, блокеры и владельцев

Доказано: Есть owner proof board, blocker register, escalation/waiting logic.

Не хватает: Красные блокеры сохраняются до внешнего proof.

Дальше: Вести R01/R02 -> QA-ready -> QA report.

 REQ18

Понятный мастер-план с proof-ссылками

Доказано: Есть “Для Алексея”, план июня, статус запуска, proof links и главный маршрут.

Не хватает: После QA потребуется пересчет месяцев и запуска.

Дальше: Использовать для разговора с Заказчиком, обновлять по фактам.

 REQ19

Автономная работа PM

Доказано: Есть autonomous workqueue, daily control и правило не дергать пользователя без real blocker.

Не хватает: Автономность не заменяет Игоря, QA, Ксению и founder decisions.

Дальше: Закрывать подготовку и не симулировать runtime.

 REQ20

Качество доказательств и защита от самообмана

Доказано: Есть стандарт доверия L1-L8 и quality-by-layer map.

Не хватает: Runtime-слои все еще требуют L1/L2 proof.

Дальше: Оценивать каждый новый результат по качеству proof.

 REQ21

Передача задач Игорю, Антону, Ксении, QA

Доказано: Есть co2p/handoff pages, dispatcher, owner board и copy requests.

Не хватает: Не все handoff приняты исполнителями и не все привязаны к runtime proof.

Дальше: Передавать только с expected result, acceptance и proof link.

 REQ22

Итоговая готовность MVP запуска

Доказано: Go/No-Go условия и чек-лист тестового запуска описаны.

Не хватает: Нет accepted safe order, E01-E05, QA, docs/payment, analytics.

Дальше: R01/R02, затем QA-ready, затем пересчет checklist.

Правило: документ, макет, Trello-карточка или PM-вывод не закрывают runtime-требование. Для клиентского пути, оплаты, эксперта, support, уведомлений, аналитики и трафика нужен L1/L2 proof.
