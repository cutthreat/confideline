Support/problem state · до трафика

Один проблемный заказ должен быть пройден и доказан до рекламы

Для запуска недостаточно доказать успешный заказ. Нужно проверить, что команда видит проблему, связывает ее с заказом и экспертом, принимает решение, уведомляет клиента в безопасном режиме и закрывает кейс.

сейчас proof = 0готовим сценарий для Игоря и QAреальные refund/email запрещены
PM-решение

Первым проблемным сценарием берем “клиент недоволен ответом или эксперт просрочил ответ”. Это самый прикладной риск для старта с 5 экспертами.

Почему это важно

Если problem-state не работает, первый платный трафик быстро превращается в ручной хаос: клиент недоволен, support не видит связку заказа, эксперт не получает задачу, PM не видит причину.

Путь проблемного заказа

1. Есть заказНужен safe order id, клиент, услуга, эксперт/анкета, сессия и вопрос.
2. Возникла проблемаПросрочка, плохой ответ, жалоба клиента или запрос на доработку.
3. Support видит кейсКейс должен открываться из заказа или иметь явную связку с заказом.
4. Есть владелец решенияНазначен support/админ/PM, выбран retry, escalation, credit или refund review.
5. Клиент получает статусСоздается no-send событие/preview, но реальные письма не отправляются.
6. Кейс закрытЕсть итог, причина, дата, владелец, влияние на качество эксперта и QA verdict.

Go / no-go

Нельзя включать рекламу: если support-кейс нельзя создать из заказа, нельзя назначить владельца, нет no-send уведомления, нет решения и закрытия.
Можно идти к первому QA-заказу: когда Игорь подтвердит safe order route, есть минимум один допущенный эксперт, и этот problem-state сценарий готов к проходу тестировщиком.
