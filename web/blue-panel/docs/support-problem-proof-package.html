Один проблемный заказ должен быть доказан до рекламы

Успешный заказ не доказывает готовность сервиса. До трафика нужно пройти проблемный сценарий: клиент недоволен, эксперт опоздал, уведомление не сработало или возник вопрос по компенсации. Support должен видеть контекст, принять решение и закрыть кейс без ручного хаоса.

PM-решение

Минимальный сценарий для первого QA: “клиент недоволен ответом” или “эксперт просрочил ответ”. Это самый вероятный риск старта с 5 экспертами.

Что считается доказательством

Есть safe order id, связка с чатом и экспертом, созданный support case, владелец, решение, no-send уведомление, закрытие кейса и строка в QA/proof отчете.

Не утверждаем сейчас: реальные refund rules, платежные возвраты и юридические формулировки. Это отдельный founder/legal/payment gate.

Маршрут проблемного заказа

1. ЗаказЕсть safe/test order id, клиент, услуга, вопрос и исполнитель.
2. ПроблемаПросрочка, плохой ответ, жалоба, сбой чата или вопрос по компенсации.
3. КейсSupport видит карточку проблемы, связанную с заказом и чатом.
4. ВладелецНазначен support/админ/PM и выбран тип решения.
5. КлиентКлиент получает понятный статус через no-send preview без реальной отправки.
6. ИтогКейс закрыт, последствия для качества/эксперта/отчета зафиксированы.

Минимальный сценарий для первого QA

Рекомендуемый сценарий

Эксперт дал слабый ответ или опоздал. Клиент открывает обращение. Support видит заказ, чат, эксперта, причину, назначает владельца, выбирает do-over/retry/review, создает no-send уведомление и закрывает кейс.

Что нельзя подменять

Нельзя считать готовностью обычную переписку в админке, отдельную жалобу без заказа, устный refund promise, реальную отправку письма или реальный возврат денег.
