Текущий PM-маршрут

Получить два proof-входа и запускать QA только после READY

Ближайшая неделя строится вокруг простого порядка: отправить запросы Игорю и Ксении, принять ответы через accepted / returned / blocked, закрыть READY gate и только потом запускать QA контрольного заказа.

Игорь + Ксения сейчас QA только после READY Трафик запрещен Реальные платежи и письма запрещены

Состояние недели

2
proof-запроса сейчас
3
исхода ответа
1
QA-start gate
0
accepted runtime proof
Если нет accepted proof, статус не улучшается. Новый документ, макет или обсуждение не заменяет реальное подтверждение работы сайта.

Маршрут выполнения

D1
Отправить proof-запросыИгорю по runtime/backend, Ксении по допуску экспертов.
Proof: отправленные запросы или ссылка на страницу выдачи задач.
PM → команда
D2
Принять ответы через proof-inboxКаждый ответ получает статус accepted, returned или blocked.
Proof: заполненная строка в журнале приема с причиной решения.
PM
D3
Если Игорь accepted: проверить QA-start gateНужны route, order id, session/question binding, answer, no-send log.
Proof: QSP/AC accepted без критичных дыр.
PM + Игорь
D4
Если Ксения accepted: назначить исполнителя для QAМинимум один эксперт должен быть реально допущен к контрольному заказу.
Proof: expert admission accepted по E01 или другому конкретному исполнителю.
PM + Ксения
D5
Подготовить no-send и supportКонтрольный заказ не должен отправлять реальные письма клиентам и должен иметь support/failure след.
Proof: no-send и support/refund acceptance rows готовы к проверке.
PM + Игорь + QA
D6
Запустить QA только после READYДо READY тестировщик не получает задачу на реальный проход.
Proof: QA-запрос выдан после accepted gate, не раньше.
PM → QA
D7
QA проходит контрольный заказОдин полный путь: выбор, оплата/симуляция, вопрос, назначение, ответ, support.
Proof: публичный отчет QA со статусом PASS / WARN / STOP.
QA
D8
Пересчитать светофор запускаОбновить красный / желтый / зеленый статус по фактам, а не ожиданиям.
Proof: обновленная readiness-страница и proof ledger.
PM
D9
Параллельно: довести всех 5 экспертовДля QA нужен минимум один; для первого трафика нужны все пять.
Proof: accepted rows E01-E05 и capacity rows CAP01-CAP05.
PM + Ксения
D10
Параллельно: сверить дизайн и backend-контрактыАнтон/design: что есть на макетах, что есть на backend, какой контент нужен.
Proof: screen/backend/content rows без “по памяти”.
PM + Антон
D11
Параллельно: подготовить legal/payment пакетPM готовит варианты и тексты, но не утверждает юридические и платежные решения.
Proof: HTML-ready пакет без статуса approval.
PM
D12
Параллельно: маркетинг только preflightОфферы, лендинги, email и аналитика готовятся, но трафик не запускается.
Proof: preflight checklist, без spend и без live traffic.
PM

Параллельные линии недели

Игорь

Дать доказательства backend/admin пути контрольного заказа: заказ, сессия, вопрос, ответ, no-send, support/failure.

Ксения

Подтвердить допуск минимум одного эксперта для QA и постепенно довести всех 5 экспертов до accepted.

Антон / дизайн

Сверить макеты Oracle/Nebula с backend-возможностями и контентом, без смешивания с текущим старым frontend.

PM

Держать Blue Panel как панель решений: факт, proof, статус, следующий шаг. Не превращать ее в архив мусора.
