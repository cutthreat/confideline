Как PM ведет проект каждый день, чтобы запуск не развалился

Эта страница фиксирует рабочий цикл PM: что проверять утром, что контролировать днем, что закрывать вечером, когда писать в Trello, когда дергать команду и какой proof нужен для смены статуса.

утро / день / вечерweekly Trello updateтрафик только после proof
Правило PM

PM не ждет, пока кто-то вспомнит о задаче. Если факт можно собрать самому — собирает. Если нужен Игорь, QA, Ксения, Антон или основатель — формулирует конкретный запрос, какой proof нужен и почему это влияет на запуск.

Правило Trello

В Trello не писать технический шум. Комментарий нужен, когда есть важное изменение, блокер, weekly update или готовый результат со ссылкой на Blue Panel.

12контрольных действий PM
2ежедневные точки: утро и вечер
1weekly update по понедельникам
1месячный отчет в конце месяца
Главный фокус: весь daily cycle подчинен одному proof-маршруту: safe test order → admin route → workspace → no-send → support case → QA verdict → решение по первому трафику.

Цикл контроля

D01Состояние июньского планаКаждое утро · PMПроверяем: Какие задачи в работе, какие должны получить proof сегодня, какие стоят без движения.Красный сигнал: Задача влияет на контрольный заказ и не имеет владельца/следующего шага.Действие: Зафиксировать next action в Blue Panel; если работа у команды — подготовить короткий ping владельцу. D02Красные блокеры MVPКаждое утро · PMПроверяем: Safe test order, question binding, workspace, admin visibility, no-send, support, experts, QA verdict.Красный сигнал: Любой P1-блокер без текущего владельца или acceptance proof.Действие: Обновить backlog/очередь команды и подготовить конкретную задачу владельцу. D03Игорь / backend-admin runtimeКаждое утро · PM + ИгорьПроверяем: Есть ли safe order proof, admin route, assignment, workspace, event log, support case.Красный сигнал: Нет ответа/артефакта по AC, который блокирует QA test order.Действие: Подготовить короткий acceptance checklist и запросить ровно недостающий proof. D04Эксперты и КсенияКаждое утро · PM + КсенияПроверяем: Есть ли статус каждого из 5 экспертов: обучение, тест, пробный ответ, допуск/доработка/стоп.Красный сигнал: Эксперт должен быть готов к тестовому запуску, но нет допуска или причины.Действие: Обновить журнал допуска; Ксении давать только ревизию понятности/практичности, не экспертный анализ вместо PM. D05Антон / дизайнКаждое утро · PM + АнтонПроверяем: Какие экраны/состояния нужны под paid flow: offer, checkout, question, chat, result, support, profile.Красный сигнал: Экран нужен для контрольного заказа или доверия до оплаты, но нет макета/правки/контента.Действие: Формировать правку как сценарий: что видит клиент, что делает backend, какой текст, какой QA. D06Входящие факты и proofВ течение дня · PMПроверяем: Появились ли новые скрины, ссылки, ответы команды, CSV, QA report, runtime logs.Красный сигнал: Факт пришел, но не привязан к области, статусу и следующему шагу.Действие: Классифицировать факт: green/yellow/red, обновить соответствующую страницу и ссылку. D07Сдвиг по контрольному заказуКаждый вечер · PMПроверяем: Стало ли ближе к QA: gate READY, order id, assignment, answer, no-send, support case.Красный сигнал: День прошел, а главный blocker route не сдвинулся и нет причины.Действие: Обновить status summary; если нужен человек — сформулировать конкретный запрос без лишней переписки. D08Светофор запускаКаждый вечер · PMПроверяем: Нужно ли пересчитать green/yellow/red после новых proof.Красный сигнал: Статус выглядит зеленым без runtime proof или противоречит карте состояния.Действие: Не завышать готовность. Менять статус только по proof. D09Weekly Trello updateПонедельник · PMПроверяем: По карточкам в работе: процесс идет/стоит, проблема, кого ждем, что изменилось, ссылка на результат.Красный сигнал: Карточка в работе неделю без понятного прогресса или причины.Действие: Подготовить короткий weekly comment по стандарту Заказчика. D10co2p-пакетПеред передачей Игорю · PMПроверяем: Есть бизнес-смысл, макет/HTML/экран, backend-связь, acceptance criteria, QA-документ, proof page.Красный сигнал: Задача отдается программисту без макета, критериев или QA-проверки.Действие: Дособрать пакет до состояния передачи; если невозможно — отметить блокер. D11QA стартПеред QA · PM + QAПроверяем: Gate READY: safe order, route, роли, no-send, support, доступ тестировщика, ожидаемый результат.Красный сигнал: QA хотят запускать без safe order или без понятного expected result.Действие: Не запускать QA; вернуть в gate с конкретным STOP. D12Отчет ЗаказчикуКонец месяца · PM + АлексейПроверяем: По каждой задаче: выполнена/частично/не выполнена, причина, ссылка на результат, общий процент.Красный сигнал: Нет доказательства результата или причина невыполнения не зафиксирована.Действие: Собрать месячный отчет строго в конце месяца/первый день нового месяца.

Когда PM должен дергать Алексея

Дергать нужно только по настоящим decision blockers: доступы к закрытым источникам, legal/payment/founder decisions, противоречие с Заказчиком, невозможность получить runtime proof от команды, риск сорвать июньский план или запуск. Все остальное PM закрывает сам: реестры, proof-карты, постановки, QA-документы, Blue Panel, формулировки, сверки и подготовку задач.
