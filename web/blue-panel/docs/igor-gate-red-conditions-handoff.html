Что нужно закрыть Игорю до первого QA test order

Эта страница сужает общий test order до красных условий gate. Если эти пункты не закрыты, QA не стартует, потому что есть риск реального платежа, реальных писем или недоказуемого результата.

критично до QAбез real paymentsproof обязателен
Что дать Игорю

Не весь мастер-план, а эту страницу + gate + короткую страницу первого задания. Результат Игоря должен быть либо proof, либо точный STOP-блокер.

Что не принимать

Фразы “это можно сделать”, “примерно есть”, “посмотрим на тесте”. До QA нужны скрины, route, marker test/no-send или явный список того, что еще не готово.

Короткая постановка

Результат для Игоря: подготовить безопасный runtime-контур, где тестовый заказ создает консультацию без реального списания, без реальной отправки писем, с видимостью в админке, вопросом клиента, задачей эксперта/агента, чат-ответом, support-сценарием и test-data marker.

Красные условия gate

IDЧто закрытьКак должно работатьПриемкаProofСтатус
IR01
TG01		Сделать или подтвердить safe test order
QA нельзя запускать при риске реального списания.		Order создается в test/sandbox/mock режиме, без обращения к реальному платежному провайдеру.Есть order id, test marker, сумма, валюта; видно, что real charge не создан.Скрин клиента success + admin order + журнал/лог отсутствия real charge.критично до QA
IR02
TG02		Сделать no-send режим уведомлений
Запрещено отправлять реальные письма/push/SMS во время QA.		События пишутся в журнал и preview, но не уходят реальным получателям.Для order/question/assignment/answer/support виден delivery_mode=no_send или эквивалентный marker.Скрин event log + preview переменных + отсутствие delivery.критично до QA
IR03
TG04		Показать админскую видимость заказа
Если админ не видит весь маршрут, PM/QA не смогут доказать управляемость услуги.		Из админки видны order, question, session/task, assignment, chat, events, support.Админ открывает тестовый заказ и без ручного поиска переходит к связанным сущностям.Скрины admin route/карточки/связанных блоков.критично до QA
IR04
TG06		Связать вопрос клиента с заказом
Вопрос не должен жить отдельно от заказа, иначе эксперт не получает понятную услугу.		Question хранит связь с order/service_session/client/language/topic.Из order открывается question; из question открывается consultation/session/task.Скрин связки order → question → session/task.критично до QA
IR05
TG07		Показать задачу эксперта/агента
Первые 5 экспертов не смогут работать, если task не появляется в рабочем контуре.		Исполнитель видит назначенную консультацию, срок, вопрос, контекст, чат, кнопку ответа.Ответ исполнителя меняет статус session/task и виден клиенту/админу по правам.Скрин workspace исполнителя + чат + статус после ответа.критично до QA
IR06
TG08		Подготовить один support/failure state
Без проблемного сценария запуск не готов к первому недовольному клиенту.		Можно создать ticket/report по test order/session/chat/expert с причиной и решением.Support видит связанную карточку и может поставить статус решения без реального refund.Скрин support ticket с order/session/chat/expert.подготовить до QA
IR07
TG10		Отделить тестовые данные от реальных
Тестовые заказы не должны попадать в реальные продажи, выплаты, LTV и customer support статистику.		У test order/session/events/tickets есть marker или фильтр test/real.Админ может отфильтровать test data; cleanup/архивация понятны после QA.Скрин filter/marker test data и правило rollback.подготовить до QA

Минимальный порядок выполнения

#ПорядокПочему так
1Safe test order + test markerСначала исключаем production-риск платежа и смешение тестовых данных.
2Order → question → session/taskДальше доказываем, что покупка превращается в услугу, а не просто в запись заказа.
3Admin visibility + expert workspaceПосле появления услуги доказываем, что команда и исполнитель могут с ней работать.
4No-send eventsСобытия проверяем без реальной отправки клиентам/экспертам.
5Support/failure stateПроблемный сценарий нужен до рекламы, но он опирается на уже существующий order/session.
