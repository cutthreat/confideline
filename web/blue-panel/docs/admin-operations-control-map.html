Какая админка нужна, чтобы первые продажи не стали ручным хаосом

Эта карта собирает в один контур все, что админ, support, PM и QA должны видеть и контролировать до запуска трафика: заказ, вопрос, исполнитель, SLA, чат, жалобы, уведомления, качество, видимость, языки, начисления и аналитику.

9 красных6 желтыхruntime proof пока нет
PM-вывод

Наличие backend и вкладок в админке не равно готовности сервиса. Для запуска нужна управляемая операционная цепочка: команда видит, где находится каждая консультация, кто отвечает, что просрочено, где жалоба, что ушло в уведомления и какие последствия для качества/начислений.

Граница P0

Для первых 5 экспертов не нужен идеальный отдельный кабинет. Достаточно admin-based рабочего места по ролям, если оно закрывает маршрут консультации и дает QA proof.

0QA proof по runtime админке
Правило готовности: если админ должен вручную искать заказ, вопрос, исполнителя, чат, событие или жалобу в разных местах и догадываться о состоянии услуги, запусковый admin-контур не готов.

Операционные зоны

A01Единая карточка консультацииИгорь + PMДолжно быть: Заказ, клиент, вопрос, исполнитель, срок, чат, события, support, начисление и итог в одном route.Не хватает: Нет proof единой карточки paid consultation lifecycle.Следующий шаг: На safe test order показать одну карточку/route, где виден весь путь. A02Очередь новых заказов и заказов без вопросаИгорь + SupportДолжно быть: Новые test/paid заказы, источник, цена, статус оплаты, вопрос есть/нет, следующий шаг.Не хватает: Нет runtime статуса “ожидает вопроса” и no-send reminder preview.Следующий шаг: Проверить на test order: заказ создан, вопрос отсутствует, support видит очередь. A03Назначение эксперта или агентаИгорь + админДолжно быть: Ручное/автоматическое назначение исполнителя с учетом доступности, языка, нагрузки, анкеты и SLA.Не хватает: Нет proof назначения исполнителя на конкретную консультацию.Следующий шаг: Показать назначение на test order и запуск срока ответа. A04Рабочее место исполнителяИгорь + QAДолжно быть: Исполнитель видит свои задачи, вопрос, чат, срок, подсказки, базу знаний, статус и замечания.Не хватает: Нет runtime proof под ролью эксперта/агента.Следующий шаг: Проверить workspace на test order под ролью исполнителя. A05Контроль сроков и SLAИгорь + SupportДолжно быть: Дедлайн, soon overdue, overdue, escalated, переназначить, удержать начисление, уведомить.Не хватает: Нет SLA-таймера/очереди просрочки на runtime.Следующий шаг: Смоделировать просрочку test order и проверить очередь. A06Support и problem statesSupport + QA + PMДолжно быть: Проблема связана с заказом, чатом, исполнителем, причиной, решением и уведомлением.Не хватает: Нет runtime support case.Следующий шаг: Смоделировать одну проблему: эксперт не ответил или клиент недоволен. A07No-send события и уведомленияИгорь + QAДолжно быть: Каждый шаг пишет событие и показывает preview письма/уведомления без реальной отправки.Не хватает: Нет no-send log на одном заказе.Следующий шаг: Снять event log: заказ, вопрос, назначение, дедлайн, ответ, support, follow-up. A08Качество ответа и ревизияPM + Ксения + QAДолжно быть: Оценка ответа по рубрике: срок, полнота, тон, безопасность, запреты, продажа, жалоба.Не хватает: Нет review queue и проверки реального/пробного ответа.Следующий шаг: Оценить один пробный ответ и показать последствия. A09Модерация, предупреждения и баныPM + ИгорьДолжно быть: Warning, hide, visible ban, shadow restriction, reason, audit log, связь с консультацией/ответом.Не хватает: Нет связи violation → paid consultation → expert visibility/quality.Следующий шаг: Сформировать sanction flow и проверить на тестовом нарушении. A10Ранжирование и поднятие экспертовPM + Игорь + основательДолжно быть: Формула видимости: качество, SLA, конверсия, жалобы, доступность, manual boost, freeze, anti-abuse.Не хватает: Нет P0 формулы и admin override.Следующий шаг: Собрать ranking decision model: что автоматом, что вручную, что запрещено. A11Языки и переводыPM + ИгорьДолжно быть: Язык клиента, язык эксперта, язык ответа, перевод, качество перевода, кто отвечает за ошибку.Не хватает: Нет P0-решения по языкам запуска и хранению language fields.Следующий шаг: Определить US/UK English-first P0 и правила перевода после test order. A12Начисления, удержания и выплатыPM + основательДолжно быть: Preview начисления по консультации, hold, bonus, deduction, dispute, payout status.Не хватает: Нет тестового начисления на закрытом заказе.Следующий шаг: После test order показать начисление без реальной выплаты. A13Аналитика работы эксперта/агентаPM + ИгорьДолжно быть: Ответы, скорость, просрочки, жалобы, качество, выручка, начисления, conversion, repeat.Не хватает: Нет runtime dashboard/KPI по исполнителям.Следующий шаг: Собрать минимальные KPI на базе test order и первых 5 экспертов. A14Ежедневный dashboard PM/AdminPM + ИгорьДолжно быть: Утром видно: новые, без вопроса, без назначения, просрочено, жалобы, ответы, выручка, нагрузка.Не хватает: Нет dashboard по paid consultation.Следующий шаг: Сначала собрать report по одному test order, затем daily dashboard. A15QA доказательство админкиQA + PMДолжно быть: QA report показывает, что админ видит весь маршрут без ручного поиска.Не хватает: Нет фактического runtime QA.Следующий шаг: После READY gate провести QA и опубликовать PASS/WARN/STOP.

Ежедневный маршрут админа и PM

УтроНовые заказы, без вопроса, без назначения, дедлайны, ночные жалобы, загрузка 5 экспертов.
ДеньНазначения, контроль ответов, помощь исполнителям, no-send события, problem states.
ВечерПросрочки, качество, support decisions, начисления, stop-сигналы и короткий отчет PM.
Перед трафикомОдин safe test order должен пройти весь admin route и получить QA PASS/WARN/STOP.
