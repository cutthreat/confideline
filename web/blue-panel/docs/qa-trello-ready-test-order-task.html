Постановка задачи QA по контрольному заказу

Это готовый текст для карточки Trello тестировщику. QA стартует только после READY по gate и закрытия красных условий Игорем. До этого задача используется как стандарт будущей приемки.

Главное ограничение

QA не должен начинать runtime-проход, если нет safe test checkout, no-send режима, тестовых ролей и заполненных фикстур.

Что считается результатом

Публичный QA-отчет со скринами, order id/session id, PASS/WARN/STOP и задачами Игорю.

Заголовок карточки

Проверить контрольный заказ платной консультации без реальных платежей и писем

Описание карточки для Trello

Постановка задачи: Нужно пройти первый контрольный заказ платной консультации Nebula/YouDate в безопасном тестовом режиме и доказать скринами, что маршрут работает или показать, где он ломается. Проверка ведется по единой сетке FX/PF: фикстуры показывают готовность теста, PF01-PF12 показывают факты работы продукта. Условие старта: QA начинает проверку только после READY по gate. Если нет safe test checkout, no-send режима, тестовых ролей, доступов или заполненных фикстур, задача не считается FAIL продукта. Это фиксируется как блокер подготовки теста. Смысл задачи: Нам нужно не просто покликать сайт, а доказать, что первая платная консультация может пройти управляемо: клиент создает тестовый заказ, задает вопрос, эксперт/агент получает задачу, отвечает, админ видит весь путь, события фиксируются без реальной отправки писем, support может обработать проблемный сценарий. Шаги выполнения: 1. Проверить, что фикстуры заполнены: тестовый клиент, эксперт/агент, админ/support, before-state, admin URL, rollback rule. 2. Снять before-state клиента, исполнителя, админки, событий и support. 3. Пройти клиентский путь: оффер/услуга → test checkout → order success без real charge. 4. Проверить, что вопрос клиента связан с order/session/task. 5. Проверить админскую видимость: order, question, session/task, assignment, chat, events, support. 6. Проверить workspace исполнителя: задача, вопрос, срок, контекст, чат, отправка ответа. 7. Проверить, что ответ виден клиенту и админу по правам, закрывая PF07. 8. Проверить no-send события: preview есть, реальные письма/push/SMS не отправлены, закрывая FX09/PF08. 9. Создать один support/problem state: клиент недоволен ответом или эксперт просрочил ответ, закрывая FX05/PF09. 10. Проверить test_run_id / test marker и rollback rule. 11. Заполнить публичный QA-отчет: PASS/WARN/STOP, скрины, order id, session id, задачи Игорю, остаточные риски. Конечная цель: Публичный QA-отчет по одному контрольному заказу с вердиктом PASS/WARN/STOP и доказательствами по клиенту, админу, исполнителю, уведомлениям и support. Временные затраты: Ориентир 8-16 часов после закрытия gate. Если gate не готов, работа останавливается как PREPARE/STOP, а не тратится на шумный тест. Результат выполнения: Ссылка на Blue Panel QA shell: https://cutthreat.github.io/confideline/web/qa-reports/nebula-test-order-runtime-qa-shell-2026-06-05/ (by Codex) После фактического теста: ссылка обновляется на заполненный QA-отчет.

Stop conditions для QA

Стоп-сигналКак классифицироватьЧто делать
Нет safe checkout / есть риск real chargeSTOPНе начинать тест. Вернуть Игорю AC01.
Нет no-send режима / могут уйти реальные письмаSTOPНе начинать тест. Вернуть Игорю AC06.
Нет доступа к роли или админкеRETEST_AUTH_REQUIREDНе считать багом продукта. Заполнить фикстуры/доступы.
Order создан, но question/session не связаныFAILФиксировать дефект маршрута, задача Игорю AC02-AC03.
Эксперт не видит задачуFAILФиксировать дефект workspace/assignment, задача Игорю AC04-AC05.
Основной маршрут работает, но админке неудобноWARNНе разрешать трафик автоматически; оформить improvement отдельно.
