Что отправить тестировщику после READY gate

Это короткий рабочий brief для QA. Он не запускает проверку сейчас: текущий gate остается STOP. Страница нужна, чтобы после ответа Игоря и допуска исполнителя тестировщик сразу получил понятный маршрут, evidence names и формат результата.

QA сейчас STOPготово как briefpaid traffic запрещенPASS/WARN/STOP формат
PM-решение

Тестировщик не должен “просто посмотреть сайт”. Он должен доказать PF01-PF12 по одному test_run_id и вернуть отчет, который можно показать Игорю, Заказчику и использовать для пересчета светофора.

Когда отправлять

Только после READY: безопасный заказ от Игоря, no-send, допущенный исполнитель, роли/доступы, admin route и лист proof.

Копируемый текст запроса

QA, задачу запускаем только после READY по gate старта QA. Цель проверки: доказать один полный контрольный заказ Nebula/YouDate от клиента до ответа исполнителя и support, без реального списания денег и без реальной отправки писем/сообщений. Перед стартом проверить STOP/READY: 1. Есть safe test order от Игоря: order_id, test_run_id, no real charge. 2. Есть no-send режим: события создаются, реальные письма/SMS/push не уходят. 3. Есть минимум один допущенный исполнитель для test order. 4. Есть тестовые роли/доступы: клиент, админ, исполнитель, support. 5. Есть order/question/session binding и admin route. 6. Есть место фиксации proof: лист фактов PF01-PF12. Если любой пункт не готов — QA не стартует, вернуть STOP с причиной и владельцем. Маршрут проверки: 1. Открыть клиентский оффер/экран услуги и зафиксировать, что покупает клиент. 2. Создать или открыть safe test order. 3. Проверить заказ в админке. 4. Проверить, что вопрос клиента связан с заказом. 5. Проверить карточку консультации/session/task. 6. Назначить или проверить назначение исполнителя. 7. Зайти под исполнителем и открыть рабочее место. 8. Отправить тестовый ответ. 9. Проверить ответ со стороны клиента и админа. 10. Проверить no-send event log/preview по ключевым событиям. 11. Создать/проверить support problem state по этому заказу. 12. Заполнить лист фактов и итоговый verdict. Что вернуть PM: - публичный QA-отчет или заполненный report shell; - итог PASS/WARN/STOP; - order_id, test_run_id, session/task id, question_id, performer_id, answer_id, support_case_id; - скрины/логи по evidence names 01-12; - список дефектов для Игоря: факт, ожидание, как повторить, где смотреть, severity, retest path; - что можно показать Заказчику; - остаточные риски и следующий шаг. PASS: PF01-PF09 и PF12 доказаны, нет real charge/send, QA может объяснить весь путь по скринам. WARN: Основной путь работает, но есть некритичные долги UX/текста/логов/cleanup; paid traffic не включаем до решения PM. STOP: Любой критический PF01-PF09 или PF12 не доказан; есть риск real charge/send; потеряна связка order/question/session/workspace/support. Ссылки: - Gate старта QA: https://cutthreat.github.io/confideline/web/blue-panel/docs/qa-start-readiness-checklist.html - QA-пакет: https://cutthreat.github.io/confideline/web/blue-panel/docs/qa-test-order-execution-brief.html - Лист фактов: https://cutthreat.github.io/confideline/web/blue-panel/docs/test-order-proof-capture-sheet.html - Публичный report shell: https://cutthreat.github.io/confideline/web/blue-panel/docs/test-order-runtime-public-report-shell.html

Какой результат принимается

PASSPF01-PF09 и PF12 доказаны, нет real charge/send, весь путь можно объяснить по скринам.
WARNОсновной путь работает, но есть некритичные долги; paid traffic не включаем до решения PM.
STOPКритичный PF не доказан, есть риск real charge/send или потеряна связка order/question/session/workspace/support.
