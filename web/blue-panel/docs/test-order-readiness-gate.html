Можно ли начинать контрольный заказ?

Эта страница отделяет подготовку теста от самого теста. Если здесь есть красный пункт, QA не должен начинать проход, потому что результат будет не доказательством работы сервиса, а шумом из-за неподготовленных условий.

сейчас gate не закрытможно готовить данныецель: допуск к QA-проходу
PM-решение

До первого runtime QA нужно закрыть минимальные условия: test checkout без списания, no-send уведомления, тестовые роли, доступ к админке, тестовая услуга, support-сценарий и место публикации отчета.

Что считается успехом gate

Все критические условия в зеленом статусе. После этого QA проходит test order и заполняет отчет PASS/WARN/STOP.

Исполнительная матрица gate · что закрываем до QA

Смысл матрицы: это не список пожеланий. Это входной контроль перед runtime QA. Если красные пункты не закрыты, тест не запускается. Желтые пункты PM/QA могут готовить без пользователя. Зеленым считается только формат отчета, а не работа сайта.

TG05Тестовая услуга и оффер
Тест должен проверять коммерческую услугу, а не пустую техническую операцию. TG06Question intake связан с order
Если вопрос живет отдельно от заказа, эксперт не получает понятную задачу.		ИгорьSTOPОдин вопрос виден клиенту, админу и эксперту/агенту с тем же order/session id.PM задает тестовый вопрос и критерий видимости.Игорю связать order → question → session/task.
TG07Expert/agent workspace на тестовом заказе
5 экспертов не смогут работать, если задача не появляется в их рабочем контуре.		Игорь + QASTOPЭксперт/агент видит задачу, срок, контекст, чат, действие ответа, статус после ответа.PM фиксирует минимальный набор полей рабочего места.Проверить вместе с test order.
TG08Один support/failure state
Первые продажи почти всегда дают проблемы; support нельзя оставлять после запуска.		PM + QA + ИгорьPREPAREТикет/обращение связано с order/session/chat/expert и имеет статус решения.PM выбирает безопасный сценарий: эксперт не ответил или клиент недоволен.Включить problem state в QA route.
TG09Имена evidence и место отчета
Без стандарта proof результат теста будет трудно проверить и передать Игорю.		PM + QAREADY как форматQA template, список имен скринов, будущий public report path.PM уже подготовил шаблон и имена evidence; QA использует их без переизобретения.Заполнить после реального test order.
TG10Rollback / test data isolation
Тестовые данные не должны попасть в реальные метрики, выплаты и customer records.		QA + ИгорьPREPAREМаркер test data, что удалить/архивировать, что оставить как proof.PM фиксирует правило: ничего не удалять до публикации QA-отчета; после отчета cleanup по списку.Уточнить технический способ маркировки test data.

Решение gate

ВердиктКогда ставитьЧто делать дальше
READYВсе критические условия закрыты, real payment/email отключены, QA знает роли и маршрут.Запускать QA-пакет test order и заполнять отчет.
PREPAREКритические риски не затронуты, но не хватает ролей, вопроса, услуги, support-сценария или before-state.PM/QA готовят данные без обращения к production-платежам/письмам.
STOPНет safe checkout, no-send, доступа к админке или есть риск реальных платежей/писем.Остановить QA и вернуть задачу Игорю/PM с конкретным блокером.

Что делать без участия пользователя

PM сам готовитТекст вопроса, support-сценарий, чеклист evidence, структуру отчета, ссылки в Blue Panel и CSV.
QA сам готовитBefore-state, имена скринов, порядок прохода, фиксацию PASS/WARN/STOP.
Игорю передается только конкретикаSafe test order, no-send, admin visibility, role/workspace, support card. Без общих слов “проверьте сайт”.
Пользователь нужен только при gateЗакрытый доступ, конфликт источников, legal/payment/founder решение или production-риск.
