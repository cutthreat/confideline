# Partner Interactions Analytics MVP

Дата: 2026-05-20
Проект: Confideline / Nebula
Задача: админская таблица активных действий между клиентами и экспертами, закрепленными за конкретным партнером.

## Цель

Показать партнеру/администратору, кто и кому совершал активные действия:

- клиент -> эксперт;
- эксперт -> клиент.

В первой версии считаем только пары, где одна из сторон является экспертом, закрепленным за выбранным партнером. Остальные связи, роли операторов и расширенная модель прав остаются вне MVP.

## Периоды

MVP-фильтры:

- сегодня;
- 7 дней;
- 30 дней;
- весь период.

Решение: считать периоды по бизнесовой зоне `Europe/Minsk`, если в production-конфигурации проекта не задан другой явный стандарт.

## Надежные источники действий

| Действие | Источник | Направление | Как считать в MVP | Статус |
|---|---|---|---|---|
| Просмотр анкеты эксперта | `guest` | `from_user_id -> visited_user_id` | По `updated_at` как "был визит в периоде" | Можно считать, но это не полная история всех повторных просмотров |
| Добавление в избранное | favorites/bookmarks source | клиент -> эксперт | По `created_at`, только если функционал реально используется | Включать только после подтверждения источника |
| Начало диалога | `message` или event-log | клиент -> эксперт | Первое клиентское сообщение или отдельное событие начала диалога | Можно считать из сообщений, лучше закрепить отдельным event-log |
| Сообщение клиента | `message` | клиент -> эксперт | Количество клиентских сообщений по `created_at` | Можно считать |
| Ответ эксперта | `message` | эксперт -> клиент | Количество ответов эксперта по `created_at` | Можно считать |
| Оплата консультации | orders/payment/balance source | клиент -> эксперт | Только успешная оплата консультации с pair-level связкой | Требует точного production-источника |
| Повторное обращение | event-log или производно из диалогов/оплат | клиент -> эксперт | Повторное обращение клиента после предыдущего взаимодействия | Лучше фиксировать отдельным событием или явно описанной формулой |
| Блокировка | `block` | `from_user_id -> blocked_user_id` | По `created_at` | Можно считать текущие/сохраненные блокировки |
| Жалоба | `report` | `from_user_id -> reported_user_id` | По `created_at`, можно дополнительно показывать причины | Можно считать |

## Спорные или отсутствующие источники

| Показатель | Проблема | Решение для MVP |
|---|---|---|
| Оплата консультации | Нужно найти точную production-связку оплаты с клиентом, экспертом, статусом, временем и источником | Не использовать для санкций/выплат, пока источник не подтвержден. Если источника нет, нужна доработка логирования события |
| Повторные просмотры профиля | `guest` хранит одну пару пользователей и обновляет `updated_at` с порогом повторного визита | В MVP считать "визит был в периоде", не обещать точное количество всех открытий |
| Кто реально выполнял действие за экспертскую анкету | Сейчас считаем действие по user-id эксперта/клиента | Операторскую идентичность партнера/сотрудника вынести во вторую фазу |

## Что уже подтверждено на live/admin

- Страница закрепленных анкет за партнером существует: `https://confideline.com/ru/admin/chief-under/index?userId=15`.
- Для партнера `userId=15` live-админка показывает закрепленную анкету `Orion Esposito / OrionEsposito`, user id `184`.
- В live-админке есть страницы сообщений, жалоб, заказов и balance transactions.
- `users-log` сейчас похож больше на журнал админских действий, а не на полный журнал пользовательских взаимодействий.
- В QA-контуре уже есть рабочий сценарий чтения закрепленных анкет через `/en/admin/chief-under/index?userId=1` и отправки ответов от анкеты через admin chat API: `/admin/chat/conversations` и `/admin/chat/message-create`.

## MVP-таблица

Минимальная строка:

- `Кто`: user id, имя, username, роль в паре;
- `Кому`: user id, имя, username, роль в паре;
- `Направление`: клиент -> эксперт или эксперт -> клиент;
- счетчики действий по колонкам.

Порядок колонок должен идти по воронке консультации:

```text
просмотр анкеты -> избранное -> начало диалога -> сообщения клиента -> ответы эксперта -> оплата консультации -> повторное обращение -> блокировки -> жалобы
```

Минимальные колонки счетчиков:

- визиты;
- добавления анкеты в избранное, если источник подтвержден;
- начало диалога;
- сообщения клиента;
- ответы эксперта;
- оплаты консультаций;
- повторные обращения;
- блокировки;
- жалобы;

## Рекомендация по реализации

1. Добавить read-only admin route для выбранного партнера.
2. Получать список expert user ids из relation/table, которую использует live `chief-under`.
3. Собрать агрегаты по каждому источнику в единый набор пар `actor_id -> target_id`.
4. Фильтровать только пары, где ровно одна сторона входит в список закрепленных expert ids.
5. Использовать стандартный Yii2 `GridView`/`ActiveDataProvider`, чтобы сохранить привычные фильтры и сортировки админки.
6. Для "оплаты консультации" сначала найти production-источник. Если его нет, добавить отдельное событие/лог перед включением счетчика.

## Реализация MVP от 2026-05-20

Целевой локальный вариант: `Chat/youdate-2.0.2-yii2/Source/youdate_extracted/application`.

Добавлено:

- `modules/admin/controllers/PartnerInteractionController.php` - read-only admin route `/admin/partner-interaction/index`;
- `modules/admin/services/PartnerInteractionAnalyticsService.php` - агрегация действий по парам `actor -> target`;
- `modules/admin/views/partner-interaction/index.php` - таблица с фильтрами `partnerId`, `period`, fallback `expertIds`;
- пункт меню `Messages -> Partner interactions`.

Страница не меняет пользовательские данные. Если таблица `chief_under` не найдена или поля отличаются от ожидаемых, страница покажет предупреждение; для диагностики можно передать `expertIds` вручную.

## Стоп-условие перед production deploy

Не выкатывать в production без проверки точного source-of-truth варианта для live-админки: локальный `youdate-2.0.2-yii2` содержит dating-функции, но live-специфичные `chief-under`/partner-разделы в нем не найдены.

Если исходник live-раздела не будет найден, безопасный путь для первой реализации:

1. сделать отдельный admin route в выбранном Yii2-варианте;
2. добавить/перенести минимальную модель связи партнера с анкетами по фактической структуре production table;
3. перед включением в production сверить имя таблицы и поля связи на live/staging базе.
