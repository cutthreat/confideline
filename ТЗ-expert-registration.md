# ТЗ: страница регистрации эксперта для Confideline

## 1. Результат
- Нужен отдельный поток регистрации эксперта в стиле careers/job application, а не обычный user signup.
- На фронте уже подготовлен preview-макет: `H:\GPT-Codex\Confideline\web\expert-registration-mockup.html`.
- Задача backend-разработки: подготовить сущности, маршруты и админ-процесс так, чтобы новый дизайн можно было натянуть без переделки логики.
- Важно: новая страница должна быть встроена в визуальную систему текущего `confideline.com`, а не выглядеть как отдельный внешний HR-лендинг.

## 2. Факты по текущему проекту
- Базовый Yii2 signup уже существует в `H:\GPT-Codex\Confideline\Chat\youdate-2.0.2-yii2\Source\youdate_extracted\application\controllers\RegistrationController.php`.
- Текущая форма `RegistrationForm` создает `User` + `Profile` и подходит для обычного пользователя, а не для ручной экспертской модерации.
- Текущий публичный signup использует поля: `email`, `username`, `password`, `name`, `sex`, `country`, `city`, `dob`, `captcha`.
- В текущей админке уже есть инфраструктура Yii2-модуля `admin`, но нет отдельного контура под expert applications.

## 3. Вывод
- Экспертскую регистрацию нельзя безопасно строить как прямую надстройку над текущим `RegistrationForm`.
- Нужен отдельный модуль/контур данных: заявка эксперта, статусы модерации, история решений, отдельный список в админке.
- Возможна интеграция с будущим `User` только после approve, а не в момент отправки формы.

## 4. Scope
- Только подготовка функционала под будущий новый дизайн.
- Без сложной логики биллинга, расписаний, мэтчинга и real-time.
- Без полноценного кабинета эксперта на этом этапе.

## 5. Done when
- Есть отдельная сущность заявки эксперта.
- Есть endpoint для приема формы.
- Есть thank-you сценарий после отправки.
- Есть админ-список заявок с фильтрами и карточкой просмотра.
- Есть статусы и базовый workflow модерации.
- Есть возможность позже привязать approve-заявку к будущему аккаунту эксперта.

## 6. Как проверить
1. Открыть preview-макет и сверить блоки страницы: hero, benefits, requirements, process, FAQ, form.
2. Убедиться, что backend принимает форму в отдельную таблицу, а не пишет сразу в `user`.
3. Убедиться, что новая заявка появляется в админке со статусом `new`.
4. Проверить смену статусов `new -> in_review -> approved / rejected / needs_info`.
5. Проверить, что после `approved` можно безопасно инициировать следующий этап onboarding без ручной пересборки данных.

## 7. Контракт фронта
- Рекомендуемый production route: `/experts/apply` или `/careers/experts`.
- Блоки страницы:
  - hero с оффером и CTA;
  - преимущества/почему у нас;
  - кого ищем;
  - процесс отбора;
  - FAQ;
  - форма заявки.
- По стилю страница должна наследовать текущий сайт:
  - существующий header/footer;
  - текущую фиолетово-розовую палитру;
  - существующие кнопки и базовые формы;
  - общую Bootstrap/Yii2 структуру текущего фронта.

## 8. Поля формы
- `full_name` — обязательное.
- `display_name` — обязательное, публичное имя эксперта.
- `email` — обязательное, уникальность желательно проверять по заявкам и по существующим пользователям.
- `messenger_contact` — обязательное.
- `specializations` — обязательное, множественный выбор.
- `languages` — обязательное.
- `experience_range` — обязательное.
- `country` — обязательное.
- `timezone` — обязательное.
- `availability_text` — обязательное.
- `about_text` — обязательное.
- `portfolio_links` — необязательное, строка или массив ссылок.
- `consent_moderation` — обязательное.
- `consent_test_task` — обязательное.
- `consent_truthfulness` — обязательное.

## 10. Статусы
- `new`
- `in_review`
- `needs_info`
- `approved`
- `rejected`
- `archived`

## 11. Workflow
1. Кандидат отправляет форму.
2. Создается запись `expert_application` со статусом `new`.
3. Кандидат видит thank-you экран или success-блок.
4. Администратор/модератор открывает заявку в админке.
5. Модератор меняет статус на `in_review`, `needs_info`, `approved` или `rejected`.
6. При `approved` появляется действие:
   - либо создать будущий expert account,
   - либо передать заявку в отдельный onboarding flow.

## 12. Админка
- Нужен раздел `Expert Applications` в `admin` модуле.
- Список заявок:
  - ID
  - дата
  - имя
  - email
  - специализация
  - страна
  - статус
  - ответственный
- Фильтры:
  - статус
  - дата
  - страна
  - специализация
  - поиск по имени/email
- Карточка заявки:
  - все поля анкеты
  - внутренний комментарий модератора
  - история смены статуса
  - действия approve/reject/request info/archive

## 13. Email и уведомления
- После отправки формы отправлять кандидату подтверждение приема заявки.
- После смены статуса опционально отправлять уведомление:
  - `needs_info`
  - `approved`
  - `rejected`
- Текст уведомлений вынести в отдельные шаблоны, не хардкодить в контроллере.

## 14. Технические рекомендации
- Не использовать существующий `RegistrationForm` как базовую модель для expert flow.
- Создать отдельный `ExpertApplicationForm`.
- Создать отдельный controller, например `ExpertApplicationController`.
- Не создавать `User` автоматически на submit.
- Все множественные поля хранить как JSON или через связующую таблицу, в зависимости от дальнейших планов.
- Валидации делать server-side; client-side только дублирует UX.
- Сразу предусмотреть защиту от спама:
  - rate limit,
  - honeypot или captcha,
  - логирование IP/user-agent.
